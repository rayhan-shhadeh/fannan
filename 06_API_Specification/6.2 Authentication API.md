# 6.2 Authentication API

## Scope
The Authentication API is the HTTP contract for the corresponding FANNAN MVP module. It follows [6.0 API Architecture & Standards](6.0%20API%20Architecture%20%26%20Standards.md) and [6.1 API Conventions](6.1%20API%20Conventions.md). Base path: `/auth`. This is specification documentation, not implementation code.

## Actors, authentication, and authorization
**Actors:** Customer, artist, admin, anonymous.

**Authorization:** Public registration/login; refresh requires refresh token; logout revokes current refresh token; MFA/recovery policy deferred to the missing Section 05 authentication/authorization source. All access checks are server-side and use the identity/role model in the missing Section 05 authentication/authorization source; do not infer role or ownership from request fields.

## Endpoint inventory
POST /auth/register; POST /auth/login; POST /auth/refresh; POST /auth/logout; POST /auth/password/forgot; POST /auth/password/reset; GET /auth/sessions; DELETE /auth/sessions/{id}. All endpoints return the common error envelope and `X-Request-Id`. Public endpoints still apply visibility, moderation, and rate-limit rules in [6.17](6.17%20API%20Security%20%26%20Rate%20Limiting.md).

## Representations and examples
Email/password and token schemas; never return password or raw refresh token in logs. Login response: `{ "accessToken":"access_token_example", "expiresIn":900, "refreshToken":"refresh_token_example", "user":{"id":"usr_1","roles":["customer"]} }`. Responses omit secrets and fields outside the actor's scope. Money, timestamps, IDs, pagination, and errors follow [6.1](6.1%20API%20Conventions.md).

## Validation and business rules
email format/verified status, password policy and lockout come from the missing Section 05 authentication/authorization source; rate-limit login/recovery; generic forgot-password response prevents account enumeration. Validation occurs before side effects; authorization occurs before revealing whether a protected resource exists (use indistinguishable 404 where required).

## Idempotency, pagination, and concurrency
Logout/revocation is idempotent. Registration uses Idempotency-Key. Lists use cursor pagination (`limit`, `cursor`) and allow-listed filters/sorts. Mutations use `If-Match` where a version is returned. Retries and conflict handling follow [6.0](6.0%20API%20Architecture%20%26%20Standards.md).

## State transitions and events
Events: UserRegistered, UserAuthenticated, SessionRevoked, PasswordResetRequested, PasswordChanged. Event payloads include `eventId`, `type`, `occurredAt`, `aggregateId`, `actorId` (when safe), and schema version. Events are emitted after commit, delivered at least once, and must not contain secrets.

## Security and privacy
TLS, secure cookie/storage guidance, token rotation, replay detection, audit authentication events. Apply centralized transport, input, logging, abuse, and rate-limit rules from [6.17](6.17%20API%20Security%20%26%20Rate%20Limiting.md), without defining a second authentication model.
