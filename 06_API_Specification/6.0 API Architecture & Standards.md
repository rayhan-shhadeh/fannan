# 6.0 API Architecture & Standards

## Purpose and scope

This suite specifies the FANNAN MVP HTTP API for the marketplace described in `03_PRODUCT_REQUIREMENTS`. It is exposed by a NestJS modular monolith; modules share one transactional boundary and database while retaining explicit domain ownership. Identity and role truth remain in [5.5 Authentication & Authorization](../05_System_Architecture/5.5%20Authentication%20%26%20Authorization.md).

## Architectural baseline

- HTTPS REST/JSON under `/api/v1`; web and mobile use the same resource contracts.
- Commands commit authoritative changes atomically; side effects use committed outbox events.
- PostgreSQL is authoritative for business state. Providers are adapters.
- Search is a read model and never the authority for price, stock, order, or permission.
- MVP payment is COD; online provider integration is deferred.

## Base URL and media types

Production base URL is `https://{host}/api/v1`. JSON requests use `Content-Type: application/json`; responses use `application/json; charset=utf-8`. File uploads use the presigned flow in [6.15](6.15%20Media%20API.md). Clients send `Accept: application/json` and `X-Request-Id`; the server generates one when absent and returns it on every response.

## Cross-cutting response contracts

Errors always have this shape:

```json
{"error":{"code":"VALIDATION_ERROR","message":"Request is invalid","details":[{"field":"email","reason":"invalid_format"}],"requestId":"req_123"}}
```

Lists use:

```json
{"data":[{"id":"..."}],"pagination":{"nextCursor":"...","hasMore":false}}
```

Dates are RFC 3339 UTC. Money at the API boundary is an integer `amount` in minor currency units plus an ISO 4217 `currency`. IDs are opaque strings. Never expose database IDs, provider tokens, password hashes, or internal stack traces.

## Authentication, authorization, and ownership

Bearer access and rotating refresh tokens follow [5.5](../05_System_Architecture/5.5%20Authentication%20%26%20Authorization.md). Guest checkout uses only the scoped checkout-session and order-access tokens defined there. Mutations require an authenticated actor or an explicitly supported guest checkout session. Ownership is checked against the resource owner, not a client-supplied role or ID.

## Reliability standards

- Financial, order, offer, media, and notification mutations accept `Idempotency-Key`; reuse with a different request fingerprint returns `409 IDEMPOTENCY_KEY_REUSED`.
- Conditional writes use `If-Match`/ETag where a version is returned; stale versions return `409 VERSION_CONFLICT`.
- Pagination is cursor-based with `limit` 1–100 and allow-listed filters/sorts.
- Retry only `429`, `502`, `503`, and `504`, and never retry a non-idempotent command without its key.
- Domain events are at-least-once and deduplicated by `eventId` after outbox publication.

## Versioning and compatibility

Additive fields and enum values are backward-compatible; clients ignore unknown fields. Breaking changes require a new major URL version and migration notes. Deprecated fields carry a sunset date.

## Documentation dependencies

Sections 03–05 are the source of truth for product behavior, persistence, identity, security, and operations. Any future conflict must be resolved by an architecture decision record before changing an API contract.
