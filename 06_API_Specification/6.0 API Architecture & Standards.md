# 6.0 API Architecture & Standards

## Purpose and scope
This suite specifies the FANNAN MVP HTTP API for the marketplace described in `02_PRODUCT_REQUIREMENTS`. It is documentation only. The API is exposed by a modular monolith; modules share one transactional boundary and database while retaining explicit domain ownership. Identity and role truth is not defined in this repository because the required Section 05 source directory is absent; this suite must not define or assume it.

## Architectural baseline
- **Transport:** HTTPS REST/JSON under `/api/v1`; browser and mobile clients use the same resource contracts.
- **Runtime:** MVP modular monolith with modules for identity, catalog, discovery, cart, checkout/orders, payments, shipping, offers, reviews, notifications, media, and administration.
- **Transactions:** Commands that change an aggregate commit atomically. Cross-module side effects are recorded as domain events/outbox records and processed asynchronously.
- **Read/write shape:** Resource representations are stable and versioned; list endpoints return a page envelope. Search may use a dedicated read index but remains owned by the Search module.
- **External boundaries:** Payment, shipping, email/push, and object storage providers are adapters. Provider secrets and callbacks never pass through clients.
- **Availability:** A provider failure must produce a safe pending/failed state, not a partial order or leaked provider detail. See 5.15 Infrastructure Architecture (source directory absent).

## Base URL and media types
`https://{host}/api/v1` is the production base. Requests use `Content-Type: application/json`; responses use `application/json; charset=utf-8`. File uploads use the documented presigned media flow in [6.15](6.15%20Media%20API.md). Clients send `Accept: application/json` and `X-Request-Id` (UUID); the server generates one when absent and returns it on every response.

## Cross-cutting response contracts
Success examples are resource-specific. Errors always have this shape:
```json
{"error":{"code":"VALIDATION_ERROR","message":"Request is invalid","details":[{"field":"email","reason":"invalid_format"}],"requestId":"req_123"}}
```
List responses use:
```json
{"data":[{"id":"..."}],"pagination":{"nextCursor":"...","hasMore":false}}
```
Dates are RFC 3339 UTC; money is integer minor units plus ISO 4217 currency; IDs are opaque strings; enum additions are backward-compatible. Never expose database IDs, provider tokens, password hashes, or internal stack traces.

## Authentication, authorization, and ownership
Bearer access tokens and refresh tokens follow the missing Section 05 authentication/authorization source. Public reads are explicitly marked in each domain file. Mutations require an authenticated actor and server-side policy evaluation. Ownership is checked against the resource owner, not a client-supplied role or ID. Admin operations require the roles/permissions defined by the missing Section 05 authentication/authorization source and are audited. See [6.17 API Security & Rate Limiting](6.17%20API%20Security%20%26%20Rate%20Limiting.md).

## Reliability standards
- Mutating requests that create financial, order, offer, media, or notification side effects accept `Idempotency-Key`; the same key and request fingerprint return the original result, while a different payload returns `409 IDEMPOTENCY_KEY_REUSED`.
- Conditional writes may use `If-Match` with a version/ETag; stale versions return `409 VERSION_CONFLICT`.
- Pagination is cursor-based (`limit` 1–100, opaque `cursor`), deterministic, and scoped to the caller's visibility. Filters are allow-listed.
- Retries use exponential backoff only for `429`, `502`, `503`, and `504`; never blindly retry a non-idempotent command without its key.
- Domain events are at-least-once. Consumers deduplicate by `eventId`; event publication is after commit through an outbox.

## Versioning and compatibility
The major URL version changes only for breaking changes. Additive fields and enum values are compatible; clients must ignore unknown fields. Deprecated fields carry a sunset date in the changelog and remain for one major version. Breaking changes require a new endpoint version and migration notes.

## Documentation dependencies and open issues
The required Sections 03, 04, and 05 source directories are absent from this repository. This is a blocking dependency before implementation. Token claims, permission names, tenancy, persistence ownership, event transport, and retention rules remain open decisions; any conflict must be resolved by an architecture decision record, not an API client assumption.
