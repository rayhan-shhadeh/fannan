# 6.9 Checkout & Orders API

## Scope
The Checkout & Orders API is the HTTP contract for the corresponding FANNAN MVP module. It follows [6.0 API Architecture & Standards](6.0%20API%20Architecture%20%26%20Standards.md) and [6.1 API Conventions](6.1%20API%20Conventions.md). Base path: `/checkout and /orders`. This is specification documentation, not implementation code.

## Actors, authentication, and authorization
**Actors:** Authenticated customer; artist sees fulfilled-order subset; admin support.

**Authorization:** Customer owns checkout/order; fulfillment actors see only assigned/necessary data; admin permission is audited. All access checks are server-side and use the identity/role model in the missing Section 05 authentication/authorization source; do not infer role or ownership from request fields.

## Endpoint inventory
POST /checkout/quote; POST /checkout; GET /orders; GET /orders/{id}; POST /orders/{id}/cancel; POST /orders/{id}/confirm-delivery; GET /artists/me/orders. All endpoints return the common error envelope and `X-Request-Id`. Public endpoints still apply visibility, moderation, and rate-limit rules in [6.17](6.17%20API%20Security%20%26%20Rate%20Limiting.md).

## Representations and examples
Order `{id,status,items,totals,shippingAddressSummary,paymentStatus,fulfillmentStatus,createdAt}`. Checkout example `{cartId,addressId,paymentMethodId,offerId}` returns order/payment next action. Responses omit secrets and fields outside the actor's scope. Money, timestamps, IDs, pagination, and errors follow [6.1](6.1%20API%20Conventions.md).

## Validation and business rules
Reprice cart, stock, address, tax/shipping, offer, payment authorization, and seller eligibility transactionally; no client total. Validation occurs before side effects; authorization occurs before revealing whether a protected resource exists (use indistinguishable 404 where required).

## Idempotency, pagination, and concurrency
Quote is read-only; checkout/cancel/confirm require keys. Order reads cursor-paginated. Lists use cursor pagination (`limit`, `cursor`) and allow-listed filters/sorts. Mutations use `If-Match` where a version is returned. Retries and conflict handling follow [6.0](6.0%20API%20Architecture%20%26%20Standards.md).

## State transitions and events
State: pending_payment -> paid -> processing -> shipped -> delivered; cancellation allowed before fulfillment; refund/return outcomes are explicit. Events: OrderCreated, PaymentAuthorized, OrderCancelled, OrderShipped, OrderDelivered. Event payloads include `eventId`, `type`, `occurredAt`, `aggregateId`, `actorId` (when safe), and schema version. Events are emitted after commit, delivered at least once, and must not contain secrets.

## Security and privacy
Minimize PII, idempotent order creation, authorization before state change, audit cancellation/refunds. Apply centralized transport, input, logging, abuse, and rate-limit rules from [6.17](6.17%20API%20Security%20%26%20Rate%20Limiting.md), without defining a second authentication model.
