# 6.10 Payments API

## Scope
The Payments API is the HTTP contract for the corresponding FANNAN MVP module. It follows [6.0 API Architecture & Standards](6.0%20API%20Architecture%20%26%20Standards.md) and [6.1 API Conventions](6.1%20API%20Conventions.md). Base path: `/payments`. This is specification documentation, not implementation code.

## Actors, authentication, and authorization
**Actors:** Guest checkout session or authenticated customer for COD order payment state; finance admin. Online provider webhooks are deferred from MVP.

**Authorization:** The checkout session or authenticated customer can access only the payment state attached to the current order; admins see masked reconciliation data. Online provider callbacks are not enabled in MVP. All access checks are server-side and use [5.5 Authentication & Authorization](../05_System_Architecture/5.5%20Authentication%20%26%20Authorization.md); do not infer role or ownership from request fields.

## Endpoint inventory
POST /payments/intents; GET /payments/{id}; POST /payments/{id}/confirm; POST /payments/{id}/cancel; POST /payments/webhooks/{provider} (deferred); GET /admin/payments/{id}/reconciliation. All endpoints return the common error envelope and `X-Request-Id`. MVP intent/confirm records COD selection and eligibility; no card data or provider token is accepted.

## Representations and examples
Payment `{id,orderId,status,amount,currency,methodSummary,nextAction,providerReferenceMasked}`; never return PAN/CVV. Responses omit secrets and fields outside the actor's scope. Money, timestamps, IDs, pagination, and errors follow [6.1](6.1%20API%20Conventions.md).

## Validation and business rules
Amount/currency must match server order, provider status allow-list, webhook timestamp/signature, duplicate event detection. Validation occurs before side effects; authorization occurs before revealing whether a protected resource exists (use indistinguishable 404 where required).

## Idempotency, pagination, and concurrency
Intent/confirm/cancel/webhook require Idempotency-Key or provider event ID. Lists use cursor pagination (`limit`, `cursor`) and allow-listed filters/sorts. Mutations use `If-Match` where a version is returned. Retries and conflict handling follow [6.0](6.0%20API%20Architecture%20%26%20Standards.md).

## State transitions and events
State: requires_action ? authorized ? captured ? failed/cancelled; refunds are linked to order policy. Events: PaymentAuthorized, PaymentFailed, PaymentCaptured, RefundCreated. Event payloads include `eventId`, `type`, `occurredAt`, `aggregateId`, `actorId` (when safe), and schema version. Events are emitted after commit, delivered at least once, and must not contain secrets.

## Security and privacy
PCI scope minimization, provider tokenization, webhook signature, replay protection, no sensitive logs. Apply centralized transport, input, logging, abuse, and rate-limit rules from [6.17](6.17%20API%20Security%20%26%20Rate%20Limiting.md), without defining a second authentication model.
