# 6.17 API Security & Rate Limiting

## Purpose
This document centralizes API security controls. It does not define identity, roles, claims, token issuance, or permission names; those remain authoritative in [5.5 Identity & Access Architecture](../05_SYSTEM_ARCHITECTURE/5.5%20Identity%20%26%20Access%20Architecture.md), which is unavailable in this checkout. Domain documents link here for enforcement rules.

## Baseline controls
- HTTPS/TLS at every hop; reject cleartext and invalid host/origin combinations.
- Validate content type, body size, encoding, schema, enum, and request ID. Reject unknown command fields.
- Authenticate bearer tokens through 5.5; never accept role/owner claims supplied in body or query. Authorize per resource and operation, then apply field-level filtering.
- Return generic protected-resource failures where disclosure would enable enumeration. Never expose stack traces, SQL/provider errors, secrets, token values, PAN/CVV, or raw storage paths.
- Use secure headers, CSRF protection where cookie credentials are used, strict CORS allow-list, and short-lived signed URLs for media.
- Encrypt sensitive data in transit and at rest per 5.13/5.15; minimize retention and redact logs per 5.14.

## Rate-limit policy
Limits are token-bucket style at the edge and application command layer. Exact numeric limits are deployment configuration and must be published in operational configuration, not hard-coded into clients. The following classes are mandatory:

| Class | Examples | Policy |
|---|---|---|
| Anonymous reads | catalog, discovery, search | Per-IP and route limit; cache safe public responses; challenge/deny abusive patterns. |
| Authenticated reads | profile, orders, notifications | Per-actor plus IP limit; ownership checks still apply. |
| Authentication | login, refresh, recovery | Strict per-account, IP, and device limits; progressive delay and lockout per 5.5. |
| Expensive queries | search, exports, metrics | Low concurrency, bounded filters, maximum page size, timeout and cost budget. |
| Financial/side-effect commands | checkout, payments, offers, uploads | Per-actor and route limit; require idempotency; never retry blindly. |
| Webhooks | payment/carrier callbacks | Provider identity/signature and event-ID dedupe; separate provider quota. |
| Admin | moderation, exports, refunds | Permission and step-up policy from 5.5; tight burst and audit requirements. |

A `429 RATE_LIMITED` response includes `Retry-After`, stable error code, and request ID. Rate limits must not be used as an authorization substitute. System-wide load shedding may return `503` and preserve command idempotency.

## Abuse and threat controls
Prevent credential stuffing, enumeration, scraping, offer spam, review spam, upload malware, request smuggling, injection, SSRF through provider URLs, and replayed callbacks. Enforce maximum query depth/cost, pagination caps, upload scanning, signed webhook timestamps, nonce/event dedupe, and alerting through 5.14. Apply step-up authentication for sensitive admin/payment actions where 5.5 requires it.

## Idempotency and replay
Required for payment, checkout/order creation, refunds, offers, media completion, shipment labels, notifications with external delivery, and destructive admin commands. Bind key to authenticated actor (or provider identity), route, and request fingerprint. Store result/status long enough for provider/client retries; return `409 IDEMPOTENCY_KEY_REUSED` for payload mismatch.

## Audit and observability
Audit authentication changes, authorization failures, admin actions, payment/order transitions, moderation, exports, webhook acceptance, and rate-limit decisions. Logs carry request ID, actor pseudonym, route, outcome, latency, and policy decision?not secrets or full PII. Security events feed the observability design in 5.14; retention and residency remain an open dependency on missing Section 03/04 and 5.x documents.

## Incident and dependency issues
Key management, WAF/edge controls, token algorithms, exact permission catalog, data classification, breach response, and provider signature contracts require confirmation against unavailable 5.5 and other mandatory sections. Record deviations as ADRs; do not create a competing auth or role model in API documentation.
