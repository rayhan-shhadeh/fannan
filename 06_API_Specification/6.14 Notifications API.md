# 6.14 Notifications API

## Scope
The Notifications API is the HTTP contract for the corresponding FANNAN MVP module. It follows [6.0 API Architecture & Standards](6.0%20API%20Architecture%20%26%20Standards.md) and [6.1 API Conventions](6.1%20API%20Conventions.md). Base path: `/notifications`. This is specification documentation, not implementation code.

## Actors, authentication, and authorization
**Actors:** Authenticated recipient; internal event consumers; admin templates.

**Authorization:** Users read/manage only their notifications and preferences; internal producers cannot impersonate recipients; admin template access is scoped. All access checks are server-side and use the identity/role model in the missing Section 05 authentication/authorization source; do not infer role or ownership from request fields.

## Endpoint inventory
GET /notifications; PATCH /notifications/{id}/read; POST /notifications/read-all; GET/PATCH /users/me/notification-preferences; GET /admin/notification-templates; PATCH /admin/notification-templates/{id}. All endpoints return the common error envelope and `X-Request-Id`. Public endpoints still apply visibility, moderation, and rate-limit rules in [6.17](6.17%20API%20Security%20%26%20Rate%20Limiting.md).

## Representations and examples
Notification `{id,type,channel,title,body,data,readAt,createdAt}`; preferences enumerate email/push/in-app and transactional exceptions. Responses omit secrets and fields outside the actor's scope. Money, timestamps, IDs, pagination, and errors follow [6.1](6.1%20API%20Conventions.md).

## Validation and business rules
Recipient and channel allow-lists, template variable schema, consent/unsubscribe rules, payload size, deduplication key. Validation occurs before side effects; authorization occurs before revealing whether a protected resource exists (use indistinguishable 404 where required).

## Idempotency, pagination, and concurrency
Read mutations are idempotent; producer events deduplicate by eventId; list cursor-paginated. Lists use cursor pagination (`limit`, `cursor`) and allow-listed filters/sorts. Mutations use `If-Match` where a version is returned. Retries and conflict handling follow [6.0](6.0%20API%20Architecture%20%26%20Standards.md).

## State transitions and events
State: queued -> sent/delivered or failed; retries use backoff and dead-letter review. Events: NotificationQueued, NotificationSent, NotificationFailed. Event payloads include `eventId`, `type`, `occurredAt`, `aggregateId`, `actorId` (when safe), and schema version. Events are emitted after commit, delivered at least once, and must not contain secrets.

## Security and privacy
Do not log message secrets/PII unnecessarily; prevent preference bypass for mandatory transactional notices. Apply centralized transport, input, logging, abuse, and rate-limit rules from [6.17](6.17%20API%20Security%20%26%20Rate%20Limiting.md), without defining a second authentication model.
