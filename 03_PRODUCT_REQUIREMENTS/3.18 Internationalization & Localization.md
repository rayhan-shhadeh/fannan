# FANNAN Internationalization & Localization

**Document ID:** FANNAN-SRS-I18N-3.18
**Status:** MVP product requirements baseline
**Launch locales:** Arabic (`ar`, RTL) and English (`en`, LTR)

## 1. Scope

Localization applies to the Next.js web application, React Native/Expo mobile application, dashboards, API messages, notifications, search, catalog content, validation, and accessibility. Domain values such as IDs, statuses, quantities, timestamps, and money remain language-neutral.

## 2. Locale resolution

Resolve locale in this order:

1. Explicit supported request preference.
2. Authenticated user's `preferred_locale`.
3. Browser or device locale.
4. English fallback.

Guests may retain a local preference until login. Saving a preference persists it on the user record. Unsupported locales resolve to English and produce observable telemetry.

## 3. Translation classes

- UI/system strings use stable namespaced translation keys.
- Marketplace content uses separate localized content records for artwork, profiles, categories, tags, and collections.
- Notification, email, and push templates are versioned by channel and locale.

Missing translations are valid. Content falls back to its source/default locale; UI and message resources fall back to English. Historical notifications retain the rendered snapshot, locale, and template version used.

## 4. Client requirements

Both clients must support RTL/LTR direction, locale-aware date/number/currency formatting, pluralization, accessible labels, long Arabic text, and runtime locale changes without changing domain semantics. Clients must not invent localized business wording or translate status codes inconsistently.

## 5. API and search requirements

The API accepts a locale preference and returns language-neutral codes plus resolved localized content where defined. Cache keys and ETags vary by locale. Search indexes approved Arabic and English fields independently, preserves display text, and applies documented fallback only when requested content is missing.

## 6. Acceptance criteria

- Every MVP user-facing string has an English key and an Arabic translation or an observable fallback fixture.
- Public pages and mobile screens render correctly in both directions.
- Money, dates, quantities, and statuses use the shared formatting and code contracts.
- Missing translations never change authorization, pricing, inventory, order, payment, or shipping behavior.
