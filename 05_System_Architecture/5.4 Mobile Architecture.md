# 5.4 Mobile Architecture

**Status:** MVP mobile-client architecture  
**Depends on:** 5.0 Architecture Decisions, 5.1 Architecture Overview, 5.2 Backend Architecture

## 1. Purpose

FANNAN Mobile is a React Native, Expo, and TypeScript client using Expo Router. This document owns mobile navigation, screen structure, API integration, state, secure storage, device behavior, network resilience, localization, accessibility, and push/deep-link behavior. It does not redefine backend business rules or detailed API contracts.

## 2. Architectural Goals

- Ship a reliable marketplace app with a small dependency and native footprint.
- Use the same REST API and domain semantics as Web.
- Support discovery, customer commerce, artist workflows, offers, and notifications required by MVP.
- Support Arabic (`ar`, RTL) and English (`en`, LTR) from first release.
- Handle intermittent networks without claiming offline mutations succeeded.
- Protect credentials, personal data, and digital media.
- Avoid offline-first infrastructure and device capabilities without a requirement.

## 3. Technology Stack

| Concern | Decision |
|---|---|
| Runtime | React Native + Expo + TypeScript |
| Navigation | Expo Router |
| API | Shared versioned FANNAN REST API |
| Authentication storage | Platform-secure storage through Expo-compatible capability; exact mechanism belongs to 5.5 |
| State | API/server state plus local screen state |
| Localization | Stable keys, locale-aware formatting, RTL/LTR |
| Push | Backend-owned localized notification payloads and delivery state |

No offline database, unnecessary native dependency, or separate mobile backend is required for MVP.

## 4. Mobile Model

```text
Expo Router screen -> feature UI -> typed API client -> REST API -> NestJS modules
```

Mobile owns navigation, presentation, local drafts, secure credential handling, permissions, push registration, and network UX. The backend owns pricing, inventory, orders, offers, payment/shipping state, authorization, notification wording, and PostgreSQL authority.

## 5. Project Structure

```text
app/
  (public)/ (auth)/ (customer)/ (artist)/ _layout.tsx
src/
  features/catalog/ features/search/ features/artist/ features/categories/
  features/favorites/ features/cart/ features/checkout/ features/orders/
  features/offers/ features/notifications/ features/account/
  components/ui/ components/layout/ components/feedback/
  lib/api/ lib/auth/ lib/i18n/ lib/formatting/ lib/storage/ lib/notifications/
  hooks/ types/ config/ theme/
```

`app` owns route composition and layouts. Features own mobile presentation and interactions. `lib/api` is the only transport boundary, `lib/storage` wraps secure/local persistence, and `lib/i18n` owns keys/direction helpers.

## 6. Expo Router and Navigation

Use route groups for public, authenticated customer, and authenticated artist surfaces. Root layout owns providers, theme, locale direction, authentication bootstrap, and global error handling. Protected-route redirects are UX only; API authorization remains mandatory.

Navigation includes public discovery/search/categories/artwork/artist pages; customer favorites/cart/checkout/orders/offers/account/notifications; and artist dashboard/products/profile/orders/offers/notifications. Exact tab/stack presentation is platform-specific. Labels and statuses are translated and deep links re-check authorization and ownership.

## 7. API Integration

The typed client handles environment/base URL, credentials, locale headers, cancellation/timeouts, normalized errors, pagination, safe retries, and mutation idempotency metadata. Mobile never accesses PostgreSQL, Prisma, Redis, S3 credentials, or provider APIs. Reconcile cached reads and every mutation with the authoritative API response.

## 8. State Ownership

Catalog, taxonomy, artists, availability, cart, orders, offers, notifications, and account data are server state. Screen drafts, filters, dialogs, navigation, and display preferences are local state. Cached availability is never authoritative; do not store price, inventory, order, offer, payment, or shipping state as local truth.

## 9. Authentication and Authorization

Store the backend-approved session/token mechanism only in platform-secure storage. Never place credentials/tokens in plain preferences, URLs, logs, or analytics. Handle expiry, logout, revoked sessions, and deletion explicitly. Customer and Artist are capabilities of one User; artist actions also require verification. Admin functionality is not assumed to be a mobile MVP surface.

Hiding a button is not authorization. Every mutation revalidates ownership, lifecycle, and permission on the server.

## 10. Marketplace and Product Flows

Use the same product, cart, order, offer, payment, and shipping concepts as Web. Support physical and digital works, unique and quantity inventory, favorites, checkout, order status, and eligible reviews.

Physical items expose shipping information; digital items expose entitlement/download only after backend authorization. Unique-item purchase conflicts and quantity reservation failures are recoverable states. Offers are finite-round structured forms/timelines, not chat, and never expose an artist's private minimum.

## 11. Checkout

Checkout uses a mobile step flow for cart validation, address/shipping information, review, and COD confirmation where applicable. The backend owns totals, inventory reservation, order creation, and payment state. Handle changed availability/prices, validation, duplicate taps, and interrupted network using server responses and idempotency semantics.

## 12. Internationalization

- All UI, validation, error, notification, and empty-state copy uses stable translation keys.
- Support `ar`/RTL and `en`/LTR at the root and across navigation, forms, dialogs, lists, icons, and typography.
- Resolve locale using explicit/user/device policy and English fallback; guests may keep a local preference until login.
- Persist authenticated preference through the backend.
- Format dates, numbers, quantities, and currency with locale-aware helpers.
- Missing translations fall back to English and remain observable.
- Artwork/profile/category/tag translations remain marketplace content, separate from UI resources.

Locale changes do not change domain values or business semantics.

## 13. Responsive and Accessible Mobile UI

Use adaptive layouts for phones and supported larger form factors. Handle safe areas, keyboard avoidance, touch targets, dynamic text sizing, long Arabic/English labels, orientation where supported, screen-reader labels, focus order, contrast, non-color status, and accessible loading/error announcements.

## 14. Media

Load images, previews, videos, and digital files through authorized backend/S3 flows. Mobile contains no storage credentials or unrestricted bucket access. Provide placeholders, retry states, accessibility descriptions, responsive sizing, and entitlement checks.

## 15. Device Capabilities

MVP may use secure storage, camera/photo selection for artist media, and push-token registration where required. Explain permissions and provide denial fallbacks. Do not add location, contacts, Bluetooth, or other native capabilities without an explicit requirement.

## 16. Offline and Network Resilience

MVP is not offline-first. Show connection/loading states, preserve safe unsent drafts where practical, optionally display clearly stale public reads, retry safe reads conservatively, and offer retry/reload for failed mutations. Never queue or display an order, offer, payment, or inventory mutation as successful without backend confirmation.

## 17. Push Notifications and Deep Links

Register device tokens through the backend-approved notification flow. Push title/body is localized by the notification/template system; the client does not invent business wording. Handle denied, expired, and invalid tokens as recoverable states.

Notification taps and external deep links navigate to authorized resources only after authentication, visibility, and ownership checks. Stale or deleted resources show a localized safe state.

## 18. Performance

Prioritize pagination, correctly sized images, incremental screen loading, minimized re-renders, and minimal native/JavaScript dependencies. Cache read data only with locale/user context and safe freshness. Measure before introducing an offline store or custom native performance layer.

## 19. Security

Use secure credential storage, TLS-configured API communication, safe deep-link parsing, no secrets in bundles, minimal sensitive local persistence, and protected media flows. Never log tokens, addresses, private offer values, payment information, or raw personal data.

## 20. Error, Loading, Empty, and Testing Architecture

Every screen defines loading, refresh, empty, unavailable, validation, unauthorized, conflict, network, and server-error states using translation keys and safe parameters.

Test formatting, locale direction, API mapping, accessible components, authentication, cart/checkout/offers, deep links, push handling, network interruption, secure storage, permissions, media, and end-to-end customer/artist flows in both languages.

## 21. Web vs Mobile Responsibility Matrix

| Concern | Shared semantics | Mobile-specific |
|---|---|---|
| API/domain/status/error contracts | Same backend contract | Native presentation |
| Authentication/authorization | Same server policy | Secure storage and route UX |
| Pricing/inventory/orders/offers | Backend authoritative | Display and input |
| Localization | Same keys/fallback/locale concepts | Direction and native layout |
| Media | Authorized backend flow | Loading/download UX |
| Notifications | Backend event/template state | Token registration/tap handling |
| Navigation | Resource destinations | Expo Router stacks/tabs |

## 22. Shared Concepts Between Web and Mobile

Both clients must share API contracts, domain terminology, status values, error semantics, authentication/authorization semantics, product/inventory/cart/order/offer/payment/shipping concepts, and localization behavior. They may differ in navigation, layout, interaction patterns, rendering strategy, device capabilities, and network presentation. Neither client may become authoritative for marketplace state.

## 23. MVP vs Future Evolution

| Area | MVP | Future |
|---|---|---|
| Offline | Graceful failure and safe drafts | Explicit offline workflows/conflict resolution |
| Push | Backend-driven localized push | Rich preferences/campaigns |
| Deep links | Authorized resource navigation | Broader sharing/deferred links |
| Background work | OS-supported push/media behavior | More background synchronization |
| Device features | Secure storage, media selection, push | Additional capabilities when justified |
| Performance | Pagination, image optimization, measured caching | Advanced native optimization |
| Shared code | Contracts and small utilities where useful | Broader shared packages |

## 24. Dependencies and Final Summary

5.1 defines system boundaries; 5.2 backend modules/execution; 5.5 authentication; 5.6 media; 5.7 localization; 5.8 search; 5.9 notifications; 5.12 caching; 5.13 security; and 5.14 observability. Section 06 defines detailed API contracts.

FANNAN Mobile is one React Native + Expo + TypeScript application using Expo Router and the same REST API as Web. It owns mobile navigation, secure storage, device permissions, push registration, native presentation, and network UX while the backend remains authoritative for all marketplace rules and state.
