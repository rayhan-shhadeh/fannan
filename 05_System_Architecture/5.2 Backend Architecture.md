# 5.2 Backend Architecture

**Document ID:** FANNAN-ARCH-5.2  
**Status:** MVP NestJS modular-monolith architecture  
**Depends on:** 5.0 Architecture Decisions and 5.1 Architecture Overview

## 1. Purpose

This document translates the high-level architecture into a practical NestJS backend structure. It defines module ownership, dependency direction, layering, transaction boundaries, integration ports, error/validation behavior, background work, and the project structure expected by later Section 05 documents.

## 2. Backend Architectural Goals

- Keep one deployable NestJS + TypeScript application for MVP.
- Give every business capability a clear owner.
- Keep domain rules out of controllers, clients, providers, and cache.
- Use PostgreSQL/Prisma for authoritative state and transactions.
- Support Arabic/English localization consistently across API, content, and messages.
- Make external integrations replaceable and failures observable.
- Keep modules testable without requiring the entire application.

## 3. Backend Technology Stack

| Concern | Decision |
|---|---|
| Runtime/framework | NestJS + TypeScript |
| API | Versioned RESTful HTTP |
| Persistence | PostgreSQL through Prisma |
| Cache/jobs | Redis selectively; simple application job mechanism |
| Media | AWS S3 through a storage port |
| Validation | Backend DTO/schema validation plus domain rules |
| Authentication | Backend-owned revocable session/token mechanism; exact choice remains in 5.5 |
| External services | Ports and adapters |

No technology in this table makes Redis, S3, a payment provider, shipping provider, notification provider, or search provider a business authority.

## 4. NestJS Modular Monolith

The backend is one application with modules that expose public application contracts and keep private implementation details internal. A module may contain controllers, use cases, domain objects, repositories, and adapters as appropriate. The boundary is ownership, not folder count.

Rules:

- A module owns writes to its business state.
- Other modules request changes through public use cases/ports.
- Read projections may be consumed through explicit read contracts.
- Domain events communicate non-blocking consequences.
- Shared libraries contain primitives and infrastructure utilities, not unowned business logic.
- No module imports another module's Prisma model/repository directly.

## 7. Module Dependency Rules

Allowed:

- Domain code depends on shared domain primitives.
- Application code depends on domain code and owned ports.
- Infrastructure implements ports.
- Orchestration use cases call public contracts of other modules.
- Events notify modules of committed changes.

Forbidden:

- Direct cross-module writes to another module's tables.
- Controllers invoking provider SDKs or Prisma directly.
- Domain entities importing NestJS, Redis, S3, or HTTP.
- Analytics or notifications blocking a core commerce transaction.
- Search becoming the source of truth for catalog eligibility.
- Clients deciding authorization, price, inventory, or payment state.

## 8. Backend Layering

### Domain layer

Aggregates, value objects, policies, statuses, invariants, and domain events. Examples include artwork publication eligibility, unique inventory rules, offer state transitions, and order price snapshots.

### Application layer

Use cases coordinate authorization context, repositories, transactions, ports, and events. Examples include publish artwork, accept offer, create order, record COD state, and publish translation resource.

### Presentation/API layer

Controllers, DTOs, guards, locale resolution, pagination, response mapping, and API documentation. It translates transport concerns into application commands/queries.

### Persistence/infrastructure layer

Prisma repositories, migrations, Redis/S3 adapters, provider adapters, jobs, and observability integrations.

## 9. Domain Layer

Domain rules remain independent of transport and provider details:

- User capabilities and artist verification requirements.
- Artwork publication and visibility.
- Physical/digital product behavior.
- Unique and quantity inventory.
- Offers, finite rounds, private minimum protection, and negotiated price distinction.
- Order, payment, shipping, and review lifecycle invariants.
- Locale-independent domain codes and structured translation keys.

Rendered text is not a domain invariant. Domain events carry stable event names and parameters; localization resolves wording at the boundary.

## 10. Application Layer

Use cases should:

1. Authenticate/authorize the actor context.
2. Load authoritative aggregates through module-owned repositories.
3. Validate the requested operation and current state.
4. Open a PostgreSQL transaction when multiple authoritative writes must remain consistent.
5. Persist changes and immutable snapshots.
6. Publish committed events or enqueue retryable side effects.
7. Return an application result mapped by the API layer.

Cross-module orchestration belongs in application services, not in controllers or repositories.

## 11. Presentation/API Layer

Controllers expose versioned REST resources and delegate immediately to use cases. API behavior must include:

- request DTO validation and normalization;
- authentication and capability guards;
- ownership and lifecycle checks through application policies;
- consistent machine-readable error codes;
- locale resolution and localized messages;
- cursor/page pagination, filtering, and sorting;
- idempotency for duplicate-sensitive mutations;
- no exposure of private prices, secrets, or internal persistence structure.

Stable status/error codes remain language-neutral. Localized text is selected using the resolved locale and fallback policy.

## 12. Persistence Layer

Prisma repositories are owned by the module whose state they write. PostgreSQL provides:

- foreign keys and constraints;
- transaction isolation and row/concurrency controls;
- immutable business snapshots;
- locale/content uniqueness and lifecycle constraints;
- UTC timestamps and precise monetary values.

JSONB is reserved for bounded metadata, provider payloads, parameter schemas, and flexible non-core data. Media binaries remain in S3.

## 13. Transaction Boundaries

Use one PostgreSQL transaction for:

- checkout/order creation, totals, item snapshots, and inventory reservation;
- unique inventory sale or quantity decrement;
- offer acceptance and negotiated purchase creation;
- payment-state recording and linked order transition;
- order-state transitions that must not interleave incorrectly.

Do not include external network calls in a long database transaction when an explicit pending/reconciliation state can be persisted instead.

## 14. Inventory Concurrency

Inventory is authoritative in PostgreSQL. Reservation/decrement operations must atomically verify status and available quantity, protect unique items from double sale, and record expiry/release where applicable. Redis may accelerate availability reads but cannot confirm a sale.

## 15. Pricing Architecture

The backend calculates authoritative prices and totals using precise monetary representations. Product base price, offer/agreed price, order-item unit price, shipping cost, discount, currency, and order total remain distinct concepts.

Negotiated prices are scoped to the accepted offer/order snapshot and never overwrite the displayed catalog price. Clients submit intent, not trusted totals.

## 16. Authentication & Authorization Integration

Identity provides authentication context. Authorization combines identity, capability, artist verification, resource ownership, lifecycle state, and admin permission. Modules ask the authorization boundary for decisions or apply policies using explicit actor/resource data.

The same User may act as customer and artist. Being an artist or owning a resource does not bypass verification, visibility, moderation, or order rules. Private artist minimum prices and protected customer data are never returned through unauthorized read models.

## 17. Error Handling

Errors are categorized as validation, authentication, authorization, not-found, conflict/state, integration, and internal failures. APIs return stable error codes with safe details and localized messages/translation keys where appropriate.

Provider errors are normalized by adapters. Internal errors are logged with correlation IDs but do not expose SQL, credentials, stack traces, or sensitive payloads to clients.

## 18. Validation

Validation occurs at multiple boundaries:

- API DTO/schema validation for shape, size, required values, and supported locale.
- Application validation for authorization, ownership, workflow, and cross-entity rules.
- Domain validation for invariants and state transitions.
- PostgreSQL constraints for final integrity.

Validation messages use stable translation keys and structured parameters. Missing translations fall back to English and emit telemetry.

## 19. Configuration Management

Configuration is environment-specific and validated at startup. Secrets and provider credentials come from deployment secret storage. Configuration includes database, Redis, S3, authentication, supported locales, job behavior, and external integration settings.

Business state and translation resources are not hidden in environment variables. Runtime-editable translations/templates belong in PostgreSQL with version/publication rules.

## 20. Background Jobs / Asynchronous Work

Use simple jobs for:

- email/push delivery and retries;
- search indexing;
- analytics aggregation;
- media processing;
- cache invalidation;
- integration reconciliation.

Jobs must be idempotent, observable, retryable, and safe after process restart. Kafka/RabbitMQ are not MVP dependencies.

## 21. External Integration Architecture

### Payments

`PaymentPort` isolates COD now and future online providers later. Orders depend on FANNAN payment states, not provider statuses.

### Shipping

`ShippingPort` isolates shipment creation, label/tracking references, and provider updates. Provider changes do not alter order ownership.

### Storage

`ObjectStoragePort` isolates S3 operations. The Media module authorizes access and stores metadata; it does not expose arbitrary bucket operations.

### Notifications

Email and push ports receive stable message/template keys and structured parameters. Notification/localization modules select locale and active template version.

## 22. Caching Integration

Cache only published, read-heavy, or short-lived data. Keys must include tenant/user context where applicable, locale, and resource/index/template version. Invalidation follows committed events.

Never use cache to decide inventory, order validity, payment success, negotiation acceptance, agreed price, shipping state, or authorization.

## 23. Search Integration

Catalog, category, tag, and artist changes emit events consumed by Search. The read model contains locale/script metadata and normalized Arabic/English searchable fields, and indexes only public eligible content.

Search results are revalidated against visibility/authorization requirements. Search may be eventually consistent; the API remains authoritative when a listing is no longer eligible.

## 24. Notifications Integration

Domain events trigger notification use cases. The recipient locale is resolved at creation/send time. The notification records locale, fallback locale when used, template key/version, delivery status, and rendered content when historical display requires it.

Notification failure is retried and observed without rolling back the source business transaction.

## 25. Observability Hooks

Each request/job carries a correlation ID. Log module, operation, actor-safe ID, resource-safe ID, outcome, latency, and error category. Emit metrics for transaction failures, inventory conflicts, job retries, provider failures, cache behavior, search freshness, and localization fallback/missing keys.

Business audit records remain distinct from technical logs and are retained according to Section 04.

## 26. Security Boundaries

- Controllers and guards authenticate and authorize.
- Application services enforce ownership and capability rules.
- Repositories use parameterized Prisma access.
- Media access is authorized before S3 retrieval.
- Secrets never enter logs or source control.
- Rate limits protect authentication, offers, search, checkout, and notification-triggering actions.
- Admin actions and sensitive state changes are auditable.

## 27. Testing Architecture

Tests should align with module ownership:

- domain tests for invariants and state transitions;
- application tests for use cases and authorization;
- repository/integration tests for PostgreSQL constraints and transactions;
- adapter contract tests for external integrations;
- API tests for validation, errors, locale, and authorization;
- job tests for retry/idempotency;
- end-to-end tests for discovery, purchase, offers, COD, shipping, notifications, and Arabic/English flows.

## 29. Example Business Flow

For checkout:

1. Controller validates request and resolves actor/locale.
2. Checkout use case loads cart and catalog data through public contracts.
3. Inventory use case atomically reserves eligible stock.
4. Order use case creates immutable item/price snapshots in one transaction.
5. Payment module records COD state through its internal abstraction.
6. Transaction commits.
7. Events enqueue shipment preparation, localized notifications, analytics, and cache invalidation.
8. API returns the order resource with stable status codes and localized display fields.

## 30. MVP vs Future Backend Evolution

| Area | MVP | Future |
|---|---|---|
| Modules | One NestJS deployable application | Extract only proven bounded capabilities |
| Persistence | Prisma/PostgreSQL authority | Replicas/partitioning if measured |
| Jobs | Simple Redis/application jobs | Dedicated workflow/broker |
| Search | Locale-aware read model | Specialized search provider |
| Payments | COD adapter | Additional provider adapters |
| Shipping | One replaceable integration boundary | Multiple providers |
| Notifications | Localized channel adapters | Routing/campaign platform |
| Media | S3 references and basic processing | Dedicated pipeline/CDN |

## 31. Backend Architectural Rules

1. No controller owns business rules.
2. No client or Redis value is trusted for business authority.
3. No module writes another module's state directly.
4. No provider SDK leaks into domain entities.
5. All commerce mutations are revalidated server-side.
6. Arabic/English and RTL/LTR remain first-class.
7. UI translations and user-generated marketplace content remain separate.
8. Side effects are retryable and idempotent.
9. Core transactions do not depend on notification, search, analytics, or cache success.
10. New infrastructure requires explicit architectural justification.

## 33. Final Backend Architecture Summary

The FANNAN backend is one NestJS modular monolith. Modules own business capabilities and communicate through application contracts and committed events. PostgreSQL/Prisma own persistent state and transactions; Redis is non-authoritative; S3 stores media; providers are replaceable adapters. The backend enforces authorization, pricing, inventory, orders, offers, payment, shipping, and localization policy, while asynchronous jobs handle delivery, search, analytics, media processing, and cache invalidation.
