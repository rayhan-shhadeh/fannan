# 5.3 Frontend Architecture

**Status:** MVP web-client architecture  
**Depends on:** 5.0 Architecture Decisions, 5.1 Architecture Overview, 5.2 Backend Architecture

## 1. Purpose

FANNAN Web is a responsive Next.js, React, and TypeScript client for public discovery, customer commerce, artist workflows, and protected administration. This document owns web structure, routing, rendering, API consumption, state ownership, localization, accessibility, SEO, and web-specific performance. It does not redefine backend business rules or detailed API contracts.

## 2. Architectural Goals

- Ship one understandable web application; do not introduce micro-frontends.
- Consume the shared REST API; never access PostgreSQL, Prisma, Redis, or providers directly.
- Keep server state separate from transient UI and form state.
- Support Arabic (`ar`, RTL) and English (`en`, LTR) from day one.
- Make public discovery fast and indexable while protecting private data.
- Make loading, empty, validation, authorization, conflict, and failure states explicit.
- Prefer a small dependency footprint and measured optimization.

## 3. Technology Stack

| Concern | Decision |
|---|---|
| Framework | Next.js + React + TypeScript |
| Routing | Next.js App Router |
| API | Shared versioned FANNAN REST API |
| Rendering | Server-oriented public pages; client components for interaction |
| State | API/server state plus local React state; no mandatory global store |
| Styling | Existing brand tokens and responsive design system; exact UI library remains open |
| Localization | Stable translation keys, locale-aware formatting, RTL/LTR |

No particular state, form, or data-fetching library is selected by this architecture. Add one only when a measured MVP need justifies it.

## 4. Frontend Model

```text
Route/page -> feature UI -> typed API client -> REST API -> NestJS modules
```

Presentation renders data and interaction states. Feature code orchestrates user actions. The API boundary owns transport, authentication context, locale headers, pagination, error normalization, and response typing. The backend remains authoritative for price, inventory, orders, offers, payment, shipping, verification, and authorization.

## 5. Project Structure

```text
src/
  app/
    (public)/ (auth)/ (customer)/ (artist)/ admin/
    layout.tsx loading.tsx error.tsx
  components/ui/ components/layout/ components/feedback/
  features/catalog/ features/search/ features/cart/ features/checkout/
  features/orders/ features/offers/ features/artist/ features/admin/
  lib/api/ lib/auth/ lib/i18n/ lib/formatting/ lib/routing/
  hooks/ types/ config/ styles/
```

Routes compose pages and boundaries. Components are reusable and presentational. Features own web interactions and API queries. `lib/api` is the only data-access boundary; feature code must not call persistence or provider SDKs.

## 6. Routing and Protection

Public routes include discovery, categories, search, artwork details, and artist profiles. Authenticated customer routes include account, favorites, cart, checkout, orders, offers, and notifications. Artist routes include dashboard, products, profile, orders, offers, and notifications. Admin routes are separately protected.

Route redirects and hidden buttons are UX only. The backend enforces authentication, capability, artist verification, ownership, and resource lifecycle. Draft, suspended, rejected, private, and deleted content must not become public through a URL.

## 7. Rendering Strategy

- Server-render public home, catalog, category, artwork, and artist content where SEO and initial load matter.
- Use dynamic server rendering where authorization, inventory, locale, or request context affects output.
- Use client components for cart changes, checkout, offers, account edits, filters, dashboards, and notifications.
- Revalidate stable public content only with explicit invalidation and locale-aware cache identity.

Rendering must use the API authorization boundary. Hydration must preserve resolved locale and direction.

## 8. API Integration

The typed client handles base URL/version, credentials, locale preference, cancellation, safe retries, pagination, mutation idempotency metadata, response parsing, and machine-readable errors. Server components may use server-safe wrappers; client components use client-safe wrappers. After mutations, refresh/revalidate affected server state. Never invent client-only APIs in this phase.

## 9. State Ownership

### Server state

Products, taxonomy, artists, availability, cart, orders, offers, notifications, user data, and search results come from the API. Cache identity must include locale and, where relevant, user and permission context.

### Client state

Menus, dialogs, tabs, temporary filters, form drafts, focus, and presentation preferences may use React state. Optimistic display is allowed only for reversible presentation and must reconcile with the server. Do not create a global store for all API data without a measured need.

## 10. Business Logic Boundary

The web may validate input shape and calculate display hints, but it must not authoritatively decide price, totals, availability, reservations, order/payment/shipping transitions, offer acceptance, private minimum prices, verification, ownership, or review eligibility. Every mutation is recalculated and authorized by the backend.

## 11. Authentication and Authorization

Use the mechanism selected by 5.5. Keep credentials out of arbitrary browser storage, URLs, logs, page metadata, and analytics. Handle expiry, revoked sessions, logout, and reauthentication explicitly. Customer and Artist are capabilities of one User account; verified selling status controls artist actions. Admin access is explicit.

## 12. Marketplace UI

Reusable product components represent physical/digital type, unique/quantity inventory, localized content, media, artist identity, price, availability, favorites, and supported actions. Physical products expose shipping requirements; digital products expose fulfillment only after backend authorization. Unique-item conflicts and quantity reservation failures are recoverable checkout states.

Offers are structured forms and timelines, not chat. The UI supports finite rounds, counter-offers, expiry, acceptance, rejection, and resulting purchase opportunity. It must never request or expose an artist's private minimum.

## 13. Checkout

Checkout stages address, eligible cart items, shipping information, review, and COD confirmation as applicable. The backend owns eligibility, totals, inventory reservation, order creation, and payment state. Handle expired carts, changed prices, unavailable inventory, validation, duplicate submission, and network interruption using server responses and idempotency semantics.

## 14. Internationalization

- All UI, validation, error, notification, and empty-state text uses stable translation keys.
- Resolve locale using request preference, authenticated user preference, browser/device locale, then English fallback.
- Support `ar`/RTL and `en`/LTR, including navigation, forms, dialogs, typography, icons, and responsive layouts.
- Format dates, numbers, quantities, and currency with locale-aware helpers.
- Missing translations fall back to English and remain observable.
- Artwork, profile, category, and tag translations are marketplace content, not UI resources.
- Locale, resource version, and user context vary page/cache/ETag identity where needed.

## 15. Responsive Design and Accessibility

Use existing brand tokens and mobile-first responsive compositions without duplicating business components by breakpoint. Support keyboard navigation, visible focus, semantic headings/landmarks, labels, status announcements, accessible dialogs/menus, contrast, non-color status, media alternatives, and correct RTL/LTR direction.

## 16. Error, Loading, and Empty States

Every data feature defines loading, empty, unavailable, validation, authorization, conflict, network, and server-error states. Messages use translation keys and safe parameters. Do not show success before backend confirmation, and preserve safe input for recovery where practical.

## 17. Notifications, Search, and Media

In-app notifications are rendered from API resources and historical locale/rendered snapshots; the web does not invent wording. Search supports Arabic/English input, filters, sorting, pagination, and no-results states while normalization/ranking remains backend-owned. Media uses authorized backend/S3 flows, responsive images, placeholders, alt text, and protected digital downloads; browser bundles never contain storage credentials.

## 18. Performance and SEO

Use server rendering for public discovery, pagination, optimized media, route-level code splitting, and measured API caching. Do not share private data through public cache keys. Localized public metadata, canonical URLs, locale alternates, and structured data should be supplied where supported. Restricted content must not be indexed.

## 19. Security and Testing

Protect mutations according to the authentication mechanism, escape displayed content, avoid unsafe HTML, and treat route hiding as non-security. Test components and feature flows in both locales, including RTL, accessibility, cart/checkout/offers/authentication, API error contracts, responsive layouts, public SEO pages, and protected routes.

## 20. Responsibility Matrix

| Concern | Web | Backend |
|---|---|---|
| Layout, interaction, display states | Owns | Provides data |
| Price, inventory, orders, payment, shipping | Displays | Authoritative |
| Offers and authorization | UX gating | Validates/transitions |
| Localization | Renders keys, direction, formatting | Resolves policy/resources/messages |
| Media | Renders authorized references | Authorizes storage |

## 21. MVP vs Future Evolution

| Area | MVP | Future |
|---|---|---|
| Structure | One Next.js app | Split only for proven scale/ownership |
| State | API state plus local React state | Shared cache/store if measured |
| Offline | Graceful failure and safe drafts | Explicit offline workflows |
| Notifications | In-app/API-driven | Rich web push/campaigns |
| Performance | SSR, pagination, media optimization | Advanced edge/CDN strategy |
| Shared code | Contracts/utilities where useful | Broader shared packages |

## 22. Dependencies and Final Summary

5.1 owns system boundaries; 5.2 owns backend modules/execution; 5.5 authentication; 5.6 media; 5.7 localization; 5.8 search; 5.9 notifications; 5.12 caching; 5.13 security; and 5.14 observability. Section 06 owns detailed API contracts.

FANNAN Web is one responsive, localized Next.js client over the shared REST API. It separates server state from UI state, supports customer and artist capabilities, protects private content, and never becomes authoritative for marketplace rules.
