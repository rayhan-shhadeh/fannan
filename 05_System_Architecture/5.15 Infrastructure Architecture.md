# 5.15 Infrastructure Architecture

## 1. Purpose

This document defines the runtime infrastructure required to operate FANNAN.
It connects the web and mobile clients, Laravel modular monolith, PostgreSQL,
Redis, S3-compatible media storage, background processing, and approved
external providers to practical environments, deployment, security, backup,
recovery, and scaling responsibilities.

FANNAN remains a modular monolith for MVP. Infrastructure must be simple,
reliable, affordable, maintainable, and capable of evolving when measured
traffic, availability, or operational requirements justify additional
components.

## 2. Scope

This architecture covers:

- Development, staging, and production environments.
- Public web hosting, mobile distribution, Laravel API hosting, workers, and
  scheduled jobs.
- PostgreSQL, Redis, S3-compatible storage, queues, DNS, HTTPS/TLS, and
  network boundaries.
- Configuration, secrets, source control, conceptual CI/CD, migrations,
  releases, rollback, health checks, backups, disaster recovery, and scaling.
- Connectivity to payment, shipping, notification, search, analytics, and
  other approved external providers.
- Integration with [5.13 Security Architecture](5.13%20Security%20Architecture.md)
  and [5.14 Observability & Logging](5.14%20Observability%20%26%20Logging.md).

This document does not redesign the database schema, create microservices,
define provider contracts, or create CI/CD configuration files.

## 3. Infrastructure Principles

1. **Modular monolith first:** One backend application and clear internal
   modules are the MVP deployment boundary. Microservices are not required.
2. **PostgreSQL is authoritative:** Durable users, roles, catalogue,
   commerce, payment, shipping, and audit state belongs in the database and
   domain services, not Redis or client storage.
3. **Stateless application tier:** Web/API instances should be replaceable.
   Sessions, jobs, files, and durable state use approved shared services.
4. **Environment isolation:** Development, staging, and production have
   separate data, credentials, storage, cache, provider configuration, and
   operational access.
5. **Private by default:** Databases, Redis, queues, original media, and
   administrative interfaces are not publicly reachable.
6. **Least privilege:** Services, deployment identities, operators, and
   providers receive only the access required for their responsibilities.
7. **Secure transport:** Public and service-to-service traffic uses HTTPS/TLS
   or an equivalent encrypted channel with certificate validation.
8. **Reproducible releases:** A release is built once, tested, identified,
   and promoted through controlled environments.
9. **Backward-compatible change:** Schema, cache, queue, and provider changes
   must support safe deployment and rollback where practical.
10. **Recoverable operations:** Backups, restore tests, reconciliation, and
    documented incident procedures are part of infrastructure, not optional
    afterthoughts.
11. **Observable by design:** Every runtime component exposes safe health,
    metrics, logs, and error signals consistent with 5.14.
12. **Cost-conscious growth:** Add managed, distributed, or redundant
    infrastructure only when measured needs and risk justify its cost.

## 4. Runtime Architecture

The MVP runtime is conceptually:

```text
                         Customers, Artists, Staff
                                  │
                    ┌─────────────┴─────────────┐
                    │                           │
             Responsive Web                 Flutter Mobile
                    │                           │
                    └─────────────┬─────────────┘
                                  │ HTTPS
                    ┌─────────────▼─────────────┐
                    │ Laravel REST API           │
                    │ Modular monolith            │
                    │ Auth, catalogue, commerce, │
                    │ admin, provider adapters   │
                    └─────┬──────────┬──────────┘
                          │          │
                 ┌────────▼───┐  ┌──▼─────────┐
                 │ PostgreSQL │  │ Redis      │
                 │ source of  │  │ cache,     │
                 │ truth      │  │ ephemeral  │
                 └────────┬───┘  │ state/jobs │
                          │      └────┬────────┘
                          │           │
                    ┌─────▼───────────▼─────┐
                    │ Workers and scheduler  │
                    └─────┬───────────┬─────┘
                          │           │
                    ┌─────▼───┐  ┌──▼────────────┐
                    │ S3      │  │ External       │

                    └─────────┘  │ payment,      │
                                 │ shipping,     │
                                 │ notifications │
                                 └───────────────┘
```

The web application may be hosted separately from the API for frontend
delivery and deployment independence, but it does not become a second
business authority. Mobile applications communicate through the documented
API. The API, workers, and scheduler share domain code and contracts while
remaining separately deployable processes only where operationally useful.

Search may use the approved search architecture and provider/service, but
search indexes are derived data. Media binaries reside in S3-compatible
storage; metadata and ownership remain authoritative in PostgreSQL.

## 5. Environment Architecture

FANNAN uses a controlled progression:

```text
Development -> Staging -> Production
```

Each environment has separate:

- Application configuration and deployment identity.
- PostgreSQL database and credentials.
- Redis instance/database and credentials.
- S3 bucket or account/prefix with independent access policy.
- Queue, worker, scheduler, domains, callback endpoints, and logs.
- External provider project/account, credentials, webhook secrets, and test
  or live mode.
- Monitoring destinations, alert recipients, and synthetic test identities.

Data must not flow backward casually. Production data is not copied to
development or staging. If a production-derived dataset is needed for
diagnosis, it must be approved, minimized, irreversibly redacted or
syntheticized, encrypted, time-limited, and audited.

Deployments promote an identified artifact and environment configuration; they
do not rebuild differently in each environment.

## 6. Development Environment

Development is optimized for safe local iteration:

- Developers may run the web client, Laravel API, worker, scheduler,
  PostgreSQL, Redis, and local/object-compatible media services locally or
  through isolated development resources.
- Data is synthetic, disposable, and representative without containing real
  customer, artist verification, payment, shipping, or support data.
- Local credentials are development-only and distributed through approved
  local configuration, never committed.
- Provider integrations use sandbox/test accounts or local adapters. Live
  payment, shipping, notification, and webhook credentials are prohibited.
- Developers may use seeded users for each documented role, but role behavior
  remains server-enforced and test data cannot grant production access.
- Local services should approximate production contracts without requiring
  enterprise infrastructure.
- Development logs may be more verbose, but the 5.13 prohibition on secrets,
  payment credentials, and unnecessary personal data still applies.

## 7. Staging Environment

Staging is a production-like release validation environment:

- It uses isolated database, Redis, S3, provider projects, domains, queues,
  credentials, and observability destinations.
- It validates migrations, API contracts, web/mobile integration, workers,
  media processing, callbacks, notifications, health checks, backups, and
  rollback procedures before production.
- Provider sandboxes are used wherever available. If a provider has no safe
  sandbox, use a controlled test account and explicit approval.
- Staging data is synthetic or redacted and has bounded retention.
- Access is restricted to authorized engineering, QA, product, security, and
  operations users through the authentication and staff controls in 5.5.
- Staging alerts reach a test or engineering channel, never customers.
- Staging should be similar enough to expose runtime risks without requiring
  production scale or cost.

## 8. Production Environment

Production serves real users, artwork, orders, payments, addresses, shipping,
notifications, and staff operations.

- Public traffic enters through approved DNS and HTTPS/TLS endpoints and is
  routed to the web/API entry point.
- PostgreSQL, Redis, queues, workers, S3 management, and admin access remain
  private or tightly restricted.
- Production credentials are individually owned or service-scoped, rotated,
  audited, and never reused in lower environments.
- Live payment/shipping/notification provider modes are isolated from
  sandbox modes and have explicit callback and reconciliation controls.
- Debug mode, development credentials, permissive test routes, public
  database/Redis ports, and unrestricted storage buckets are prohibited.
- Production releases require reviewed changes, passing tests and checks,
  migration readiness, observability, backup evidence, and an owner.
- Production access is least-privileged and time-bounded where practical.
  Emergency access is recorded and reviewed after use.
- Production capacity, availability, error, security, backup, and provider
  signals are monitored according to 5.14.

## 9. Web Infrastructure

The public website and dashboards may be served from a managed web host,
application host, or equivalent platform selected for reliability and cost.
The hosting choice must support:

- HTTPS, custom domains, secure headers, compression, asset caching, and
  predictable deployment.
- Environment-specific builds and runtime configuration without embedding
  secrets in client bundles.
- Route handling for public pages, dashboards, authentication transitions, and
  API failures without exposing internal diagnostics.
- Safe public caching only for content approved by [5.12 Caching &
  Performance](5.12%20Caching%20%26%20Performance.md). Private account,
  order, payment, support, and admin responses must not enter shared caches.
- Web telemetry and error reporting that obey 5.14 and does not collect
  secrets, private content, or unauthorized user profiles.

The frontend is not a security boundary. Protected operations always return to
the Laravel API for authentication, authorization, validation, and state.

## 10. Backend Infrastructure

The Laravel REST API is the MVP application runtime. It runs on one or more
managed application instances or containers behind a controlled HTTPS entry
point.

- API processes are stateless with respect to durable business state.
- Worker processes execute queued media, notification, search, analytics,
  provider, and reconciliation work using scoped service credentials.
- A scheduler runs periodic tasks with singleton/overlap protection where
  required. Scheduler failures are observable and do not silently skip
  payment, shipment, retention, or notification responsibilities.
- API, worker, and scheduler releases use the same identified application
  artifact and compatible configuration.
- Long-running or CPU/memory-intensive work is not performed synchronously in
  customer requests when a documented queue flow exists.
- Separate worker capacity may be introduced if queues threaten API latency;
  this is an operational split, not a microservice boundary.
- Resource limits prevent one upload, search, export, or provider integration
  from exhausting the entire runtime.

## 11. PostgreSQL Infrastructure

PostgreSQL is the source of truth for durable FANNAN state. Production should
use a managed PostgreSQL service or a comparably operated private instance
with:

- Encrypted storage, private connectivity, controlled firewall/security-group
  access, automated backups, and monitored availability.
- Separate application, worker, migration, reporting, and administrative
  roles. The application is not a database superuser.
- TLS connection validation and environment-specific credentials.
- Connection pooling or bounded connection management appropriate to the
  runtime size.
- Monitoring for connections, locks, deadlocks, slow operations, storage,
  backups, replication where used, and constraint/migration failures.
- Maintenance, patching, vacuum/analyze, extension, and version ownership
  assigned to operations or the managed provider.

The infrastructure layer does not change schema design. Database constraints
and ownership rules remain governed by [4.5 Database Constraints](4.5%20Database%20Constraints.md)
and domain architecture.

## 12. Redis Infrastructure

Redis is an internal support service for caching, rate limiting, ephemeral
state, locks, queues, and other uses explicitly defined by the architecture.
It is never the source of truth for users, orders, payment, shipping, or
ownership.

- Development, staging, and production use separate instances or isolated
  resources and credentials.
- Production Redis is private, authenticated, encrypted in transit where
  supported, and protected by network rules.
- Persistence is not assumed for correctness. If Redis persistence is
  enabled, it supports operational recovery and does not replace PostgreSQL
  backups.
- Cache loss, eviction, restart, or temporary unavailability must fail to a
  safe cache miss or queued retry and recover from authoritative services.
- Critical operations use explicit idempotency and locking behavior; Redis
  locks cannot be treated as permanent ownership.
- Key namespaces, TTLs, memory limits, eviction policy, queue behavior, and
  invalidation follow 5.12 and 5.13.
- Redis credentials are not exposed to web/mobile clients or written to logs.

## 13. S3 Infrastructure

S3-compatible object storage holds binary media and derived assets. PostgreSQL
stores the authoritative metadata, ownership, lifecycle, moderation, and
visibility state.

- Use separate development, staging, and production buckets or storage
  accounts. Do not mix live originals with test assets.
- Buckets are private by default. Public delivery is limited to approved,
  eligible derivatives or through a controlled media delivery path.
- Originals, drafts, rejected files, verification documents, and private
  assets require authorization and short-lived signed access where applicable.
- S3 access is performed by scoped service identities; no access key or secret
  is shipped to web or mobile clients.
- Object keys are generated by the server and do not directly contain
  uncontrolled user input. Object overwrite, traversal, and cross-tenant
  access are prevented.
- Upload quarantine, scanning, transformation, moderation, derivative
  creation, and cache invalidation follow 5.6 and 5.13.
- Lifecycle rules expire temporary uploads, failed processing artifacts, and
  obsolete derivatives according to 4.7 and approved media policy.
- Storage versioning or recovery features may be enabled where cost and
  deletion requirements justify them; they do not replace database/media
  lifecycle controls.
- Back up irreplaceable originals and required metadata according to business
  policy. Public derivatives can generally be regenerated; originals may not
  be.

## 14. Networking & Connectivity

The network is segmented conceptually into public ingress, application
runtime, data services, storage/provider egress, and operator access:

```text
Internet
   │ HTTPS
Public edge / web entry
   │
Web and API runtime
   ├── private PostgreSQL
   ├── private Redis/queue
   ├── private S3 API
   └── restricted outbound provider connections
```

- Only required web/API ports are public. PostgreSQL, Redis, worker control
  planes, and storage administration are not internet-facing.
- Egress is restricted to approved providers, package/build services, time
  synchronization, monitoring, and necessary operational endpoints.
- Administrative access uses a controlled, individually authenticated path
  rather than exposed database or server ports.
- Security groups/firewalls, service identities, and network policies are
  documented and reviewed with each new dependency.
- Network failures produce bounded retries, circuit breaking, and observable
  pending states rather than unbounded request or job growth.
- Internal DNS/service discovery names are environment-specific and are not
  exposed in public responses.

## 15. DNS & TLS

- Each environment has distinct domains or subdomains and callback endpoints.
- DNS records are managed through an approved registrar/provider with
  restricted change access, audit, and recovery contacts.
- Production customer, artist, staff, API, media, and webhook endpoints use
  valid certificates, automatic renewal monitoring, and modern TLS settings.
- HTTP is redirected to HTTPS or disabled. Sensitive traffic is never sent
  over plaintext.
- Provider webhooks use HTTPS and certificate validation. Callback URLs are
  environment-specific so sandbox events cannot reach production.
- HSTS, secure cookies where applicable, security headers, and correct
  origin/CORS policy follow frontend, backend, and security architecture.
- Certificate expiry, DNS changes, TLS failures, and misrouted environment
  traffic are monitored through 5.14.

## 16. Configuration & Secrets

Configuration is separated into non-secret settings and secrets:

- Non-secret settings include environment name, service URLs, feature
  boundaries, timeouts, queue names, cache TTL policy, locale defaults, and
  safe operational thresholds.
- Secrets include database credentials, Redis credentials, storage keys,
  provider keys, webhook signing secrets, encryption keys, deployment
  credentials, and authentication secrets.
- Secrets are injected at runtime through an approved secret manager or
  protected environment facility. They are not committed, baked into public
  assets, placed in mobile bundles, or copied between environments.
- Each environment and service uses distinct secret values and least-
  privileged scopes. Rotation and revocation procedures are documented.
- Configuration changes are reviewed, auditable, validated at startup, and
  fail clearly when required values are absent. The application must not
  silently substitute production or development defaults.
- Logs, health responses, crash reports, and client responses redact secrets.

## 17. CI/CD Architecture

CI/CD is a conceptual controlled path, not a set of configuration files:

```text
Source Control
      ↓
Build
      ↓
Test and quality/security checks
      ↓
Package an identified artifact
      ↓
Deploy to development/staging
      ↓
Health and smoke checks
      ↓
Approval and deploy to production
      ↓
Post-deploy verification
```

The pipeline must:

- Use protected source branches and reviewed changes for application,
  dependencies, migrations, infrastructure, permissions, and secrets wiring.
- Run the repository's existing tests and applicable quality/security checks.
- Build web, API, worker, scheduler, and mobile release artifacts according to
  their architecture without embedding secrets.
- Produce a version/commit identifier used by logs, errors, metrics, and
  release records.
- Scan dependencies and artifacts according to 5.13, and block unresolved
  critical findings where release policy requires.
- Promote the same tested artifact while applying environment-specific
  configuration.
- Require explicit production approval and record who/what/when was released.
- Support rollback, migration safety, health checks, and post-release
  observation.

No new GitHub Actions, pipeline, infrastructure-as-code, or provider
configuration is introduced by this architecture document.

## 18. Deployment Strategy

MVP deployment may use a short maintenance-aware release or rolling deployment
depending on the selected hosting provider. In both cases:

1. Confirm source revision, artifact, configuration, dependencies, backup
   status, migration plan, and communication owner.
2. Deploy compatible application code and supporting worker/scheduler code.
3. Apply backward-compatible database migrations.
4. Restart or replace processes in a controlled order.
5. Run liveness, readiness, smoke, authentication, media, queue, and
   business-critical checks.
6. Observe errors, latency, queues, provider callbacks, and business metrics.
7. Mark the release active only after authoritative verification.

Release order must not create a period where new code requires absent schema,
workers process incompatible payloads, callbacks route to the wrong
environment, or old clients receive unsafe responses. Feature flags or
dark-launch behavior may limit exposure when a change is high risk.

## 19. Database Migration Strategy

- Every schema change is versioned, reviewed, tested against a representative
  dataset, and associated with a release.
- Prefer additive, backward-compatible migrations: add nullable/unused
  structures, deploy compatible code, backfill safely, switch reads/writes,
  then remove obsolete structures in a later release.
- Destructive changes, large backfills, uniqueness changes, ownership changes,
  and payment/order changes require explicit risk, lock, duration, backup, and
  rollback analysis.
- Migrations run with a dedicated least-privileged migration identity, not
  ordinary request credentials.
- Production migration execution is serialized and observable. A failed
  migration stops the release and enters recovery; it is not silently
  skipped.
- Data migrations preserve audit, retention, ownership, and reconciliation
  requirements. They never fabricate payment, shipping, or order success.
- Staging validates migration runtime, lock impact, rollback/recovery path,
  worker compatibility, and old-client behavior before production.

## 20. Rollback Strategy

Application rollback restores the last known-good artifact and configuration
when health, errors, security, or business outcomes regress.

- Keep the previous application artifact available for the approved rollback
  window.
- Prefer roll-forward for database changes that are additive or have already
  changed durable state. Do not blindly reverse migrations containing user,
  order, payment, shipping, or media data.
- Use feature flags, provider disablement, queue pause, traffic reduction, or
  maintenance mode to contain partial failures.
- Reconcile payment, shipping, notification, and media provider state after
  rollback; external side effects may have succeeded even when the release
  failed.
- Invalidate incompatible caches and preserve queue/idempotency state as
  required by 5.12.
- Verify health and authoritative business state after rollback. Record the
  release, impact, decision, and follow-up fix in observability/audit systems.

## 21. Health Checks

Infrastructure supports the health model in 5.14:

- **Liveness:** Process/runtime is alive and can answer a basic check. It does
  not require every provider or a deep database query.
- **Readiness:** Instance has required configuration and essential
  dependencies and can safely receive assigned traffic.
- **Dependency checks:** PostgreSQL, Redis, queue, S3, search, and providers
  are checked separately with bounded timeouts.
- **Business smoke checks:** Safe synthetic flows validate authentication,
  catalogue/public visibility, media processing, queue execution, checkout
  and order paths, payment callback handling, shipping tracking, and
  notifications where test facilities permit.

Health responses contain only safe status and component information. Liveness
must not cause restart loops during a provider outage. Readiness can remove an
instance from traffic while operators investigate.

## 22. Backups

Backups protect recoverability and do not replace security, replication, or
data lifecycle controls.

- PostgreSQL production backups are automated, encrypted, access-controlled,
  monitored, and tested by restoration at an approved frequency.
- Backup coverage includes required database state, migration history,
  configuration references, audit records, and reconciliation data.
- S3 originals and required metadata follow an explicit media backup or
  replication policy. Regenerable public derivatives need not have the same
  protection as irreplaceable originals.
- Redis is not the authoritative backup for business data. If Redis
  persistence is enabled, it is treated as a convenience for recovery and
  discarded/rebuilt safely when necessary.
- Backup credentials and destinations are separate from ordinary application
  access. Backup data is not available to development by default.
- Backup success, age, size anomalies, encryption, retention, and restore
  tests are observable through 5.14.
- Retention and deletion follow [4.7 Data Lifecycle](4.7%20Data%20Lifecycle.md),
  including legal holds and controlled exceptions.

## 23. Recovery & Disaster Recovery

MVP disaster recovery prioritizes realistic risks: provider outage, bad
deployment, accidental deletion, database corruption, credential compromise,
media loss, infrastructure failure, and regional service disruption.

Recovery principles:

1. Detect and classify impact using 5.14.
2. Protect evidence and contain the affected service or credential.
3. Restore or promote PostgreSQL from a verified backup/recovery mechanism.
4. Rebuild Redis from safe authoritative state and invalidate unsafe caches.
5. Restore S3 originals/metadata according to media policy; regenerate
   derivatives where possible.
6. Reconcile payment, shipping, notification, search, and queue state with
   provider records and PostgreSQL before reopening workflows.
7. Validate liveness, readiness, smoke paths, security boundaries, and
   business outcomes.
8. Communicate status and complete a post-incident review.

MVP should define, before launch, an approved recovery point objective (RPO),
recovery time objective (RTO), backup owner, provider escalation path,
restore procedure, and emergency contact list. Exact values depend on launch
market, provider, budget, and legal requirements. Recovery is not complete
when servers are running; authoritative orders, payments, shipping, and
notifications must be reconciled.

## 24. Scaling Strategy

### MVP

- One modular backend deployment may serve API, with bounded worker and
  scheduler processes.
- Use managed PostgreSQL and Redis resources sized to measured traffic.
- Use S3-compatible storage for binary media rather than local disk.
- Use queue workers for media, notifications, search indexing, analytics,
  provider callbacks, and other asynchronous work.
- Apply caching and public delivery according to 5.12, without caching
  private or high-impact state in shared layers.
- Monitor capacity, p95/p99 latency, queue age, database connections, Redis
  memory, storage, provider quotas, and error budgets before scaling.

### Evolution when justified by metrics

1. Increase resources or worker count for the bottleneck.
2. Separate API, queue workers, scheduler, and media-processing capacity.
3. Add horizontal API instances behind a load balancer once sessions and
   shared state are verified stateless.
4. Scale PostgreSQL vertically, tune indexes/queries, add read capacity or
   replicas where the database architecture permits.
5. Scale Redis resources or adopt a managed cluster only when cache/queue
   metrics justify it.
6. Add CDN/media edge delivery for public derivatives when traffic and
   geographic latency justify cost.
7. Add search or analytics capacity independently while protecting checkout
   and authentication.
8. Introduce additional regions, failover, or service boundaries only after
   reliability, ownership, and operational costs are understood.

Microservices are not a default scaling response. A module becomes a separate
service only when independent scaling, deployment, failure isolation, or
ownership benefits exceed distributed-system complexity.

## 25. Security Integration

Infrastructure implements [5.13 Security Architecture](5.13%20Security%20Architecture.md):

- Public ingress is separated from private API dependencies and data services.
- TLS protects web, mobile, provider, database, Redis, storage, and operator
  traffic where supported.
- PostgreSQL, Redis, S3, provider, deployment, and monitoring credentials are
  environment-specific, scoped, rotated, and never client-visible.
- IAM/service identities separate API, worker, migration, backup, media, and
  operator responsibilities.
- Production access is individual, least-privileged, audited, and restricted
  by network and approved administrative paths.
- Storage buckets, database ports, Redis ports, queue control planes, and
  observability destinations are private by default.
- Webhooks use HTTPS, provider verification, replay controls, idempotency, and
  environment-specific endpoints.
- Infrastructure logs and alerts exclude passwords, tokens, API keys,
  provider secrets, payment credentials, full addresses, and private media
  URLs.
- Secret leakage, exposed service, suspicious access, and backup compromise
  have containment, rotation, recovery, and audit procedures.

## 26. Observability Integration

Infrastructure implements [5.14 Observability & Logging](5.14%20Observability%20%26%20Logging.md):

- API, web, worker, scheduler, database, Redis, storage, queue, and provider
  components emit structured, redacted logs.
- Request IDs and correlation IDs follow an operation across API, jobs,
  migrations, provider callbacks, and business transitions.
- Metrics cover availability, latency, traffic, errors, saturation, queue
  depth, database health, Redis health, storage, backups, and provider state.
- Liveness, readiness, dependency, and safe business smoke checks are
  available to deployment and operators.
- Alerts identify owner, severity, user/business impact, correlation examples,
  dashboard, and runbook.
- Release identifiers connect deployments to errors, performance changes, and
  business metrics.
- Observability data follows 4.7 retention and 5.13 sensitive-data controls.

## 27. External Provider Connectivity

Payment, shipping, email, push, search, analytics, and other providers are
separate trust boundaries:

- Each environment uses provider-specific sandbox/live accounts and
  credentials. Production callbacks never point to non-production systems.
- Provider calls use TLS, timeouts, bounded retries, circuit breakers, and
  idempotency where side effects exist.
- Egress is restricted to approved provider endpoints and required regions.
- Provider payloads contain minimum necessary fields. FANNAN does not send
  passwords, tokens, raw payment credentials, internal notes, or unnecessary
  personal data.
- Callback ingress verifies signatures, timestamps, event IDs, schemas,
  expected object/state, and replay behavior.
- Provider status cannot bypass API authorization or set an internal state
  without validation and reconciliation.
- Provider outage produces pending/retry/reconciliation behavior rather than
  false success.
- Provider credentials, quotas, outages, callback failures, and settlement
  mismatches are monitored and escalated.

## 28. Cost Considerations

FANNAN should prefer:

- Managed services where they reduce maintenance for PostgreSQL, Redis,
  object storage, certificates, backups, or basic hosting.
- One modular backend deployment and a small worker footprint before adding
  orchestration, multiple regions, or independent services.
- S3/object storage rather than expensive local disk or database blobs.
- Queue-based asynchronous processing rather than oversized synchronous
  application instances.
- Targeted logs, metrics, error tracking, and alerts rather than an
  enterprise telemetry platform before traffic justifies it.
- Automatic lifecycle expiration for temporary objects, logs, and artifacts.

Costs must still account for security, backup, egress, storage growth,
provider fees, observability retention, failover, and operator time. The
cheapest service is not economical if it creates unsafe manual operations or
unrecoverable data.

## 29. MVP Infrastructure

The practical MVP baseline is:

- Managed or reliably hosted web delivery for Next.js and dashboards.
- One Laravel modular-monolith API deployment with bounded worker and
  scheduler processes.
- Managed PostgreSQL as the durable source of truth.
- Managed/private Redis for cache, ephemeral state, rate limiting, locks,
  and queues as defined by prior architecture.
- Separate S3-compatible buckets/accounts for development, staging, and
  production media.
- HTTPS/TLS, environment-specific DNS, private data services, and restricted
  provider egress.
- Environment-specific secrets, service identities, and deployment access.
- Conceptual source-build-test-deploy-health-release pipeline, without
  introducing configuration files in this document.
- Automated encrypted PostgreSQL backups, media recovery policy, restore
  testing, and documented RPO/RTO decisions.
- Structured logs, metrics, error tracking, health checks, alerts, and
  runbooks from 5.14.
- Horizontal scaling, CDN, replicas, multi-region, and microservices remain
  optional and evidence-driven.

## 30. Future Infrastructure

Future infrastructure may add:

- Multiple API instances, independently scaled workers, and managed
  autoscaling after load evidence.
- Read replicas, connection proxies, partitioning, or managed PostgreSQL
  failover after database metrics and recovery objectives justify them.
- Redis cluster/replication and separate cache/queue resources.
- CDN and image delivery optimization for public media at meaningful traffic.
- Dedicated search, analytics, media-processing, or notification capacity
  while preserving domain ownership and security boundaries.
- Multi-region deployment, object replication, provider failover, and tested
  regional disaster recovery.
- Infrastructure-as-code, policy-as-code, managed key services, private
  service networking, and stronger deployment attestations.
- Service decomposition only where independent scaling, failure isolation,
  compliance, or team ownership makes it worthwhile.

## 31. Alternatives Considered

| Alternative | Decision |
| --- | --- |
| Microservices for every domain at MVP | Rejected. The modular monolith is simpler to deploy, test, observe, and operate. |
| Self-host every stateful service | Rejected unless managed options are unavailable or materially unsuitable; operational burden is higher. |
| Local disk for artwork media | Rejected as the durable media store. Use S3-compatible object storage. |
| Redis as database or payment/order authority | Rejected. Redis is ephemeral/supporting infrastructure. |
| One shared environment for all stages | Rejected. It creates data, credential, provider, and release-contamination risk. |
| Production data in development | Rejected except for approved, minimized, irreversibly redacted diagnostics. |
| Multi-region active-active at MVP | Deferred. Cost and complexity are not justified before availability and geographic needs are measured. |
| Public database, Redis, or S3 administration | Rejected. Private connectivity and controlled operator access are required. |
| Build separately for every environment | Rejected. Promote an identified artifact with environment-specific configuration. |

## 32. Tradeoffs

- **Simplicity versus redundancy:** A small MVP topology costs less and is
  easier to operate, but has less automatic failover. Backups, restore tests,
  health checks, and a documented recovery path reduce the risk.
- **Managed services versus control:** Managed PostgreSQL/Redis/storage reduce
  patching and operations but introduce provider dependency and cost.
- **Stateless runtime versus shared dependencies:** Stateless API instances
  scale and recover easily, while Redis, PostgreSQL, queues, and storage need
  careful security and availability controls.
- **Deployment speed versus migration safety:** Backward-compatible migrations
  and post-release observation reduce risk but may require multiple releases.
- **Provider flexibility versus integration surface:** Each external provider
  adds credentials, callbacks, quotas, outages, and data-processing review.
- **Performance versus privacy:** CDN/public caching and telemetry improve
  speed and diagnosis only when private data remains excluded.
- **Recovery objective versus cost:** Faster RPO/RTO requires replication,
  standby capacity, and more testing; MVP targets must be explicit and
  proportionate to business risk.

## 34. Consistency & Open Issues

- Hosting providers, regions, launch countries, DNS ownership, TLS ownership,
  and production operational owners must be selected before implementation.
- Exact PostgreSQL sizing, Redis sizing, storage limits, queue capacity,
  worker count, rate limits, RPO, RTO, and backup retention require measured
  traffic and approved operational targets.
- The selected web host must support secure environment configuration and must
  not expose private dashboard responses through shared caching.
- The selected provider set must provide approved sandbox/live separation,
  callback verification, quotas, data-processing terms, and escalation paths.
- Database migration, media restore, provider reconciliation, and rollback
  procedures must be rehearsed in staging before production launch.
- 4.7 must finalize retention and deletion behavior for backups, logs,
  observability data, media versions, and provider evidence.
- 5.12 must finalize cache topology and invalidation behavior before adding
  CDN or multi-instance caching.
- No future infrastructure component should be introduced solely because it
  is common at larger companies; measured load, reliability, security, cost,
  or ownership evidence is required.
