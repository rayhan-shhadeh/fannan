# 5.5 Authentication & Authorization

**Document ID:** FANNAN-SYS-ARCH-5.5
**Status:** Authoritative MVP identity and access contract
**Applies to:** NestJS API, Next.js web, React Native/Expo mobile, dashboards, jobs, and integrations

## 1. Identity model

FANNAN has one `User` identity. A user may have Customer and Artist capabilities simultaneously. Artist selling actions additionally require an approved Artist Verification state. Admin access is explicit and permission-based; it is not implied by a client role label.

Canonical capabilities are `customer`, `artist`, and `admin`. Canonical administrative permissions are resource-specific and are evaluated server-side. Clients must not infer authorization from decoded claims or hidden controls.

## 2. MVP authentication

- Login and registration issue a short-lived bearer access token and a rotating refresh token.
- Access tokens expire after 15 minutes by default; the API returns `expiresIn`.
- Refresh tokens are opaque, stored only as hashes server-side, rotated on every successful refresh, and revoked on logout, password reset, reuse detection, or administrative session revocation.
- Web stores the refresh token in a Secure, HttpOnly, SameSite cookie. The access token remains in server-side/session-safe web runtime state and is never placed in URLs, page metadata, analytics, or arbitrary local storage.
- Mobile stores refresh credentials only through Expo-compatible platform secure storage. Access tokens remain in memory where practical.
- All transport is HTTPS. Tokens are never logged.

The exact token signing algorithm and key rotation mechanism are infrastructure configuration, not client assumptions.

## 3. Guest checkout credentials

Guest checkout is not an anonymous general-purpose session. The API issues:

- a short-lived opaque `checkoutSessionToken`, scoped to one cart and checkout session;
- a short-lived opaque `orderAccessToken`, scoped to one guest order and read-only order-status operations.

These tokens cannot access account, profile, payment-provider, admin, artist, or unrelated order resources. They are revocable, rate-limited, and delivered only through the active checkout response or the submitted contact channel. Account linking requires an authenticated explicit action.

## 4. Authorization policy

Every request is evaluated against:

1. authenticated identity or explicitly scoped guest token;
2. capability and administrative permission;
3. artist verification state where relevant;
4. resource ownership or assigned operational scope;
5. resource lifecycle and visibility;
6. tenant/region/policy restrictions where applicable.

Resource IDs and role values supplied by clients are never authorization evidence. Protected resources use an indistinguishable not-found response where disclosure would leak existence.

## 5. Sessions and account security

Users may list and revoke their own sessions. Password reset uses generic responses to prevent account enumeration, single-use expiring reset tokens, and revokes existing refresh sessions after a successful change. Login, registration, refresh, recovery, and session-revocation endpoints are rate-limited and audited.

MFA is deferred from MVP, but the contract allows a future step-up state without changing resource ownership or client API boundaries.

## 6. Locale and privacy

`preferred_locale` is an optional user preference with supported MVP values `ar` and `en`. It does not affect identity or authorization. Guests may keep a device preference, but it is not an authoritative user record until saved.

Authentication and authorization failures, tokens, reset links, private addresses, and provider payloads are excluded from logs and analytics. Administrative access and sensitive policy decisions produce auditable records.

## 7. API contract

The Authentication API exposes registration, login, refresh, logout, password recovery/reset, session listing, and session revocation under `/api/v1/auth`. API clients must treat access tokens as credentials, ignore unknown response fields, and use the common error and request-correlation contracts in Section 06.

This document is the sole source of truth for identity, token, session, guest-token, capability, and authorization behavior. Domain documents may add resource-specific policy but may not define a second authentication model.
