# 5.12 Caching & Performance Architecture

| Attribute | Value |
|---|---|
| Document ID | FANNAN-SYS-ARCH-5.12 |
| Status | Proposed Phase 3 architecture baseline |
| Authority | PostgreSQL and approved domain contracts remain authoritative |

## 1 Purpose

Define measurable performance and caching behavior for FANNAN without allowing a cache to become a second database. PostgreSQL is the source of truth for identity, permissions, catalogue, orders, offers, payments, shipping, notifications, media metadata, and audit records. Redis is a bounded coordination and short-lived acceleration facility.

## 2 Scope

This document covers API, PostgreSQL, Redis coordination, web, mobile, media, search, digital artwork, concurrency, monitoring, failure behavior, and scaling. It is architecture documentation only; it does not define a schema or implementation. The repository contains no requested Section 04 directory and no `5.0`–`5.4` files, so canonical entities, indexes, API contracts, deployment topology, capacity limits, and transaction boundaries cannot be invented here.

The available PRDs describe Laravel REST API, Next.js web, and Flutter mobile. Existing 5.5–5.11 architecture documents provisionally describe NestJS, React Native/Expo, PostgreSQL, Redis, and AWS. This Laravel/Next.js/Flutter versus NestJS/React Native/Expo conflict requires an approved technology ADR and is not silently resolved here.

## 3 Performance Goals

These are initial release gates to confirm against the missing non-functional baseline:

| Workload | Initial target at normal load | Measurement |
|---|---:|---|
| Public catalogue/API reads | p95 ≤ 400 ms, p99 ≤ 900 ms | API timing, excluding client network |
| Authenticated dashboard reads | p95 ≤ 600 ms | API timing with authorization |
| Search | p95 ≤ 700 ms, bounded result size | Query and serialization timing |
| Checkout/order mutation | p95 ≤ 900 ms, correctness first | End-to-end API timing |
| Cache hit | p95 ≤ 50 ms from API process | Redis timing |
| Image/card delivery | p95 ≤ 1.5 s after request | Client-observed timing |
| Background work | Queue age ≤ 60 s for normal notifications | Queue metrics |

Targets must be segmented by locale, role, endpoint, payload size, cache outcome, and dependency. No target permits stale authorization, price, stock, payment, or shipment truth.

## 4 Performance Principles

1. Measure before optimizing; protect correctness before reducing latency.
2. Keep request paths bounded with strict page sizes, query and payload limits, and timeouts.
3. Read from the nearest safe representation, but re-check authoritative state for sensitive actions.
4. Prefer PostgreSQL indexes and query shaping over indiscriminate caching.
5. Use one simple Redis deployment boundary in MVP; do not add multiple clusters, complex orchestration, or an event bus solely for invalidation.
6. Degrade to PostgreSQL or a safe error when Redis is unavailable; cache availability is never a prerequisite for checkout or authorization.
7. Treat public, user-scoped, role-scoped, and secret data as different caching classes.
8. Make background work idempotent, observable, bounded, and justified by latency or retry needs.

## 5 Performance-Sensitive Areas

Sensitive workflows include registration, login, refresh, password reset, role changes, MFA/step-up, checkout revalidation, offer acceptance, COD transitions, refunds, address changes, shipment transitions, media publication/deletion, and notification preference changes. They must read current PostgreSQL state inside the authoritative transaction or immediately before transition. A cached response may improve a preceding display, but cannot authorize or commit the action.

High-volume or expensive areas include public catalogue and artwork browsing, bilingual search and filters, authenticated dashboards, notifications, media derivatives, digital artwork previews/download authorization, provider calls, concurrent checkout and offer actions, and background reconciliation.

## 6 Caching Architecture

The API is the cache-policy boundary. A request cache is non-shared and short-lived. Redis may hold transient values, locks, counters, deduplication markers, queue metadata, and selected public/read projections. PostgreSQL stores durable records and any invalidation/version metadata needed for correctness. Object storage owns media bytes; browser caching may serve approved public derivatives, but delivery URLs do not authorize private media.

The authoritative flow is: client to API; the API reads safe projections from request/local cache or Redis, and authoritative state from PostgreSQL; bounded workers may use PostgreSQL and Redis; controlled object storage serves media. PostgreSQL commits precede cache invalidation.

## 7 Redis Responsibilities

Redis is limited to short-lived coordination, read acceleration, and rate limits:

| Responsibility | Required property |
|---|---|
| Short-lived public/read projections | Rebuildable, bounded, versioned keys |
| Request coalescing and stampede locks | Lease expiry and safe recovery |
| Login, reset, search, upload, and API rate limits | Fail-safe policy and short TTL |
| Idempotency/deduplication windows | Never the only durable business record |
| Short-lived queue/worker coordination | Durable outcome written to PostgreSQL |
| Session-risk or revocation hints | PostgreSQL remains authoritative |
| Non-sensitive locale/catalog metadata | Safe fallback on miss |

Redis is not a second database, durable business record, search authority, or unrestricted personal-data store. It must not be the only store for users, roles, permissions, refresh sessions, products, prices, inventory, carts, orders, offers, payments, refunds, addresses, shipments, notification history, media ownership, moderation, audit, or legal evidence. It must not hold access tokens, passwords, payment secrets, private addresses, or unrestricted personal data.

## 8 Cacheable Data

| Data | TTL | Invalidation and safety |
|---|---:|---|
| Public published artwork/artist summaries | 60–300 s | Publish, edit, unpublish, delete; public fields only |
| Public category/filter metadata | 5–30 min | Taxonomy/configuration change |
| Search result pages | 15–60 s | Publication/edit/delete marks; detail endpoint re-checks visibility |
| Locale/translation catalogue | 5–60 min | Catalog release/version |
| User profile presentation | 30–120 s | User-scoped; profile, locale, or privacy update |
| Wishlist/cart display | 10–30 s | Every mutation; PostgreSQL wins on miss |
| Shipping quote estimate | 30–120 s | Hashed address/cart/service/package key; non-binding and revalidated |
| Notification unread count | 10–30 s | User-scoped; durable center remains authoritative |
| Rate-limit, lock, and deduplication state | Policy-specific | Expiry/release; coordination only |
| Public media derivative metadata/URLs | 5–60 min | Moderation, unpublish, delete; private delivery remains signed and short-lived |

Public/user-scoped caches require bounded staleness, explicit scope, security review, and safe fallback. Mobile convenience caches are presentation copies and must be revalidated before sensitive actions.

## 9 Non-Cacheable Data

Prices, inventory, payment status, order status, offer state, authorization decisions, private commissions, support cases, unapproved media, and audit records are not cacheable for mutation decisions. A read-only display may use a very short projection only when clearly labelled as such and refreshed before action. PostgreSQL remains authoritative for all durable business state.

## 10 Cache Keys

Keys use a documented namespace such as `fannan:{environment}:{version}:{scope}:{resource}:{id}:{variant}`. IDs are opaque and normalized; locale, direction, role-safe variant, filter hash, and representation version are explicit. Hash bounded filter material, cap key length, and include an authorization scope only when a projection is safe for that exact scope.

Never put access tokens, email addresses, phone numbers, addresses, raw search terms, payment data, artwork secrets, or private message content in keys. User-scoped keys must never be shared across users; role, tenant, resource, and policy versions must be separated.

## 11 TTL Strategy

TTL is a maximum retention window, not a promise that data remains current. Every key has a namespace, schema/version component, owner, TTL, and invalidation trigger. TTLs are deliberately short for commerce and security data. A cache miss is normal. Stale, expired, malformed, or incompatible values are discarded and rebuilt; they are never repaired by trusting client input.

Bounded stale-while-revalidate is permitted only for public, non-sensitive representations. Short jittered leases reduce synchronized expiry. No TTL permits stale authorization, price, stock, payment, shipment, entitlement, or destructive-action decisions.

## 12 Cache Invalidation

The authoritative write commits PostgreSQL first. After commit, the API deletes or versions affected keys. Missed invalidation is bounded by TTL and scheduled reconciliation. MVP uses direct application invalidation and reconciliation, not a new event bus solely for cache invalidation. Multi-key invalidation is best-effort and idempotent; versioned namespaces support inexpensive bulk retirement.

Unpublish/delete, role or session revocation, price/stock/order/payment/shipment changes, and private-media deletion synchronously bypass or delete relevant projections before returning where feasible. The next sensitive operation always re-checks PostgreSQL. Private-media deletion also invalidates delivery metadata and queues object purge according to 5.6.

## 13 Cache Consistency

PostgreSQL transactions define business truth and ordering. Public discovery, safe profile presentation, and notification badges may be eventually consistent within documented TTL. Checkout totals, negotiated prices, eligibility, inventory, COD policy, payment/refund state, shipping commitment, permissions, entitlements, and destructive actions require PostgreSQL read-after-write. If cache and PostgreSQL disagree, PostgreSQL wins and the cache is invalidated.

## 14 Database Performance

Optimize PostgreSQL before adding infrastructure. Use explicit transactions, narrow projections, prepared/parameterized queries, bounded connection pooling, query timeouts, and measured query plans. Add indexes only for measured predicates and the approved Section 04 schema; do not invent index names or columns here. Remove unused indexes after review.

Index families to validate include identity/session references, ownership foreign keys, publication/visibility plus recency, order/customer and order-state, payment/order, shipment/order and tracking, notification recipient/read/created time, media owner/state, and offer participants/state/expiry. Composite order must follow actual selectivity and sort order. Writes and index maintenance must be measured.

All list endpoints enforce maximum page sizes and stable ordering. Cursor pagination with an opaque, server-validated order/version boundary is preferred for catalogue, notifications, orders, shipments, and search; offset is acceptable for small stable administrative lists. Counts may be omitted or approximate. Pagination must not permit unbounded joins or records that became private.

## 15 Search Performance

MVP search uses PostgreSQL full-text search and `pg_trgm`, with Arabic/English normalization, visibility-first filtering, allowlisted filters and sorting, bounded highlights, deterministic tie-breaks, and cursor pagination. Search indexes are projections, not truth; publication, unpublication, edit, and delete require reconciliation.

If search is degraded, return a bounded error or empty state rather than an unbounded `LIKE` scan or unauthorized fallback. Search result caches have short TTLs and must not include private query data or analytics secrets.

## 16 API Performance

Use compact DTOs, field-appropriate projections, compression where safe, conditional requests for public representations, and explicit timeouts for PostgreSQL, Redis, storage, and providers. Avoid N+1 queries, duplicate serialization, unbounded payloads, and unbounded retries. Authorization is enforced at the API boundary with default deny; no auth-sensitive cache bypass is permitted.

Sensitive commands use current PostgreSQL state, database transactions, constraints, row/version checks, and idempotency. Redis rate limits and hints may assist but cannot authorize or commit a command.

## 17 Web & Mobile Performance

Next.js is the PRD choice; Flutter is named by the PRDs, while React Native/Expo is the provisional architecture direction. The stack ADR must decide ownership. Web and mobile clients use bounded payloads, cursor pagination, image dimensions/derivatives, cancellation on navigation, and retry with jitter.

Conditional/browser caching is appropriate for approved public representations only. Authenticated/private responses require explicit cache controls. Mobile caches are convenience copies: clear or partition them on account switch/logout, never persist tokens or unencrypted private media, and revalidate before sensitive actions. Accessibility, RTL, locale formatting, and error states must not be removed for speed.

## 18 Media Performance

Follow 5.6 quarantine, scanning, bounded derivatives, and controlled object-storage delivery. Serve thumbnail/card/detail derivatives rather than originals in lists; declare dimensions, select responsively, and lazy-load below the fold. Versioned public immutable derivatives may use browser caching.

Private originals and commissions use short-lived signed URLs and restrictive cache controls. Do not add a CDN in MVP; revisit only with measured latency, egress, or traffic evidence. Digital artwork previews may use approved public derivatives. Download authorization must query current order/payment/license state, issue a short-lived controlled URL only when allowed, and record audit evidence in PostgreSQL. Resumable or large-file delivery is future scope.

## 19 Concurrency

Use PostgreSQL constraints, transactions, row/version checks, and idempotency for competing checkout, offer, payment, stock, shipping, publication, and deletion commands. Redis locks may reduce duplicate work but cannot replace database concurrency control or prove a transition succeeded.

Bound connection pools and worker concurrency per dependency. Apply backpressure rather than unbounded retries. Stampede protection may use request coalescing and short jittered leases for expensive safe reads; a failed lease holder falls back to PostgreSQL or a safe empty/error result. Track lock waits, deadlocks, retries, and rejected work.

## 20 Failure Handling

On Redis failure, bypass safe caches and use PostgreSQL; rate limits use a fail-safe policy. Sensitive mutations continue when their authoritative path is healthy. On PostgreSQL failure, do not fabricate cached commerce, authorization, payment, shipping, notification, or entitlement state; return a safe error and preserve retryable commands only through an approved durable mechanism.

On search failure, return a bounded degraded state. On object-storage failure, browsing metadata may continue while media uses a safe placeholder. Provider failures follow 5.10/5.11 and must not silently change business state. Redis eviction, restart, replication lag, or loss must never corrupt business state.

## 21 Performance Monitoring

Measure request rate, p50/p95/p99 latency, errors, timeouts, payload sizes, PostgreSQL query latency/plans/pool saturation, Redis hit/miss/eviction/memory/latency, lock wait, invalidation lag, stale age, stampede rate, queue age/retries, search quality, media delivery, and client startup/render metrics.

Segment by endpoint, locale, role-safe scope, dependency, and cache result. Correlation IDs connect API, worker, notification, payment, and shipping operations. Do not log secrets, tokens, private content, raw addresses, or payment data. Alert on SLO breaches, contention, queue age, and invalidation lag.

## 22 Security Considerations

There is no authorization cache bypass. Permission or session-revocation hints may be cached only with very short TTL and fail-closed semantics for elevated actions. Role changes, logout-all, password reset, suspension, media unpublish/delete, and support-scope changes retire hints immediately after PostgreSQL commit.

Never cache a positive authorization result across users, tenants, resources, or policy versions. Client route guards and stale Redis data are not security controls. Use restricted Redis access, opaque identifiers, hashed bounded key material, safe cache headers, signed private-media URLs, and no credentials or sensitive personal data in cache values or keys.

## 23 MVP Scope

- PostgreSQL source of truth, measured indexes/query shaping, narrow projections, cursor pagination, and PostgreSQL FTS/`pg_trgm`.
- One Redis boundary for short-lived public/user-scoped read projections, coordination locks, rate limits, and idempotency hints.
- Short TTLs, direct post-commit invalidation, versioned namespaces, reconciliation, safe fallbacks, and observability.
- Responsive media derivatives, public immutable browser caching, safe mobile convenience caches, and revalidation.
- Idempotent bounded workers for notifications, media, reconciliation, provider polling, cleanup, and justified analytics.
- No auth-sensitive cache bypass, no second database, no CDN, and no overengineered orchestration.

## 24 Future Extensions

Only after measured need and an approved ADR: dedicated cache tiers or multiple Redis clusters, a dedicated search or vector engine, edge/CDN delivery, advanced warming, complex orchestration, or an event bus for broader workflows. Offline-first commerce and resumable/large digital downloads remain future scope.

## 25 Alternatives Considered

| Alternative | Decision |
|---|---|
| Make Redis a durable domain store | Rejected; PostgreSQL remains source of truth |
| Add a dedicated search engine in MVP | Deferred; PostgreSQL FTS/`pg_trgm` is sufficient until measured otherwise |
| Use an event bus solely for invalidation | Deferred; direct invalidation plus reconciliation is simpler |
| Add CDN or multiple Redis clusters immediately | Deferred; require latency, egress, traffic, or saturation evidence |
| Cache authorization and commerce decisions | Rejected; correctness and security require current PostgreSQL state |
| Choose between Laravel/Next.js/Flutter and NestJS/React Native/Expo here | Rejected; requires an approved technology ADR |

## 26 Tradeoffs

Short TTLs and revalidation increase database reads but protect price, stock, permission, payment, shipment, and entitlement correctness. Direct invalidation is simpler than a distributed event topology but can leave bounded staleness until TTL or reconciliation. PostgreSQL search avoids MVP infrastructure but limits scale and search features. One Redis boundary reduces operational complexity but provides less isolation. Responsive derivatives improve latency and egress at the cost of storage and processing. Correctness, security, and operability take priority over theoretical maximum cache hit rate.
