## 1. Overview

This document defines the checkout experience for FANNAN. It covers the flow a customer follows to review, confirm, pay for, and receive an order, including guest and authenticated checkout, shipping and address selection, coupon application, payment authorization, confirmation, order creation, failure handling, and recovery.

The checkout experience must be clear, trustworthy, accessible, multilingual, and resilient. It shall help users complete purchases with confidence while protecting payment, order, shipping, and account information. Checkout must support both buyer intent and operational reliability without inventing inaccessible or unsafe flows.

This document describes product behavior only. It does not define database fields, undocumented API endpoints, payment provider contracts, or internal implementation details. Exact request and response shapes, transaction data, persisted order fields, payment provider integrations, and routing logic shall be documented in the dedicated commerce, payments, shipping, and API specifications before implementation.

## 4. Guest Checkout

### 4.1 Purpose

Guest checkout allows a user to complete a purchase without creating an account. It supports low-friction buying while still preserving trust, order traceability, and recovery in case the user leaves mid-flow.

### 4.2 Workflow

1. User adds one or more eligible items to cart.
2. User opens checkout without signing in.
3. System checks cart validity, product availability, shipping eligibility, and order constraints.
4. User enters required contact and shipping information or continues with a supported guest contact flow.
5. User reviews summary and proceeds to payment.
6. User receives confirmation or a safe failure state if payment or order creation is blocked.

### 4.3 Business Rules

- Guest checkout shall support a legally and operationally allowed purchase path without forcing account creation.
- The system shall not require a password or account setup before a purchase can be completed in the permitted workflow.
- Guest orders must maintain a valid order and contact record for status communication, shipping, and support.
- The system shall clearly explain what data is required and what is optional before the user submits payment.

### 4.4 Validation

- Cart eligibility shall be revalidated at checkout start and again before final payment submission.
- Contact and shipping information shall be checked for required fields and safe formatting.
- Buyers shall not be allowed to complete a payment if required product, shipping, or buyer conditions are not met.

### 4.5 Permissions

| Actor | Permissions |
| --- | --- |
| Guest | Begin guest checkout to complete a permitted purchase without account creation. |
| Customer | Complete both guest and authenticated checkout flows when applicable. |
| Admin | Review operational failures and support outcomes for guest purchases. |

### 4.6 Edge Cases

- If the cart becomes invalid while the guest is in checkout, the system shall prevent payment and direct the user to the cart or product page.
- If the user leaves the checkout mid-flow, the system shall preserve cart state and return them to a safe recovery path.
- If contact details are incomplete, the system shall block submission and highlight the required fields.

### 4.7 Acceptance Criteria

- A guest can complete a purchase without creating an account when the flow is allowed.
- The guest receives clear, actionable feedback on required data and payment state.
- Failed or interrupted guest checkout leads to a recoverable path without losing cart intent.

## 5. Authenticated Checkout

### 5.1 Purpose

Authenticated checkout provides a faster, safer, and more personalized purchase process for existing customers. It allows the customer to leverage saved addresses, order history, preferences, and secure account context while completing purchase.

### 5.2 Workflow

1. Customer signs in or continues an authenticated session.
2. System loads the current cart, address book, preferred shipping, and order summary.
3. Customer reviews cart, updates quantities or addresses if needed, and proceeds.
4. Customer confirms eligibility, applies coupon, and initiates payment.
5. System creates the order and returns confirmation.

### 5.3 Business Rules

- Authenticated checkout shall preserve account identity, profile context, and trusted order history where allowed.
- Saved addresses, shipping preferences, and earlier orders must be read-only or editable only within documented account rules.
- The system shall not bypass security checks for an authenticated user simply because the user is signed in.
- Authenticated checkout must still validate order state, shipping availability, price, and payment conditions before completion.

### 5.4 Validation

- Order confirmation shall validate the current cart, selected address, shipping method, payment authorization, and order summary.
- Duplicate or stale user session states shall not allow a second order to be created for the same cart without authorization.
- Account status, restrictions, and payment-policy checks shall be revalidated before payment authorization.

### 5.5 Permissions

| Actor | Permissions |
| --- | --- |
| Customer | Complete authenticated checkout for eligible cart items and account status. |
| Guest | Not allowed to bypass authentication if the platform requires it for the active purchase path. |
| Admin | Support authenticated purchase failures and account-related conditions. |

### 5.6 Edge Cases

- If the session expires during checkout, the system shall guide the customer back to a safe authenticated state without losing cart contents.
- If account restrictions or payment issues appear after login, the system shall stop the purchase and show the correct recovery instructions.
- If the user changes account context while in checkout, the system shall revalidate the cart and order summary before payment.

### 5.7 Acceptance Criteria

- An authenticated customer can complete checkout with a familiar, trusted flow and valid saved context.
- Authentication does not bypass required validation for price, shipping, products, or payment eligibility.
- Session expiry or account state changes produce a safe recovery state.

## 6. Address Selection

### 6.1 Purpose

Address selection defines how customers choose the shipping destination for their order. It supports saved addresses, new address entry, validation, and correct fulfillment routing.

### 6.2 Workflow

1. User opens address selection in checkout.
2. System loads saved addresses when available or shows address-entry form requirements.
3. User selects an address or adds a new one.
4. System validates country, region, city, postal code, and contact details against the supported shipping logic.
5. Selected address becomes the active shipping destination for the order summary and payment step.

### 6.3 Business Rules

- The selected address must match the shipping country, region, and supported shipping policy.
- The system shall not allow a customer to choose a shipping destination that violates the product’s shipping coverage or supported delivery policy.
- Address validation must be clear and actionable when fields are missing, invalid, or inconsistent.
- Customers must be able to edit or replace the selected address before order submission.

### 6.4 Validation

- Address completeness and field-level validation shall be enforced before moving to payment.
- Shipping coverage checks shall validate that the destination is eligible for the selected shipping options.
- Duplicate or ambiguous addresses must be handled with clear prompts or a safe default action.

### 6.5 Permissions

| Actor | Permissions |
| --- | --- |
| Guest | Enter and use a valid delivery address in guest checkout. |
| Customer | Select from saved addresses or add/edit a new shipping address. |
| Admin | Review address-related support cases or order issues in approved operational contexts. |

### 6.6 Edge Cases

- If the address is not supported for shipping, the system shall show the reason and prevent order completion.
- If the user entered a courier or delivery method that conflicts with the selected address, the system shall block the invalid combination.
- If the customer is using a saved address that is no longer valid, the system shall prompt for update rather than silently applying stale data.

### 6.7 Acceptance Criteria

- The customer can choose a valid address for shipping before committing to payment.
- Invalid or unsupported addresses are surfaced clearly and block order completion.
- Address changes are reflected consistently in order summary and shipping calculations.

## 7. Shipping

### 7.1 Purpose

Shipping defines the delivery options available to the customer and how those options are presented and validated in checkout.

### 7.2 Workflow

1. Customer selects or confirms shipping destination.
2. System checks supported shipping methods for the destination, order value, and product constraints.
3. System presents the valid shipping options with cost, timing, and any restrictions.
4. Customer selects a method or the system defaults to the approved option where policy allows.
5. Order summary is updated with shipping cost and expected delivery timing.

### 7.3 Business Rules

- Shipping methods shall be based on approved coverage, product eligibility, and delivery policy.
- Shipping cost and timing shall be clearly shown before the user commits to payment.
- A customer shall not be charged for a shipping option that is invalid for the selected order or destination.
- Shipping information must remain in sync with the selected address and current order state.

### 7.4 Validation

- Shipping options must be validated against destination, product category, and warehouse or fulfilment constraints.
- User-selected shipping must be checked before payment authorization and order creation.
- Shipping estimates must remain consistent with the order summary and final confirmation.

### 7.5 Permissions

| Actor | Permissions |
| --- | --- |
| Guest | Select supported shipping options for eligible orders. |
| Customer | Choose from valid shipping methods and review timing/cost before payment. |
| Admin | Review shipping-related operational failures and support cases. |

### 7.6 Edge Cases

- If no shipping method is valid for the destination, the system shall clearly explain the limitation and prevent checkout.
- If shipping is temporarily unavailable, the system shall hide or disable the unavailable options and show a safe message.
- If a shipping cost changes after selection, the system shall notify the customer before payment and require confirmation if required by policy.

### 7.7 Acceptance Criteria

- Customers see only valid shipping options for their order and destination.
- Shipping cost and timing are clear before payment submission.
- Unsupported shipping scenarios are blocked with clear guidance.

## 8. Coupons

### 8.1 Purpose

Coupons allow customers to apply eligible discounts to an order. They support a promotional and customer-acquisition mechanism while preserving fairness, validation, and fraud safeguards.

### 8.2 Workflow

1. User enters or selects a coupon code during checkout.
2. The system validates the code against the current cart, order value, eligibility, expiry, usage rules, and customer status.
3. The system applies a valid discount to the order summary or shows a clear rejection reason.
4. Customer can remove the coupon if they change their mind or if the cart no longer qualifies.

### 8.3 Business Rules

- Coupon application shall be validated against the active cart and its current state.
- Customers shall not be able to apply expired, ineligible, or duplicate coupons without clear feedback.
- Coupon discounts shall be shown transparently in the order summary before payment.
- Discount application must be consistent with product policy, order value, and customer eligibility rules.

### 8.4 Validation

- Coupon validity, expiry, product restrictions, minimum purchase conditions, and user eligibility shall be checked before application.
- The system shall not apply a coupon to a cart that no longer meets the conditions after quantity or item changes.
- The order summary must reflect coupon deductions accurately before payment authorization.

### 8.5 Permissions

| Actor | Permissions |
| --- | --- |
| Guest | Apply eligible coupons where guest checkout permits discount usage. |
| Customer | Apply, remove, and review valid coupons for their order. |
| Admin | Review coupon eligibility and operational issues. |

### 8.6 Edge Cases

- If a coupon becomes invalid after item changes, the system shall remove it and show a safe explanation.
- If a customer enters an invalid code, the system shall show a clear error without implying it was accepted.
- If multiple coupons are configured and only one is allowed, the system shall enforce the policy and explain the valid state.

### 8.7 Acceptance Criteria

- Valid coupons are applied transparently, and invalid ones are rejected with clear feedback.
- Discounts update order totals in real time or before final submission.
- Coupon removal and reapplication remain predictable and easy to understand.

## 9. Taxes (Future)

### 9.1 Purpose

Tax handling is a future requirement that defines how checkout accounts for tax or VAT obligations where the marketplace supports them. Until formally implemented, tax behavior must be documented as a future policy requirement and must not be silently assumed.

### 9.2 Workflow

1. Customer reaches the checkout summary.
2. System evaluates the supported tax policy for the order destination, product type, and legal region.
3. Tax amount is calculated and shown in the order total if the policy is active.
4. Customer reviews final charges before payment submission.

### 9.3 Business Rules

- Tax handling must be intentionally enabled through approved policy and legal compliance review.
- Unsupported regions or scenarios shall not silently apply or omit tax without the documented policy.
- A user must see the tax breakdown where tax policy is active and affects the final total.

### 9.4 Validation

- Tax rules must be checked against approved destination and product policy before order completion.
- If tax support is not yet active, the system must avoid implying a tax calculation that does not exist.

### 9.5 Permissions

| Actor | Permissions |
| --- | --- |
| Customer | Review total costs when tax policy is active. |
| Guest | See total when tax policy is active in the supported purchase flow. |
| Admin | Maintain future tax configuration in approved policy workflows. |

### 9.6 Edge Cases

- If region is unsupported or tax policy is absent, the system shall not claim a tax calculation without a documented rule.
- If a tax policy changes after the user starts checkout, the system shall communicate the change before final payment.

### 9.7 Acceptance Criteria

- Tax support, when enabled, is clear and transparent in the final order total.
- Unsupported or future tax scenarios do not create false user expectations.

## 10. Review Order

### 10.1 Purpose

The review order step allows the customer to confirm the cart, selected shipping, coupons, totals, and chosen delivery method before payment. It is the final trust and accuracy checkpoint before purchase commitment.

### 10.2 Workflow

1. User reaches the review step from the checkout form.
2. System displays a clear summary of items, quantities, pricing, shipping, coupon adjustment, and totals.
3. User verifies address, shipping, contact, and order details.
4. User confirms that the order and total are correct before payment.

### 10.3 Business Rules

- The review step shall show the most current order data and allow corrections before payment.
- Any change to address, shipping method, item quantity, or coupon must trigger a refreshed total before submission.
- Users must be able to go back and change details without losing the cart or order intent.
- Final review must clearly distinguish order amount, shipping amount, discount, and total payable.

### 10.4 Validation

- Final order summary shall be validated against the live item state and selected fulfillment options.
- Payment cannot proceed until the review state is current and the cart is valid.
- The system shall not allow hidden or stale cart adjustments to bypass the review checklist.

### 10.5 Permissions

| Actor | Permissions |
| --- | --- |
| Guest | Review order details before final payment in the allowed guest flow. |
| Customer | Review and edit checkout details before payment submission. |
| Admin | Support operational review of failed or disputed orders. |

### 10.6 Edge Cases

- If the cart changes after review, the system shall refresh the summary and require confirmation of the updated total.
- If a product becomes unavailable or out of stock, the system shall remove or block it before payment and present the safe alternative or recovery path.
- If a selected item is no longer eligible for a coupon or shipping option, the order summary must update and the user must be notified.

### 10.7 Acceptance Criteria

- Customers can review the complete order before final payment with no ambiguity about items or totals.
- Review reflects the latest valid state and prevents stale order data from being submitted.
- The user can safely back out or revise the order before final commitment.

## 11. Payment

### 11.1 Purpose

Payment is the final transaction step in checkout. It authorizes payment for the order and ensures the user receives clear status updates about success, decline, or retry options.

### 11.2 Workflow

1. User proceeds from review to payment.
2. System validates order state, totals, shipping, contact details, and payment eligibility.
3. User provides payment details through the approved payment flow.
4. System requests authorization and returns success or failure status.
5. System continues to confirmation only for approved payment states.

### 11.3 Business Rules

- Payment shall be initiated only when the line items, order summary, shipping, coupon, and address are still valid.
- The system shall not show a false success state if payment is declined or pending.
- Payment is subject to documented security, fraud, and compliance rules.
- Payment failures must provide clear next steps and avoid suggesting the order has been placed when it has not been finalized.

### 11.4 Validation

- Payment authorization must be validated against the active order and payment method policy.
- Declined, failed, or pending payment states shall be treated as non-final purchase states.
- Payment method restrictions shall be enforced before the user enters or submits payment.

### 11.5 Permissions

| Actor | Permissions |
| --- | --- |
| Guest | Submit payment in the supported guest purchase flow. |
| Customer | Submit payment in the authenticated checkout flow. |
| Admin | Monitor payment failures and support incidents in approved operational workflows. |

### 11.6 Edge Cases

- If payment is declined, the user must remain in a recoverable flow and be allowed to retry or adjust details.
- If a payment method is unsupported or blocked, the system shall show the correct explanation and offer alternate paths.
- If a payment provider timeout occurs, the system shall avoid claiming failure or success without a confirmed final state.

### 11.7 Acceptance Criteria

- Payment is only finalized when the order state and payment authorization are valid.
- Users receive clear, trust-preserving feedback for approval, decline, and pending states.
- Payment failure does not create a false order or misleading confirmation state.

## 12. Confirmation

### 12.1 Purpose

Confirmation communicates the successful completion of an order and gives the customer confidence that the purchase is secured and tracked.

### 12.2 Workflow

1. Payment is approved and order creation is authorized.
2. System updates order status to a confirmed or pending confirmation state as allowed by product policy.
3. Customer sees a confirmation screen with the order reference, summary, shipping information, and next steps.
4. The system sends the relevant notification or confirmation message in the supported channel policy.

### 12.3 Business Rules

- Confirmation shall only be shown for a valid order and approved payment state.
- The confirmation state must display a clear order reference or equivalent human-readable identifier.
- The confirmation state must remain understandable in both Arabic and English and remain accessible.
- The system shall not send a confirmation for an order that is still pending or failed.

### 12.4 Validation

- Confirmation status must be validated against the final order and payment state.
- Final order summary must be consistent between checkout and confirmation.
- Notification triggers must respect the user’s notification preference policy.

### 12.5 Permissions

| Actor | Permissions |
| --- | --- |
| Guest | Receive confirmation for a successful guest order. |
| Customer | Receive confirmation for their successful order and status tracking. |
| Admin | Review confirmation state and support issues in approved workflows. |

### 12.6 Edge Cases

- If confirmation is delayed after a successful payment, the system shall show a safe pending state without falsely claiming complete success.
- If the order is created but a confirmation message fails to send, the order remains valid and the user can continue to use the order reference for support.
- If a duplicate confirmation event is triggered, the system shall prevent duplicated or conflicting confirmation states.

### 12.7 Acceptance Criteria

- Successful orders receive a clear confirmation message with the right next actions.
- Confirmation is not displayed before payment and order state are valid.
- Users can identify their order confidently and continue through tracking or support paths.

## 13. Order Creation

### 13.1 Purpose

Order creation converts the checkout state into an authorized customer order that can be tracked, shipped, supported, and reviewed.

### 13.2 Workflow

1. Payment is approved.
2. System creates the formal order, links the cart items, and records the selected shipping and totals.
3. The order is assigned a status and a reference number or equivalent identifier.
4. The system updates the user’s order history and support visibility according to the approved rules.

### 13.3 Business Rules

- Order creation shall happen only after payment approval or the approved transaction state for the sales policy.
- Orders shall preserve a single authoritative source of truth for status, summary, customer contact, shipping, and payments.
- Order creation must align with documented inventory, shipping, and payment rules.
- An order shall not be created for a cart that is invalid, empty, or blocked by policy.

### 13.4 Validation

- Cart, totals, shipping, and payment state shall be revalidated before order creation.
- Order references and state transitions must be checked for consistency.
- Duplicate creation from repeated payment callbacks or retries must be prevented.

### 13.5 Permissions

| Actor | Permissions |
| --- | --- |
| Customer | View their successful and pending orders in their order history. |
| Guest | Receive order reference details and support follow-up after a guest purchase. |
| Admin | View and support order records in approved operational workflows. |

### 13.6 Edge Cases

- If a duplicate payment callback arrives, the system shall ensure only one order is created.
- If an order fails after creating a preliminary record, the system shall clear or mark the status safely without leaving a misleading confirmed order.
- If stock or shipping validation fails after payment approval, the system must not silently proceed with an invalid order.

### 13.7 Acceptance Criteria

- Each successful purchase results in a single valid order record with consistent state and reference details.
- Order creation is blocked when the cart or payment state is invalid.
- Duplicate or retry events do not create multiple orders from one purchase attempt.

## 14. Failure Handling

### 14.1 Purpose

Failure handling ensures that checkout problems are communicated clearly, safely, and recoverably. The user should never be left guessing whether the order succeeded or failed.

### 14.2 Workflow

1. A failure occurs in cart validation, price calculation, shipping, payment, or order creation.
2. The system identifies the failure category and the user-facing message to display.
3. The user is shown an action-oriented message with either retry, edit, or recovery options.
4. The system records the failure state for support or operational review without creating a false success state.

### 14.3 Business Rules

- User-facing failure states must be explicit, honest, and actionable.
- A failure in payment or order creation shall never imply a completed purchase.
- System failures must degrade gracefully and avoid leaving the user in a non-recoverable state.
- The customer shall be able to act on the failure without losing the cart or intended purchase.

### 14.4 Validation

- Error messages shall be checked for clarity, actionability, and language support.
- Failure states must be mapped to safe recovery paths and not silently reset the cart.
- Recovery flows must be validated for all high-risk checkout failure points.

### 14.5 Permissions

| Actor | Permissions |
| --- | --- |
| Guest | See and act on checkout failure guidance in guest flow. |
| Customer | Receive failure guidance and proceed to recovery or support state. |
| Admin | Review support-worthy failures and operational patterns. |

### 14.6 Edge Cases

- If payment is attempted but the provider is unreachable, the system shall show a timeout or connection error without claiming the order has failed or succeeded.
- If shipping or stock becomes unavailable during review, the system shall block payment and request a corrected selection.
- If there is a technical interruption after the user submits payment, the system shall maintain a pending or recovery state and guide the user to the next step.

### 14.7 Acceptance Criteria

- Failed checkout states are transparent, actionable, and recoverable.
- Users always know whether the order is pending, failed, or confirmed.
- Failure handling does not damage trust or leave the user stranded.

## 15. Recovery

### 15.1 Purpose

Recovery gives the customer a safe route back into checkout after an interruption, error, or temporary failure without requiring them to start the purchase from scratch.

### 15.2 Workflow

1. The system detects a failed, interrupted, or incomplete checkout state.
2. The system restores the cart, selected address, shipping method, discount state, and summary where supported.
3. The user is shown a recovery path, such as retry payment, re-enter shipping details, or return to review.
4. The user resumes the purchase from the last valid state or a safe next action.

### 15.3 Business Rules

- Recovery must preserve the customer’s intent and valid cart state wherever possible.
- Recovery flows shall not claim the order is already complete when the cart or payment is not yet confirmed.
- The customer must be able to return to a safe state without losing necessary purchase information.
- Recovery screens must remain accessible and localized in the supported languages.

### 15.4 Validation

- Recovery must be validated for cart preservation, address retention, and payment retry states.
- A recovery path must not overwrite valid selections without a clear user action.
- Restored states must be checked against current availability and pricing before payment resumes.

### 15.5 Permissions

| Actor | Permissions |
| --- | --- |
| Guest | Resume checkout after a valid recovery path in guest flow. |
| Customer | Resume or retry an interrupted checkout from a safe saved state. |
| Admin | Support customer recovery issues and review operational failures. |

### 15.6 Edge Cases

- If the cart changes while the user is recovering, the system shall refresh the summary and ask the user to confirm updated pricing or remaining availability.
- If the session expires during recovery, the user must be sent back to a verified login or guest-safe state without losing the cart.
- If a payment is already authorized but order creation is not complete, the system shall show the correct pending or reconciliation state rather than restarting the order.

### 15.7 Acceptance Criteria

- Users can recover from interruptions and technical errors without starting over unnecessarily.
- Recovery preserves valid cart and checkout state wherever safe and allowed.
- Recovery paths do not create false purchase states or misleading success messages.

## 16. Summary

The FANNAN checkout workflow must help customers move from cart to confirmed order with clarity, confidence, and minimal friction. It must support guest and authenticated buying, correct address and shipping selection, transparent coupon and total handling, safe payment authorization, confirmation, and structured recovery from failures. This specification defines the product-level checkout behavior while leaving the detailed payment-provider contracts, order persistence, fulfillment integration, and system-level transaction choreography to the relevant engineering and API specifications.
