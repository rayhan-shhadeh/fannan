## 1. Overview

FANNAN's marketplace features help Guests, Customers, and Artists discover, evaluate, save, follow, review, request, and share Palestinian artwork and artist profiles through a trustworthy, accessible, bilingual, artist-first experience. These features refine the marketplace requirements in `FR-MKT`, `FR-PROD`, `FR-SRCH`, `FR-CUSTD`, `FR-ARTD`, `FR-ADM`, `FR-NOT`, and `FR-ANL`.

This document describes product behavior only. It does not define database fields, undocumented API endpoints, provider contracts, ranking algorithms, or moderation policies. Exact request and response shapes, persisted fields, cache keys, analytics events, and state machines shall be documented in the relevant API, data model, search, analytics, moderation, commerce, and commission specifications before implementation.

## 2. Marketplace Principles

| ID | Principle | Requirement |
| --- | --- | --- |
| MKT-PR-001 | Artist-first presentation | Marketplace surfaces shall elevate the artwork, artist identity, materials, cultural context, availability, and next permitted action without turning artists into anonymous inventory. |
| MKT-PR-002 | Server authority | Availability, price, visibility, eligibility, permissions, review state, favorite state, follow state, commission availability, and report outcomes shall derive from the documented REST API. |
| MKT-PR-003 | Public-private boundary | Public marketplace pages shall expose only eligible public content. Drafts, suspended content, internal notes, private buyer data, and review rationale shall not be exposed. |
| MKT-PR-004 | No deceptive growth tactics | Marketplace features shall not use fake scarcity, undisclosed paid placement, fabricated trending claims, invented recommendations, or manipulative prompts. |
| MKT-PR-005 | Accessibility and localization | All features shall satisfy WCAG 2.2 AA, support Arabic and English, work from 320 px width upward, and preserve correct LTR/RTL behavior. |
| MKT-PR-006 | MVP boundary | Public social feeds, public comments, direct messages outside approved workflows, auctions, resale, NFTs, subscriptions, and AI-generated recommendations are out of MVP unless separately approved. |

## 4. Homepage

### 4.1 Purpose

The homepage shall introduce FANNAN as a premium Palestinian artist-and-artisan marketplace and route users into public discovery, artist exploration, categories, featured collections, search, and authenticated intent actions without requiring sign-in.

### 4.2 Workflow

1. User opens the public homepage.
2. System loads approved public marketplace modules, such as hero editorial area, featured artworks, artist highlights, categories, featured collections, and search entry.
3. User selects a discovery path: search, category, collection, artist page, product page, sign-in, sign-up, favorite, follow, commission request, or purchase entry.
4. Account-required actions preserve safe intent and route the user to authentication.
5. System returns the user to the permitted destination after successful authentication where the target content remains eligible.

### 4.3 Business Rules

- Homepage content shall display only public, eligible, approved marketplace content.
- The homepage shall not show draft, private, suspended, rejected, under-review, or internally restricted content.
- Featured modules shall be governed by documented editorial or ranking rules and shall not imply paid placement unless disclosure rules are documented.
- The homepage shall provide visible routes to search, categories, artist discovery, and authentication.
- Homepage modules shall remain useful when catalogue volume is small; empty sections shall be hidden or replaced with approved empty states rather than fabricated content.
- Homepage content shall meet NFR performance, SEO, accessibility, localization, and image optimization targets.

### 4.4 Validation

- Public content eligibility shall be validated server-side.
- Homepage module configuration shall reference only active, eligible public resources.
- Links shall resolve to public routes or documented authentication entry points.
- Localized copy, alt text, and metadata shall exist for supported launch languages or use approved fallback behavior.

### 4.5 Permissions

| Actor | Permissions |
| --- | --- |
| Guest | View homepage, search entry, public modules, and public content links. |
| Customer | View homepage and perform authenticated intent actions such as favorite, follow, cart entry, or commission entry where eligible. |
| Artist | Same as Customer when acting in marketplace context; artist dashboard controls are not exposed on public homepage. |
| Moderator | View public homepage; moderation actions occur only in authorized internal workspace. |
| Admin | View public homepage; homepage configuration is allowed only through documented admin configuration workflows. |

### 4.6 Edge Cases

- If homepage content fails to load, the system shall show a recoverable error and retain navigation to search and public informational pages.
- If a featured item becomes unavailable after page load, destination pages shall show current authoritative availability.
- If the user is offline or on a poor connection, safe cached public shell content may appear, but account and transaction state shall not be implied.
- If Arabic and English content are mixed, the layout shall maintain correct language and direction semantics.

### 4.7 Acceptance Criteria

- Given a Guest opens the homepage, when content loads, then only eligible public content is shown.
- Given an account-required action is selected, when the user is unauthenticated, then authentication is requested and safe intent is preserved where policy permits.
- Given a homepage module has no eligible content, when the page renders, then it is hidden or replaced with an approved empty state.
- Given the homepage is tested at required breakpoints and zoom levels, then no essential action or content is lost.

## 5. Categories

### 5.1 Purpose

Categories shall help users browse artwork and artists through approved marketplace taxonomy such as medium, product type, theme, craft category, or other documented classification.

### 5.2 Workflow

1. User opens category navigation or a category landing page.
2. System displays active public categories and any approved hierarchy, descriptions, imagery, and counts.
3. User selects a category.
4. System shows eligible public artworks or artists filtered by the selected category.
5. User refines results using documented filters and sort options.

### 5.3 Business Rules

- Categories shall be approved marketplace configuration, not arbitrary user-generated labels.
- A category shall not be public unless it is active and permitted for marketplace discovery.
- Category counts shall include only eligible public content and shall not expose draft or restricted inventory.
- Deprecated, merged, or renamed categories shall route users through documented migration or redirect behavior.
- Category pages shall support SEO metadata and localized names where translations are approved.
- Category display shall not make unsupported cultural, provenance, or eligibility claims.

### 5.4 Validation

- Category identifiers, slugs, localized labels, sort order, and visibility shall be validated by the API contract before client use.
- Filters applied within categories shall use documented filter values only.
- Empty or invalid category routes shall return documented not-found or redirect behavior.

### 5.5 Permissions

| Actor | Permissions |
| --- | --- |
| Guest | Browse public active categories and public category results. |
| Customer | Browse categories and perform permitted authenticated actions on result items. |
| Artist | Browse categories as a marketplace user; manage own listing categories only in artist catalogue workflows. |
| Moderator | Review category-linked content only through assigned moderation queues. |
| Admin | Manage categories only through documented governed configuration with audit logging. |

### 5.6 Edge Cases

- Category has no eligible public content.
- Category is renamed while a user has an old link.
- Filter combination returns zero results.
- Category label is longer in Arabic than English and must wrap without truncating meaning.
- A listing belongs to a deprecated category.

### 5.7 Acceptance Criteria

- Given a public category exists, when a user opens it, then only eligible public content in that category is displayed.
- Given no content matches the category and filters, when results render, then the page explains the empty state and offers valid refinements.
- Given a category is inactive, when a public user accesses it, then restricted content is not exposed.
- Given Admin changes category configuration, when approved, then the change is audited and clients use authoritative configuration.

## 6. Featured Collections

### 6.1 Purpose

Featured Collections shall provide curated discovery paths that highlight selected artworks, artists, themes, materials, occasions, or editorial narratives while preserving factual accuracy and artist agency.

### 6.2 Workflow

1. Authorized operations user creates or updates a collection through documented admin workflow.
2. System validates that collection content is eligible for public display.
3. Collection is previewed and submitted for approval where governance requires it.
4. Approved collection appears on homepage, collection index, category pages, artist pages, or product pages where configured.
5. User opens the collection and browses included public items.

### 6.3 Business Rules

- Featured Collections shall be curated or configured through documented governance.
- A collection shall show only public eligible artworks, artists, or approved editorial content.
- A collection shall not alter an artist's profile, artwork facts, price, availability, or cultural context.
- Collection attribution, sponsorship, or editorial ownership shall be disclosed where policy requires.
- Time-limited collections shall have documented start and end visibility behavior.
- Removal of a product or artist from public visibility shall remove or suppress that resource in any collection.

### 6.4 Validation

- Collection title, description, imagery, ordering, membership, visibility, schedule, and localization shall be validated before publication.
- Collection membership shall reject private, draft, suspended, rejected, or unavailable resources where policy excludes them.
- Collection links shall point only to public routes or documented fallback states.

### 6.5 Permissions

| Actor | Permissions |
| --- | --- |
| Guest | View public approved collections. |
| Customer | View public approved collections and perform permitted authenticated actions on included resources. |
| Artist | View collections; cannot place own work in a collection unless a documented workflow permits submission. |
| Moderator | Review assigned collection content or escalations within documented scope. |
| Admin | Create, edit, schedule, approve, archive, and audit collections where authorized. |

### 6.6 Edge Cases

- All collection items become unavailable.
- A collection includes an artist later suspended.
- Collection copy lacks a translation in one supported language.
- Collection end date passes while user is viewing it.
- Collection order references a deleted resource.

### 6.7 Acceptance Criteria

- Given a collection is public, when a user opens it, then only eligible public resources are shown.
- Given a collection item becomes restricted, when the collection is rendered, then the restricted item is omitted or replaced according to policy.
- Given collection configuration changes, when saved by an authorized Admin, then the action is audited.
- Given a collection has no eligible items, when rendered, then it shows approved empty or archived behavior.

## 7. Trending

### 7.1 Purpose

Trending shall help users discover currently active marketplace content based on approved, privacy-safe, non-deceptive signals.

### 7.2 Workflow

1. System computes trending candidates from documented public and privacy-safe marketplace signals.
2. System excludes restricted, unavailable, policy-blocked, or insufficiently qualified resources.
3. User views trending module or page.
4. User opens product, artist, category, collection, or search result from trending.
5. System records permitted analytics events according to the analytics plan.

### 7.3 Business Rules

- Trending shall use documented calculation windows, eligible signals, freshness rules, and tie-breakers.
- Trending shall not expose raw private behavior, individual customer actions, or small-cohort sensitive data.
- Trending shall not be described as real time unless the update interval supports that claim.
- Trending shall not include paid placement unless sponsorship disclosure is documented.
- Trending shall not allow fake scarcity or fabricated popularity claims.
- Trending may be disabled or replaced by curated content when data volume is insufficient.

### 7.4 Validation

- Trending input events shall be documented analytics events.
- Candidate resources shall be revalidated for public visibility before display.
- Sort labels and metadata shall match the actual ranking rule.
- Cache TTL and invalidation shall be documented.

### 7.5 Permissions

| Actor | Permissions |
| --- | --- |
| Guest | View public trending content. |
| Customer | View trending and perform permitted authenticated actions. |
| Artist | View public trending; view own aggregated insight only through artist analytics where approved. |
| Admin | View operational trending/reporting data where authorized and privacy-safe. |

### 7.6 Edge Cases

- Not enough events exist to compute a meaningful trend.
- A trending item is sold, hidden, or moderated after calculation.
- Trending data becomes stale during cache window.
- A coordinated abuse pattern attempts to manipulate trending.
- User asks why an item is trending and no explainability copy exists.

### 7.7 Acceptance Criteria

- Given trending content is displayed, when candidates are selected, then all candidates are eligible public resources.
- Given data volume is insufficient, when the module renders, then FANNAN shows approved fallback discovery content instead of fake trends.
- Given a resource becomes restricted, when trending is refreshed or opened, then the restricted resource is not accessible.
- Given abuse signals exceed documented thresholds, when detected, then affected signals are excluded or escalated according to policy.

## 8. Artist Pages

### 8.1 Purpose

Artist Pages shall provide a dignified public presence for approved Artists, presenting their identity, practice context, portfolio, available work, commission availability, follow action, and relevant marketplace trust signals.

### 8.2 Workflow

1. User opens an artist page from homepage, search, category, collection, product page, follow list, or direct public link.
2. System validates artist public visibility and profile eligibility.
3. Page displays approved artist profile content, public portfolio/listings, commission availability, follow state, and permitted contact or request actions.
4. Authenticated user follows, favorites artwork, starts commission request, or starts purchase path where eligible.
5. Artist updates profile or catalogue through artist dashboard; public page reflects authoritative approved state.

### 8.3 Business Rules

- Only approved public artist profiles shall be visible to Guests and Customers.
- Artist pages shall not fabricate biography, location, verification, cultural context, follower count, or availability.
- Artists with no public listings shall still have a dignified page if the profile is approved and public.
- Suspended, rejected, private, or under-review artist profiles shall follow documented hidden or restricted behavior.
- Follow, commission, and purchase actions shall be displayed only when permitted by authoritative state.
- Artist profile content shall respect localization, privacy, and cultural integrity rules.

### 8.4 Validation

- Public artist profile content shall be validated for required public presentation rules.
- Portfolio lists shall include only eligible public listings owned by the artist.
- Commission entry shall validate artist commission availability before rendering enabled actions.
- Follow state shall be retrieved from the authenticated user's authorized context.

### 8.5 Permissions

| Actor | Permissions |
| --- | --- |
| Guest | View public artist pages and public listings; account-required actions route to authentication. |
| Customer | View public artist pages, follow/unfollow, favorite artwork, start permitted purchase or commission request. |
| Artist | View own public page; edit own profile only through artist dashboard. |
| Moderator | Review assigned artist profile content through moderation workspace. |
| Admin | Govern artist visibility and escalations through documented admin workflows. |

### 8.6 Edge Cases

- Artist has no public listings.
- Artist profile becomes suspended while user is viewing it.
- Artist closes commissions while user is starting a request.
- Artist profile media fails to load.
- Follower count is below privacy threshold or not approved for public display.
- Artist profile has mixed Arabic and English content.

### 8.7 Acceptance Criteria

- Given a public approved Artist, when a user opens the artist page, then approved profile content and eligible public listings are shown.
- Given a Guest selects follow or commission request, when the action requires an account, then authentication is requested without exposing private data.
- Given an Artist is suspended, when a public user opens the page, then restricted content is not exposed.
- Given an Artist has no public listings, when the page renders, then the empty state remains accurate and dignified.

## 9. Product Pages

### 9.1 Purpose

Product Pages shall give users the complete, accurate, accessible information needed to evaluate artwork and decide whether to favorite, share, follow the artist, request a commission, add to cart, or purchase where permitted.

### 9.2 Workflow

1. User opens product page from discovery, search, category, collection, artist page, wishlist, related products, recently viewed, or shared link.
2. System validates product public visibility and availability state.
3. Page displays approved images, title, artist, medium, dimensions, year, edition information, materials, description, price, availability, shipping context, artist link, review summary where enabled, and permitted actions.
4. User may view gallery images, favorite, share, follow artist, add to cart, start checkout, report content, or request commission where eligible.
5. System revalidates price and availability before cart or checkout commitments.

### 9.3 Business Rules

- Product Pages shall display only approved public listing data.
- Required product facts shall not be fabricated or inferred by the client.
- Availability and purchase calls to action shall reflect authoritative state.
- Sold artwork may remain visible where policy supports provenance, but purchase actions shall be disabled.
- Product images shall preserve artist intent, reserve layout space, include appropriate alt text, and use optimized derivatives.
- Price, shipping implications, edition, dimensions, and material details shall be easy to locate.
- Product Pages shall support SEO metadata without exposing private or internal content.

### 9.4 Validation

- Product identifier and route shall resolve to an eligible public listing or documented not-found/restricted state.
- Action controls shall validate user role, listing state, price, availability, cart rules, and commission rules before mutation.
- Image gallery shall validate supported media, ordering, primary image, alt text strategy, and fallback behavior.
- Review summary shall include only approved reviews.

### 9.5 Permissions

| Actor | Permissions |
| --- | --- |
| Guest | View public product page, artist link, public reviews, share links, and authentication prompts for account-required actions. |
| Customer | Favorite, unfavorite, add eligible item to cart, start checkout, submit review if eligible, report content, follow artist, or start commission request where permitted. |
| Artist | View public product page; manage own listing only through artist dashboard; cannot edit from public page unless routed to authorized dashboard context. |
| Moderator | Review reported or assigned product content through moderation workspace. |
| Admin | Govern product visibility, escalations, and configuration through documented admin workflows. |

### 9.6 Edge Cases

- Product becomes unavailable while user is viewing it.
- Product has missing optional metadata.
- Required metadata is absent due to legacy or migration issue.
- Images fail to load or derivative generation is delayed.
- Product is removed, hidden, sold, or suspended after a shared link was created.
- Currency or shipping destination is unsupported.

### 9.7 Acceptance Criteria

- Given a public product page, when it renders, then all available buyer-relevant facts are shown accurately from authoritative data.
- Given a product is sold or unavailable, when the page renders, then purchase actions are disabled and state is clear.
- Given a Customer favorites or adds the item to cart, when state changes, then the API validates current eligibility before success.
- Given image loading fails, when the gallery renders, then accessible fallback content and recovery behavior are available.

## 10. Wishlist

### 10.1 Purpose

Wishlist shall allow authenticated Customers and Artists acting as Customers to save artworks for later evaluation, comparison, notification, and purchase intent without creating a public social signal.

### 10.2 Workflow

1. Customer selects favorite/save on an eligible artwork.
2. System validates authentication, product visibility, and duplicate state.
3. Artwork is added to the user's wishlist.
4. Customer views wishlist in customer dashboard or saved content surface.
5. Customer removes artwork, opens detail, starts purchase, follows artist, or manages relevant notification preferences.

### 10.3 Business Rules

- Wishlist is private to the owning Customer unless a future sharing specification is approved.
- Guests cannot create persisted wishlist entries; safe intent may be preserved through authentication where policy permits.
- Duplicate saves shall be idempotent and show saved state.
- Removed, hidden, suspended, or unavailable artworks shall be handled according to policy with accurate labeling.
- Wishlist notifications shall respect notification preferences and rate limits.
- Artists may not view individual customer wishlist entries unless an approved privacy-safe aggregate metric is provided.

### 10.4 Validation

- User authentication and ownership shall be validated server-side.
- Product eligibility shall be checked before saving.
- Wishlist remove operations shall validate ownership of the saved relationship.
- Notification preferences shall be validated before enabling wishlist-triggered alerts.

### 10.5 Permissions

| Actor | Permissions |
| --- | --- |
| Guest | Prompted to authenticate when attempting to save; no persisted private state unless documented. |
| Customer | Add, remove, view, sort, and act on own wishlist items. |
| Artist | Same as Customer for personal buyer activity; may view only privacy-safe aggregate saved-work insights for own artworks where approved. |
| Support Agent | View wishlist only if required by an assigned support case and policy permits; otherwise denied. |
| Admin | Access only through documented privacy-governed support or audit workflow. |

### 10.6 Edge Cases

- User saves the same artwork multiple times.
- Artwork becomes unavailable after being saved.
- User removes an item accidentally.
- Wishlist is empty.
- User signs in after attempting to save as Guest.
- Account deletion request occurs while wishlist exists.

### 10.7 Acceptance Criteria

- Given an authenticated Customer saves an eligible artwork, when the action succeeds, then the artwork appears in that user's wishlist exactly once.
- Given a Guest attempts to save, when authentication is required, then the user sees a clear sign-in/sign-up path.
- Given a saved artwork becomes unavailable, when wishlist renders, then the state is accurately labeled or handled by policy.
- Given a Customer removes a saved item, when the action succeeds, then only that Customer's wishlist changes.

## 11. Reviews

### 11.1 Purpose

Reviews shall provide trustworthy post-purchase feedback for artworks and artists while preventing fake, abusive, private, or policy-violating content from damaging marketplace trust.

### 11.2 Workflow

1. Eligible Customer receives review opportunity after documented purchase and delivery state.
2. Customer submits rating and review content within the approved review window.
3. System validates purchase eligibility, review window, content rules, and duplicate state.
4. Review enters approved publication or moderation workflow.
5. Public users view approved reviews and rating summary on product page where enabled.
6. Customer may edit or delete their review within documented rules.
7. Artist may view reviews for own artworks and report policy concerns.
8. Moderator/Admin reviews reported or queued reviews.

### 11.3 Business Rules

- Only verified eligible purchasers may submit reviews.
- Review window, rating scale, edit window, delete behavior, and artist response behavior shall be documented before implementation.
- Reviews shall not expose private transaction details, contact information, harassment, prohibited content, or unsupported claims.
- Public review summaries shall show review count alongside average rating.
- Removing or rejecting a review shall update public rating summaries according to documented calculation rules.
- Review moderation decisions shall be audited and reasons exposed only according to policy.

### 11.4 Validation

- Purchase eligibility, delivery status, review window, duplicate review state, rating value, content length, and prohibited content checks shall be server-validated.
- Review edits shall validate author ownership and current moderation state.
- Review display shall include only approved public reviews.
- Reports against reviews shall validate reporter identity where authentication is required and prevent duplicate abuse.

### 11.5 Permissions

| Actor | Permissions |
| --- | --- |
| Guest | View approved public reviews and summaries where enabled. |
| Customer | Submit, edit, delete, and report own eligible review according to policy; report other reviews where permitted. |
| Artist | View reviews for own artwork and report policy issues; cannot alter customer review content. |
| Moderator | Review assigned review moderation cases and apply documented decisions. |
| Admin | Govern review moderation, escalations, and audit visibility. |

### 11.6 Edge Cases

- Customer attempts to review without purchase.
- Review window has expired.
- Review contains prohibited content or private data.
- Review is reported while Customer tries to edit it.
- Review removal changes the average rating.
- Artwork is deleted, hidden, or sold after review submission.

### 11.7 Acceptance Criteria

- Given a Customer did not complete an eligible purchase, when they attempt to review, then submission is denied.
- Given an eligible review is submitted, when it passes validation and moderation rules, then it becomes visible according to policy.
- Given a review is rejected or removed, when product page renders, then public summary excludes that review.
- Given an Artist reports a review, when submitted, then a moderation case is created or updated according to policy.

## 12. Recommendations

### 12.1 Purpose

Recommendations shall help users continue discovery through transparent, rule-based, privacy-safe suggestions such as similar category, same artist, same medium, curated collection membership, or editorial fallback. AI-generated or opaque personalized recommendations are out of MVP unless separately approved.

### 12.2 Workflow

1. User views a product, artist, category, collection, wishlist, or empty state.
2. System selects recommendation candidates using documented deterministic rules.
3. System filters candidates for public eligibility, availability where required, content policy, and privacy constraints.
4. User opens a recommended product, artist, category, or collection.
5. System records permitted analytics events without exposing private recommendation inputs.

### 12.3 Business Rules

- Recommendation rules shall be documented and testable.
- Recommendations shall not claim personalization unless a privacy and consent model is approved.
- Recommendations shall not use generative AI, sensitive personal attributes, private wishlist contents, private order data, or unapproved profiling for MVP.
- Recommendations shall exclude the current product where duplicate display would confuse the user.
- Recommendation modules shall disclose or label their basis in plain language where useful, such as "More from this artist" or "Similar medium".
- Sponsored recommendations require separate disclosure and ranking policy.

### 12.4 Validation

- Candidate resources shall be public eligible resources at render time.
- Recommendation source type shall be an approved rule.
- Candidate list shall be bounded, deduplicated, and ordered according to documented tie-breakers.
- Cache behavior shall avoid cross-user leakage.

### 12.5 Permissions

| Actor | Permissions |
| --- | --- |
| Guest | View public non-personal recommendations. |
| Customer | View public recommendations; may receive account-aware suggestions only after privacy, consent, and ranking rules are approved. |
| Artist | View public recommendations; cannot force placement except through documented catalogue/collection workflows. |
| Admin | Configure approved recommendation rules only through governed settings. |

### 12.6 Edge Cases

- No eligible candidates exist.
- Current product appears in the candidate list.
- Candidate becomes restricted after recommendation generation.
- User has opted out of analytics or personalization.
- Recommendation could reinforce only one artist and reduce marketplace diversity.

### 12.7 Acceptance Criteria

- Given recommendations are shown, when rendered, then every item is public and eligible.
- Given no eligible candidates exist, when the module renders, then it hides or shows approved empty fallback.
- Given a recommendation label is displayed, when reviewed, then the label matches the documented rule.
- Given AI-generated recommendations are proposed, when MVP scope is checked, then implementation is blocked until a separate approved specification exists.

### 13.4 Validation

- Collection filters and sorts shall use documented search capabilities.

### 13.5 Permissions

| Customer | View collections and perform permitted authenticated actions on resources. |
| Artist | View collections; may see own work included publicly; cannot edit collection membership unless a documented workflow exists. |
| Moderator | Review assigned collection-related content or reports. |
| Admin | Manage collection lifecycle through documented audited workflow. |

### 13.6 Edge Cases

- Collection is expired.

- Collection contains a resource later removed by moderation.
- Collection link is shared after archive.
- Collection has inconsistent localization.

### 13.7 Acceptance Criteria

- Given a public collection is active, when a user opens it, then the collection renders with approved content and eligible resources.
- Given a collection expires, when opened after expiry, then documented archive, redirect, or not-found behavior occurs.
- Given an item is removed from public visibility, when the collection renders, then that item is not shown.
- Given collection management occurs, when saved, then changes are authorized and audited.

## 14. Commission Requests

### 14.1 Purpose

Commission Requests shall give Customers a structured, private, artist-controlled path to request custom work and give Artists a governed way to accept, decline, request more information, and manage request status.

### 14.2 Workflow

1. Customer opens commission entry from artist page, product page, dashboard, or approved marketplace prompt.
2. System validates authentication and artist commission availability.
3. Customer completes documented request information such as project description, budget, timeline, and reference materials where approved by commission specification.
4. System validates request completeness, policy constraints, attachment rules, budget rules, and rate limits.
5. Request is submitted to the Artist and enters documented initial state.
6. Artist reviews request in artist dashboard and accepts, declines with reason, requests more information, or updates status.
7. Customer tracks status in customer dashboard and receives notifications.
8. Disputes or policy issues route to Support Agent or Admin according to documented escalation workflow.

### 14.3 Business Rules

- Commission requests require authentication.
- Customers may submit requests only to Artists currently open for commissions.
- Commission request details are private to authorized Customer, Artist, and scoped operations roles.
- Artists control whether they are accepting new commission requests.
- Commission states, payment deposits, milestones, cancellation, refunds, dispute handling, and response service levels shall be documented before implementation.
- Platform-mediated communication may be used only inside approved commission workflow and is not a general direct-message system.
- Reference materials and messages shall follow content, copyright, privacy, and attachment rules.

### 14.4 Validation

- Authentication, Customer ownership, Artist eligibility, commission availability, request requiredness, budget constraints, timeline constraints, attachment type/size, and prohibited content shall be validated server-side.
- State transitions shall follow the documented commission state machine.
- Artist responses shall validate ownership of the incoming request and current state.
- Customer access shall validate ownership of submitted request.

### 14.5 Permissions

| Actor | Permissions |
| --- | --- |
| Guest | View commission availability where public; prompted to authenticate to submit. |
| Customer | Submit, view, track, and communicate about own commission requests. |
| Artist | View and manage incoming commission requests assigned to them. |
| Support Agent | Access assigned commission cases only with minimum necessary context. |
| Admin | Monitor disputes, escalations, and governed interventions where authorized. |

### 14.6 Edge Cases

- Artist closes commissions while Customer is drafting.
- Budget is below Artist minimum or unsupported by policy.
- Request includes prohibited or copyrighted reference material.
- Artist is unresponsive past service window.
- Customer asks to change scope mid-process.
- Commission has payment or refund questions before payment rules are approved.

### 14.7 Acceptance Criteria

- Given an Artist is open for commissions, when an authenticated Customer submits a valid request, then the request is created in the documented initial state and the Artist is notified.
- Given an Artist is closed for commissions, when a Customer attempts to submit, then submission is blocked with clear explanation.
- Given a user tries to access another user's commission request, when authorization runs, then access is denied.
- Given an Artist changes request status, when the transition is valid, then Customer status and notifications update from authoritative state.

## 15. Follow Artist

### 15.1 Purpose

Follow Artist shall let Customers build an ongoing relationship with Artists and receive approved updates without turning FANNAN into a public social network.

### 15.2 Workflow

1. Customer selects follow on an eligible public Artist page or artist card.
2. System validates authentication, artist visibility, duplicate state, and follow limit rules.
3. Follow relationship is created and UI reflects following state.
4. Customer views followed artists in dashboard or return-discovery surfaces.
5. Customer unfollows when desired.
6. Artist sees privacy-safe aggregate follower insight where approved.

### 15.3 Business Rules

- Guests cannot create persisted follows; safe intent may be preserved through authentication.
- Customers and Artists acting as Customers may follow public Artists.
- Follow state is private to the Customer unless a future public social specification is approved.
- Artist-facing follower insight shall be aggregate or privacy-safe only.
- Follow notifications shall respect user preferences and rate limits.
- Suspended or non-public Artists cannot be newly followed.

### 15.4 Validation

- Authentication and Customer ownership shall be validated server-side.
- Artist public eligibility shall be validated before follow.
- Duplicate follow and unfollow actions shall be idempotent.
- Follow limit and abuse controls shall be enforced by the API.

### 15.5 Permissions

| Actor | Permissions |
| --- | --- |
| Guest | Prompted to authenticate when attempting to follow. |
| Customer | Follow, unfollow, and view own followed artists. |
| Artist | Same as Customer for personal buyer activity; view approved aggregate follower metrics for own artist profile. |
| Support Agent | Access follow data only if required by assigned support case and policy permits. |
| Admin | Access aggregate or case-scoped follow data only through documented governed workflow. |

### 15.6 Edge Cases

- User follows an Artist already followed.
- Artist is suspended after being followed.
- User reaches follow limit.
- User unfollows accidentally.
- Follow notification would violate recipient preferences.
- Artist tries to identify individual followers where privacy policy does not permit it.

### 15.7 Acceptance Criteria

- Given an authenticated Customer follows a public Artist, when the action succeeds, then the Customer's follow state changes to following.
- Given a Guest attempts to follow, when authentication is required, then the user receives a clear authentication path.
- Given an Artist becomes non-public, when followed list renders, then the Artist is hidden or labeled according to policy.
- Given an Artist views follower insight, when privacy thresholds are not met, then individual private data is not exposed.

## 16. Recently Viewed

### 16.1 Purpose

Recently Viewed shall help users return to artwork or artist pages they inspected, while respecting privacy, consent, shared devices, and public-private boundaries.

### 16.2 Workflow

1. User views eligible public product or artist page.
2. System records recent-view signal according to consent and authentication rules.
3. User opens homepage, product page, dashboard, or recently viewed surface.
4. System displays eligible recently viewed resources in reverse chronological order or documented order.
5. User removes or clears recently viewed history where account-level storage is enabled.

### 16.3 Business Rules

- Recently viewed data shall not expose private browsing history to other users.
- For Guests, recently viewed may be session/local-device only and shall not create authenticated profile data.
- For authenticated Customers, account-level recently viewed requires documented privacy, retention, and deletion rules.
- Recently viewed shall include only resources still eligible for the user's context.
- Recently viewed shall not be used for personalized recommendations unless consent and recommendation rules are approved.
- Shared-device risks shall be addressed through sign-out/session behavior and optional clearing controls.

### 16.4 Validation

- Viewed resource eligibility shall be validated before display.
- Recently viewed storage shall validate consent, retention, and account ownership.
- Clear/remove actions shall validate ownership.
- Private or restricted resources shall be suppressed.

### 16.5 Permissions

| Actor | Permissions |
| --- | --- |

| Customer | View and clear own recently viewed history where enabled. |
| Artist | Same as Customer for personal buyer activity; cannot see individual viewers of own work. |
| Support Agent | No access unless explicitly required by privacy-approved support workflow. |
| Admin | Aggregate analytics only where privacy-safe; no arbitrary user browsing history access. |

### 16.6 Edge Cases

- User is on a shared device.
- User signs in after browsing as Guest.
- Recently viewed item becomes hidden, sold, or suspended.
- Browser blocks local storage.
- User requests account deletion or data export.

### 16.7 Acceptance Criteria

- Given recently viewed is enabled, when a user views an eligible product, then it can appear in their own recent history according to storage policy.
- Given a resource becomes restricted, when recently viewed renders, then the resource is omitted or labeled according to policy.
- Given a user clears recent history, when the action succeeds, then the surface no longer displays cleared items for that user/session.
- Given an Artist views analytics, when recent-view data exists, then individual viewer identity is not exposed.

## 17. Related Products

### 17.1 Purpose

Related Products shall help users continue evaluating relevant artwork from a product page using documented public catalogue relationships.

### 17.2 Workflow

1. User views a product page.
2. System selects related candidates based on approved rules such as same artist, same category, same medium, same collection, price band, or editorial configuration.
3. System filters candidates for public eligibility and deduplicates the current product.
4. User opens a related product.

### 17.3 Business Rules

- Related Products shall use documented, testable, non-deceptive rules.
- Related Products shall include only public eligible products.
- Current product shall not appear in its own related list.
- Related Products shall not imply availability unless the product is currently available.
- If related products are sponsored, disclosure and ranking policy must be approved before release.
- Related Products shall revalidate candidate visibility at render time or within documented cache TTL.

### 17.4 Validation

- Product eligibility, relationship rule, candidate count, deduplication, sort order, and cache scope shall be validated.
- Related product card actions shall use the same validation as product listing actions.
- Candidate resources shall exclude restricted, draft, under-review, or suspended content.

### 17.5 Permissions

### 17.6 Edge Cases

- Current product is sold or hidden.

### 17.7 Acceptance Criteria

- Given no eligible related products exist, when the page renders, then the module is hidden or shows approved fallback.
- Given a related product is selected, when opened, then its current authoritative state is shown.
- Given related logic changes, when reviewed, then the rule is documented and testable.

## 18. Product Sharing

### 18.1 Purpose

Product Sharing shall let users share public product and artist discovery links through platform-supported or browser-supported mechanisms while preserving accurate previews, privacy, and content eligibility.

### 18.2 Workflow

1. User selects share on a public product, artist, collection, category, or approved marketplace page.
2. System prepares canonical public URL and approved share metadata.
3. If native share is available, the client opens the platform share sheet; otherwise it offers copy-link behavior.
4. Recipient opens shared link.
5. System validates current public eligibility and renders current authoritative state or documented fallback.

### 18.3 Business Rules

- Sharing shall be limited to public eligible resources.
- Shared metadata shall not expose private notes, buyer activity, wishlist status, draft content, internal moderation data, or personalized state.
- Shared links shall use canonical URLs.
- Share previews shall use approved public title, description, and image metadata.
- Product sharing shall not generate affiliate, referral, or tracking behavior unless separately documented and consented.
- If a resource becomes unavailable, the shared link shall show accurate current state.

### 18.4 Validation

- Resource public eligibility shall be validated before showing share controls.
- Generated share URL shall be canonical and safe.
- Metadata shall be drawn from approved public fields only.
- Copy-link success/failure shall provide accessible feedback.

### 18.5 Permissions

| Actor | Permissions |
| --- | --- |
| Guest | Share public eligible resources. |
| Customer | Share public eligible resources; private wishlist or order context is never included. |
| Artist | Share own or other public eligible resources; private dashboard preview links require separate protected sharing rules. |
| Moderator | Share controls in public marketplace only; moderation case sharing is forbidden unless internal workflow documents it. |
| Admin | Share public resources; internal links remain governed by staff access controls. |

### 18.6 Edge Cases

- Browser native share API is unavailable.
- Clipboard permission is denied.
- Shared product is later hidden, sold, or suspended.
- Share preview image fails.
- Arabic title appears in an English interface or vice versa.
- User attempts to share a draft preview.

### 18.7 Acceptance Criteria

- Given a public product page, when user selects share, then the shared URL is canonical and contains no private context.
- Given native share is unavailable, when user selects share, then copy-link fallback is available.
- Given a shared resource becomes restricted, when the recipient opens the link, then restricted content is not exposed.
- Given share metadata is generated, when audited, then it uses only approved public fields.

## 19. Reporting

### 19.1 Purpose

Reporting shall allow users and staff to flag marketplace content, reviews, profiles, commission messages, or suspicious activity for governed moderation or support review without exposing private case details publicly.

### 19.2 Workflow

1. User selects report on eligible marketplace content or communication surface.
2. System displays report form with approved reason options and optional detail guidance.
3. User submits report.
4. System validates actor eligibility, target eligibility, reason, abuse limits, and required detail.
5. Report creates or updates a moderation/support case according to policy.
6. Moderator, Support Agent, or Admin reviews the case within authorized workspace.
7. System communicates only permitted status or outcome to affected parties.

### 19.3 Business Rules

- Reportable surfaces shall be documented before implementation.
- Report reason taxonomy shall be approved by trust, safety, legal, and product owners.
- Reports shall not become public content.
- Reporters shall not receive private moderation rationale unless policy permits.
- Duplicate reports may be merged or rate-limited.
- Malicious or abusive reporting shall be rate-limited and escalated where policy requires.
- Staff actions on reports shall be audited.
- Reporting shall not replace emergency, legal, privacy, payment, or security escalation procedures.

### 19.4 Validation

- Target resource, reporter identity where required, reason, optional details, attachments, duplicate report state, and rate limits shall be validated.
- Guest reporting may be allowed only for public content if abuse controls and contact rules are documented.
- Staff case access shall validate assignment, scope, role, and current state.
- Report outcomes shall follow documented moderation/support state transitions.

### 19.5 Permissions

| Actor | Permissions |
| --- | --- |
| Guest | Report public content only where policy permits; may need contact or anti-abuse verification. |
| Customer | Report public content, reviews, and own commission interactions where supported. |
| Artist | Report reviews, public content, and own commission interactions where supported. |
| Moderator | Review assigned reports and apply documented content decisions. |
| Support Agent | Handle assigned support reports where not moderation/security/payment restricted. |
| Admin | Resolve escalations, govern report policy, and audit staff actions. |

### 19.6 Edge Cases

- Same user reports the same target repeatedly.
- Reported content is deleted before review.
- Report involves payment, privacy, legal, or security issue.
- Reporter is the content owner.
- Moderator has conflict of interest.
- Report details include sensitive personal data.

### 19.7 Acceptance Criteria

- Given a user submits a valid report, when validation succeeds, then a governed case is created or updated.
- Given a report target is no longer available, when the case is reviewed, then available historical context follows retention policy.
- Given a staff user reviews a report, when they act, then authorization, assignment, decision reason, and audit rules are enforced.
- Given a reporter requests outcome details, when policy restricts disclosure, then private moderation details are not exposed.
