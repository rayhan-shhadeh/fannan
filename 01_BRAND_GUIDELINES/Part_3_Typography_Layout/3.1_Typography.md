# FANNAN Typography

Typography gives FANNAN its quiet confidence: editorial enough to honour the work of Palestinian artists, and clear enough to make discovery and purchasing feel effortless. The system is intentionally restrained. Generous scale, calm rhythm, and careful Arabic shaping allow artwork and craft stories to lead.

## Principles

- **Let the work speak.** Use display sizes sparingly—on campaign moments, artist stories, and key editorial introductions—not as general decoration.
- **Design bilingually from the start.** Arabic is not a fallback. Arabic and Latin content must receive equivalent hierarchy, spacing, and prominence.
- **Prioritise reading comfort.** Use relaxed line height for descriptions and editorial text; keep interface labels compact and decisive.
- **Use contrast through scale and weight.** Avoid relying on all caps, excessive tracking, or many font styles to create emphasis.
- **Respect direction.** Arabic content is RTL; numbers, prices, and mixed-language strings need deliberate bidirectional testing.

## Typeface recommendation and pairing

| Role | Arabic | Latin | Why |
| --- | --- | --- | --- |
| Display / editorial | **Noto Kufi Arabic** | **DM Sans** | Geometric Arabic character paired with a warm, contemporary Latin voice. Use for expressive titles only. |
| UI, body, and supporting text | **Noto Sans Arabic** | **DM Sans** | Highly legible, neutral, and compatible across product interfaces and long-form reading. |
| Code | System monospace | System monospace | Clear differentiation for technical details, order metadata, and developer surfaces. |

Use the display pairing for Arabic-first and Latin-first content alike: `Noto Kufi Arabic` renders Arabic glyphs and `DM Sans` renders Latin glyphs. Use the UI pairing for all body copy, labels, navigation, and controls. Do not substitute a Latin serif for Arabic display text; it creates unequal visual voices across languages.

### Fallback stacks

| Context | Stack |
| --- | --- |
| Display | `"Noto Kufi Arabic", "DM Sans", Tahoma, Arial, sans-serif` |
| UI / body | `"Noto Sans Arabic", "DM Sans", Tahoma, Arial, sans-serif` |
| Code | `ui-monospace, "SFMono-Regular", Consolas, "Liberation Mono", monospace` |

`Tahoma` is retained because it provides broadly available Arabic coverage. Always place the intended Arabic family before the intended Latin family so a mixed string resolves naturally.

## Variable fonts

Use the variable versions of Noto Sans Arabic, Noto Kufi Arabic, and DM Sans where available. A variable font reduces requests and lets the system use intentional intermediate weights—particularly `450` for quiet supporting text or `550` for a subtle emphasis—without inventing a new type style.

- Request only the weight range used by the product (normally `400–700`); avoid loading every axis by default.
- Use `wght` for weight. Do not animate weight on hover or during content changes; it can cause reflow and distract from art.
- Use optical sizing only after visual QA in Arabic and Latin. If enabled, keep it on (`font-optical-sizing: auto`) rather than setting arbitrary values.
- Do not synthesise bold or italic. Supply a real style or fall back to a semantic weight.

## Font loading strategy

1. Self-host production font files when possible for reliable performance, privacy control, and explicit subsetting. Otherwise use Google Fonts with a preconnect to `fonts.gstatic.com`.
2. Subset by script: load Latin early for a Latin-only route; load Arabic plus Latin for bilingual or Arabic routes. Never ship Arabic glyph payloads only after Arabic text appears.
3. Preload the single most important above-the-fold face and weight—usually UI `400` or display `600`—then load remaining weights normally.
4. Use `font-display: swap` for UI/body text. Use `optional` for non-critical campaign display faces if layout remains acceptable with the fallback.
5. Match fallback metrics where practical and reserve stable line heights to reduce layout shift. Test slow 3G and cached-return visits.

Useful CSS for a self-hosted variable UI face:

```css
@font-face {
  font-family: "Noto Sans Arabic";
  src: url("/fonts/noto-sans-arabic-variable.woff2") format("woff2");
  font-weight: 400 700;
  font-style: normal;
  font-display: swap;
}
```

In Tailwind, expose the three stacks as semantic families (`display`, `sans`, and `mono`) and map the named styles below to semantic utilities. In React, use those named styles through reusable text primitives rather than arbitrary one-off font sizes.

## Responsive approach

The system has three design ranges:

| Range | Viewport | Intent |
| --- | --- | --- |
| Mobile | `< 640px` | Preserve hierarchy without oversized wrapping; prioritise scanability. |
| Tablet | `640–1023px` | Add breathing room as columns and imagery widen. |
| Desktop | `≥ 1024px` | Full editorial scale for pages with generous measure. |

Use the mobile value as the default Tailwind utility, the tablet value at `sm`, and the desktop value at `lg`. Sizes are fixed tokens, not fluid interpolation; this makes Arabic/Latin line wrapping predictable. Keep body text at a comfortable measure: approximately 45–75 Latin characters or 22–38 Arabic characters per line, depending on content.

## Typography hierarchy

All values are in `px`; line height is shown as a unitless ratio so it scales correctly. Letter spacing is in `em`. `Normal` means `0em`.

## Applying the system

### Content rules

- Use a single display style per viewport section. Pair it with Body Large or Body XL, rather than another large heading.
- Use Body Medium as the default component text. Body Small and Caption must never contain essential instructions, legal terms, or error messages.
- Make action labels verb-first and concise. Keep labels in sentence case for Latin; Arabic has no equivalent uppercase convention.
- Keep an Arabic phrase intact when possible. Avoid manual line breaks inside connected Arabic words or between a number and its unit/price.
- For a bilingual title, prefer separate language blocks with appropriate `lang` and `dir` attributes rather than forcing both scripts into one visual line.

### CSS helpers

Use logical alignment so the same component works in both directions:

```css
.fannan-body {
  font-family: "Noto Sans Arabic", "DM Sans", Tahoma, Arial, sans-serif;
  font-weight: 400;
  line-height: 1.55;
  text-align: start;
}

.fannan-display {
  font-family: "Noto Kufi Arabic", "DM Sans", Tahoma, Arial, sans-serif;
  font-weight: 600;
  line-height: 1.12;
  letter-spacing: -0.02em;
}

[lang="ar"] .fannan-display {
  letter-spacing: 0;
}
```

For Tailwind/React implementation, keep typography names stable even if the underlying size changes. A `Text` primitive should accept semantic variants such as `body-medium`, `label`, and `caption`; a `Heading` primitive should own the semantic level (`h1`–`h6`) separately from its visual variant. This prevents a heading that looks like H3 from accidentally becoming an inaccessible paragraph.

## Accessibility and QA

- Maintain WCAG 2.2 AA contrast: at least **4.5:1** for normal text and **3:1** for large text (at least 24px regular or 18.67px/14pt bold). FANNAN’s warm neutrals need contrast testing over imagery and tinted surfaces.
- Do not use text smaller than 12px. Caption text must remain supplementary; use Body Small or larger for information users need to act on.
- Preserve browser zoom to 200% and text-only zoom without clipping, overlap, or loss of controls. Avoid fixed-height text containers.
- Use real HTML headings in descending order, meaningful button labels, and associated form labels. Typography classes do not provide semantics.
- Set `lang="ar" dir="rtl"` for Arabic content and the correct `lang` for Latin content. Test mixed Arabic/English product names, Western numerals, prices, punctuation, and screen-reader pronunciation.
- Never convey selected, error, or disabled state through weight or colour alone; pair it with a clear label, icon, border, or message.
- Ensure focus indicators remain visible at every type scale. Do not remove outlines around compact navigation or text buttons.
- Test the loaded and fallback states, including Arabic shaping, at mobile width and at 200% zoom. A fallback that causes a line to wrap differently is a layout defect, not merely a visual difference.

## Design review checklist

- Is the chosen style semantic and appropriate to the content’s importance?
- Does Arabic receive the same hierarchy and visual space as Latin?
- Is the smallest essential text Body Small or larger?
- Are line length, contrast, direction, and zoom behaviour verified?
- Is the component using a named token rather than an arbitrary font size or weight?
