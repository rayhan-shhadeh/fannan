# FANNAN Accessibility

FANNAN is designed to be usable by everyone who discovers, buys, and sells Palestinian art. This specification targets **WCAG 2.2 Level AA** for all customer-facing and artist-dashboard experiences. Accessibility is a product requirement, not a finishing pass.

## Principles

- Build with semantic HTML first; add ARIA only when native semantics cannot express the interaction.
- Keep information, actions, and status changes available to keyboard and assistive-technology users.
- Do not convey meaning through colour, motion, position, or iconography alone.
- Support Arabic and English equally, including correct text direction and meaningful language changes.
- Test each reusable component before it enters the design system; accessibility defects compound quickly.

## Baseline Requirements

| Area | FANNAN standard |
| --- | --- |
| Conformance | WCAG 2.2 AA minimum; do not knowingly ship Level A failures. |
| Language | Set `lang` on the document and on inline language changes. Use `dir="rtl"` for Arabic interfaces and content where appropriate. |
| Reflow | Content must work at 320 CSS px wide with no two-dimensional scrolling, except for essential data tables or galleries. |
| Zoom | Support browser zoom to 200% without lost content or functionality; support text-only zoom to 200%. |
| Input | Every operation works with keyboard, touch, mouse, and assistive technology where the platform supports them. |
| Status | Loading, validation, save, cart, and upload states are announced or otherwise perceivable. |
| Target size | Interactive controls provide at least 24 × 24 CSS px targets; use 44 × 44 px as the FANNAN default for touch-first controls. |

## Typography

Typography should remain legible, calm, and culturally respectful in both Latin and Arabic scripts.

| Requirement | Standard |
| --- | --- |
| Body text | Use a minimum of 16 px for primary reading text. Do not make essential text smaller than 14 px. |
| Line height | Use at least 1.5 for body copy; Arabic body text generally benefits from 1.6–1.8. |
| Paragraph spacing | Use spacing between paragraphs rather than relying only on indentation. |
| Line length | Keep long-form text near 45–75 Latin characters or 30–45 Arabic characters per line. |
| Weight | Use regular or medium for paragraphs; reserve thin weights for decorative, non-essential text. |
| Alignment | Prefer start alignment. Avoid justified body copy, which creates uneven word spacing, particularly in Arabic. |
| Text resizing | Use relative units for type and layout. Never disable user scaling or pinch zoom. |
| Text in images | Do not embed essential text in artwork, banners, or product imagery. Provide equivalent HTML text. |

Use real heading elements in sequence. A visual heading must not be a generic `div` or `span`; do not choose heading levels solely for appearance.

### Bilingual Content

- Match font families and scale tokens approved in the Typography specification; verify Arabic glyph coverage before release.
- Let the browser manage bidi text where possible. Set direction on the smallest meaningful container, not individual words.
- Keep numerals, prices, dates, and mixed-language product names understandable in both LTR and RTL contexts.
- Do not use left/right-only instructions. Use logical terms such as “start”, “end”, “previous”, and “next”.

## Colour Contrast

Warm, understated colour must still provide clear contrast. Verify actual foreground/background pairs, including translucent layers and image overlays.

| Content | Minimum contrast | Notes |
| --- | --- | --- |
| Normal text under 24 px regular / 18.66 px bold | 4.5:1 | Includes placeholder text, labels, helper text, and text over imagery. |
| Large text | 3:1 | Large means at least 24 px regular or 18.66 px bold. |
| Icons and visual controls | 3:1 | Required for boundaries, icons, selected states, and focus indicators needed to operate the UI. |
| Non-essential decoration | No ratio | Must not carry information or be the only state indicator. |
| Disabled controls | No fixed ratio | Clearly communicate why a control is unavailable where relevant; do not make disabled state the only way to prevent an invalid action. |

- Pair every colour cue with text, an icon, pattern, or state label. Sale status, errors, inventory, and chart series require more than colour.
- Maintain contrast in hover, pressed, focus, selected, dark-mode, and high-contrast operating-system modes.
- Avoid placing text directly over detailed artwork. Use a solid or sufficiently opaque surface behind essential text.
- Treat placeholder text as supplemental; labels remain visible after entry.

## Keyboard Navigation

All interactive elements must be reachable and operable with a keyboard.

| Requirement | Standard |
| --- | --- |
| Tab order | Follow the visual and logical reading order. Do not use positive `tabindex`. |
| Skip link | Provide a visible-on-focus “Skip to main content” link as the first focusable item. |
| Native controls | Use links for navigation and buttons for actions. Do not imitate either with clickable generic elements. |
| Custom controls | Implement expected keyboard patterns from the WAI-ARIA Authoring Practices, including arrow keys where applicable. |
| No trap | Users can move focus into and out of every non-modal component. |
| No keyboard trap | A modal may contain focus temporarily, but must offer a clear close action and return focus to its invoker. |
| Visible focus | The current focus location is always visible and never hidden behind sticky UI. |
| Shortcuts | Single-key shortcuts can be turned off, remapped, or only work while the target control has focus. |

Recommended baseline:

```css
:focus-visible {
  outline: 3px solid var(--color-focus-ring);
  outline-offset: 3px;
}

:focus:not(:focus-visible) {
  outline: none;
}
```

Do not remove focus outlines without providing an equally visible replacement. Ensure the ring has at least 3:1 contrast against adjacent colours.

## Focus States

| State | Behaviour |
| --- | --- |
| Keyboard focus | 3 px ring with 2–4 px offset; visible on every interactive element, including icon-only buttons and cards acting as links. |
| Mouse interaction | Do not require a focus ring after pointer use if `:focus-visible` is supported, but retain programmatic focus visibility. |
| Focus on validation error | Move focus to an error summary after submit; link each summary item to the invalid field. |
| Focus after modal close | Return focus to the control that opened the modal, unless that control no longer exists. |
| Focus after route change | Move focus to the page `<main>` heading or main region; announce meaningful title changes. |
| Sticky elements | Offset scrolling so focus targets are not obscured by the sticky header. |

## ARIA and Semantic Structure

ARIA supplements semantic HTML; it never repairs a non-semantic interaction by itself.

| Use case | Preferred approach |
| --- | --- |
| Page landmarks | Use `header`, `nav`, `main`, `aside`, and `footer`; label multiple navigation regions distinctly. |
| Buttons | Use `<button type="button">`; provide an accessible name for icon-only controls with visible text or `aria-label`. |
| Links | Use `<a>` with a valid destination. Do not use `role="link"` on a button. |
| Form controls | Use `<label for>` or a wrapped label. Associate help and error text with `aria-describedby`. |
| Expand/collapse | Use a button with `aria-expanded` and `aria-controls`. |
| Loading and updates | Use a concise `aria-live="polite"` status region. Use `assertive` only for urgent errors. |
| Dialogs | Use native `<dialog>` where support fits the product, or `role="dialog"`/`aria-modal="true"` with a labelled title and focus management. |
| Decorative icons | Hide with `aria-hidden="true"`; do not hide icons that communicate state or action. |

- Do not add redundant ARIA roles to native elements, such as `role="button"` on `<button>`.
- Every ARIA reference must point to an element that exists and has meaningful text.
- Do not use `aria-label` to replace a visible label with different wording. They should agree.
- Prefer an accessible name from visible text. Keep hidden helper text short and purposeful.

## Forms

Forms include search, checkout, artist onboarding, artwork listing, payout settings, and account management.

| Requirement | Standard |
| --- | --- |
| Labels | Every input has a persistent visible label. Placeholder text is not a label. |
| Required fields | Mark visually and programmatically; explain the required convention before the form. |
| Instructions | Put format guidance before input where possible, and associate it with the field. |
| Errors | Identify the field, explain how to resolve it, and preserve user-entered values. |
| Validation | Validate on submit and, where helpful, after a field is complete. Avoid interrupting users on every keystroke. |
| Error summary | On failed submission, show a linked summary at the top and focus it. |
| Autocomplete | Apply relevant HTML `autocomplete` tokens for personal, shipping, payment, and address fields. |
| Input purpose | Use correct input type and `inputmode` to bring up suitable mobile keyboards. |
| Time limits | Avoid them; if unavoidable, warn users and allow extension. |

For field-level errors, connect the message to its input and expose invalid state:

```css
[aria-invalid="true"] {
  border-color: var(--color-border-critical);
  box-shadow: 0 0 0 3px var(--color-focus-critical);
}
```

Error copy should be specific: “Enter a valid email address, such as name@example.com.” Avoid “Invalid input” or colour-only error treatment.

## Buttons and Interactive Controls

- Use a descriptive verb-first label: “Add to cart”, “Save artwork”, “Continue to delivery”. Avoid isolated “Click here” or “Submit”.
- Preserve a control’s accessible name across loading states. Add status such as “Saving…” without replacing its purpose with an unlabeled spinner.
- Icon-only buttons require an accessible name and a visible focus state; tooltips may supplement but never supply the only name.
- Use disabled controls sparingly. When a prerequisite is understandable, an enabled control that explains the unmet condition can be more accessible.
- Keep confirmation, destructive, and irreversible actions clearly separated from secondary actions.

## Modals, Drawers, and Bottom Sheets

| Component | Required behaviour |
| --- | --- |
| Modal | Has a programmatic name, moves focus inside on open, keeps focus within while active, closes with Escape when appropriate, and restores focus on close. |
| Confirmation modal | Clearly names the consequence and preferred safe action; do not place destructive action in the default focus position. |
| Drawer | Has a labelled region and a visible close button. Treat blocking drawers as modals; non-blocking drawers must not trap focus. |
| Bottom sheet | Meets the same labelling, close, focus, and touch-target requirements as a modal or drawer. Ensure it does not cover the focused input behind it. |
| Backdrop | Dimming alone does not communicate modality; background must be inert/non-interactive while a modal is open. |

Avoid nested modals. If a task requires a second layer, close or transform the first layer and preserve context.

## Navigation

- Wrap primary navigation in a labelled `nav` landmark, for example `aria-label="Primary"`.
- Indicate the current page using `aria-current="page"`; use `aria-current="step"` for checkout progress.
- Mobile menu triggers expose expanded/collapsed state. Opening the menu must not reposition keyboard focus unpredictably.
- Menus are for action lists, not ordinary site navigation. Prefer a disclosure list for mobile navigation unless menu keyboard behaviour is needed.
- Breadcrumbs describe hierarchy; mark the current item with `aria-current="page"` and do not make it a link.
- Search has a visible label or accessible name, clear submit behaviour, and understandable results count/status.

## Images and Artwork

| Image type | Alternative text approach |
| --- | --- |
| Product artwork | Describe the work accurately and succinctly: artist, medium or key visual subject when useful. Do not repeat adjacent title text. |
| Artist portrait | Identify the person where the information is not already supplied nearby, for example “Portrait of artist Leila Al-Khalidi”. |
| Functional image | Describe its action, such as “Open gallery image 3”. |
| Decorative texture or flourish | Use empty `alt=""` and omit redundant title text. |
| Complex visualisation | Provide a concise summary plus a text table, downloadable data, or detailed description. |

- Do not use filenames, “image of”, or visual assumptions as alt text.
- Preserve meaningful artwork captions, dimensions, materials, edition, and condition as real text near the image.
- Never rely on an image crop to show essential product detail; give users access to full-resolution images and descriptive metadata.

## Product Gallery

- Each thumbnail has an accessible name that identifies its image order or content, such as “View detail image 2 of 6”.
- The active image is programmatically identifiable, for example through selected-state semantics and a descriptive gallery status.
- Gallery controls work with Tab and Enter/Space. Arrow-key navigation is optional unless implemented as a tabs or carousel pattern.
- Do not auto-advance product imagery. If autoplay is offered, provide pause/stop controls and respect reduced-motion preferences.
- Zoom must be optional, keyboard accessible, dismissible with Escape, and usable without hover.
- Announce image loading only when it affects the user’s task; avoid noisy announcements while browsing thumbnails.

## Artist Dashboard

The dashboard must not exclude artists who use keyboards, magnification, voice control, or screen readers.

- Use a visible page heading and landmarks for dashboard navigation, main content, filters, and notifications.
- Ensure metric cards, sales charts, and inventory indicators have textual equivalents. Include values, time ranges, comparisons, and trend direction in text.
- Tables provide headers with `scope`, a caption or accessible name, responsive alternatives, and keyboard-accessible row actions.
- Bulk selection exposes selected count and the next available actions. Never rely on a checkbox’s visual colour alone.
- Artwork upload has a labelled file input, supported formats and size requirements in text, upload progress, retry action, and explicit completion/error status.
- Autosave announces status quietly and exposes the last saved time; never cause focus loss or overwrite edited content without warning.

## Responsive and Reflow Behaviour

| Area | Requirement |
| --- | --- |
| Small screens | At 320 px width, maintain a single logical reading order and avoid horizontal page scrolling. |
| Orientation | Do not lock to portrait or landscape unless essential to the task. |
| Zoom | At 400% browser zoom, ensure controls remain available and content reflows without hidden actions. |
| Navigation | Collapsed navigation retains all destinations and clear expanded-state feedback. |
| Tables | Preserve headers and relationships; use horizontal scrolling only when essential, with a visible cue and an alternative summary where possible. |
| Touch | Keep targets at least 44 × 44 px when space permits, with enough separation to avoid accidental activation. |
| Drag operations | Provide click/tap or keyboard alternatives for reordering, zooming, and sliders. |

## Reduced Motion and Sensory Considerations

- Respect `prefers-reduced-motion: reduce`. Remove non-essential movement, parallax, auto-scrolling, and decorative transitions.
- Do not use flashing content more than three times per second. Avoid strobing, rapid zooms, and high-contrast animated patterns.
- Motion must not be the only signal for successful add-to-cart, upload completion, errors, or navigation.
- Let users pause, stop, or hide moving content that starts automatically and lasts longer than five seconds.

```css
@media (prefers-reduced-motion: reduce) {
  *,
  *::before,
  *::after {
    animation-duration: 0.01ms !important;
    animation-iteration-count: 1 !important;
    scroll-behavior: auto !important;
    transition-duration: 0.01ms !important;
  }
}
```

## Screen Reader Support

- Give each page a unique, meaningful document title that reflects the current route and state.
- Use one primary `<h1>` per page and a logical heading structure for sections.
- Place asynchronous messages in dedicated, persistent live regions; do not dynamically insert the live region only when a message occurs.
- Announce concise results such as “3 artworks added to cart” or “Filters applied: 24 works found.”
- Avoid over-announcing visual changes, especially on every keystroke, carousel movement, or filtered search result.
- Test critical user journeys with at least one desktop screen reader and one mobile screen reader before release.

## Error Messages and Recovery

| Situation | Required response |
| --- | --- |
| Inline field error | Name the field, explain the correction, expose invalid state, and associate error text to the field. |
| Form submission error | Provide a summary, move focus to it, retain entered data, and link to each issue. |
| Server error | Use plain language, state what happened and what the user can do next; preserve work where possible. |
| Payment failure | Do not expose sensitive details. Clearly distinguish payment failure from order confirmation. |
| Upload failure | Identify the failed file, reason when known, and offer retry/remove actions. |
| Network interruption | State whether the action was saved, pending, or needs retrying. Never imply success without confirmation. |

## Implementation Notes for React and Tailwind

- Prefer native HTML elements in React components. Component APIs should require an accessible label for icon-only controls and reject missing `alt` text except where decoration is explicit.
- Manage focus in React after route changes, modal transitions, and error summaries. Do not use timeouts as the primary focus-management mechanism.
- Keep DOM order aligned with visual order; CSS `order` should not create a different keyboard reading sequence.
- Use Tailwind focus utilities consistently, for example `focus-visible:outline-none focus-visible:ring-3 focus-visible:ring-focus focus-visible:ring-offset-3` using approved token values.
- Ensure responsive utility classes do not hide the only label, close control, table header, or error explanation at a smaller breakpoint.
- Use automated checks in development, but treat them as a safety net. Manual keyboard, zoom, and screen-reader testing remains required.

## Accessibility Checklist

### Content and visual design

- [ ] Text meets 4.5:1 contrast (or 3:1 for qualifying large text).
- [ ] Non-text controls, focus indicators, and boundaries meet 3:1 contrast.
- [ ] Information is not communicated by colour, position, shape, or motion alone.
- [ ] Text can resize to 200%; pages reflow at 320 px and 400% zoom.
- [ ] Arabic and English content have correct language and direction settings.
- [ ] Images have appropriate alternative text; decorative images use empty alt text.

### Interaction

- [ ] Every action works with keyboard alone.
- [ ] Focus order is logical and focus is always visible.
- [ ] A skip link reaches the main content.
- [ ] Targets are at least 24 × 24 px, with 44 × 44 px used for primary touch controls.
- [ ] No interaction depends on dragging, hover, or a single pointer gesture alone.
- [ ] Motion can be reduced, paused, or avoided where required.

### Components and forms

- [ ] Controls use native semantics or complete accessible interaction patterns.
- [ ] Icon-only controls have accessible names.
- [ ] Forms have visible labels, instructions, valid input types, and useful autocomplete values.
- [ ] Errors identify the problem, explain the fix, retain entered data, and move focus appropriately.
- [ ] Modals and blocking drawers label themselves, manage focus, close predictably, and restore focus.
- [ ] Navigation exposes current page and expanded/collapsed state where relevant.

### Verification

- [ ] Test the customer purchase journey and artist upload journey with keyboard only.
- [ ] Test at 200% and 400% zoom, at 320 px width, and in portrait and landscape orientations.
- [ ] Test with a screen reader on desktop and mobile.
- [ ] Verify reduced-motion behaviour and high-contrast/system colour modes.
- [ ] Run automated accessibility checks and manually review all findings before release.
