# FANNAN Components Sizing

This specification defines the standard sizing rules for core UI components in FANNAN. The system is designed for a premium, minimal marketplace experience that feels calm, consistent, and easy to scan across Arabic and Latin content.

Sizing is built around a compact, comfortable hierarchy:

- Primary actions stay prominent but restrained.
- Inputs and navigation controls are tall enough for touch and comfortable pointer use.
- Cards and browsing surfaces maintain strong visual rhythm without feeling heavy.
- Administrative and dashboard surfaces prioritize information density without sacrificing clarity.

## Sizing Principles

- Use fixed component heights where predictability improves rhythm and alignment.
- Allow widths to adapt to content, container size, and screen class.
- Prefer 8px increments for spacing and radius values.
- Keep touch targets at least 44px high on mobile.
- When Arabic text increases intrinsic width, allow flexible layouts rather than forcing truncation too early.

## Reference Tokens

| Token | Value | Use |
| --- | ---: | --- |
| `xs` | 32px | Compact utility controls, dense table actions |
| `sm` | 36px | Secondary controls, compact inputs on desktop |
| `md` | 40px | Default desktop control height |
| `lg` | 44px | Default mobile control height, touch-safe controls |
| `xl` | 48px | Emphasized buttons, search bars, dialogs |
| `2xl` | 56px | Large hero controls and featured actions |

## Responsive Rules

| Screen Class | Buttons | Inputs | Cards | Tables | Navigation |
| --- | --- | --- | --- | --- | --- |
| Mobile | Full width primary actions where practical | Full width fields, larger touch heights | Single-column cards | Convert to stacked or horizontally scrollable layouts | Use bottom nav, drawer, or sheet patterns |
| Tablet | Mix full width and inline actions | Balanced form rows, 2-column sections where useful | Two-column or three-column card grids | Condense low-priority columns | Sidebar can collapse into a rail or drawer |
| Desktop | Inline actions and grouped toolbars | Side-by-side form rows | Multi-column browsing grid | Full tables with scanning priority | Persistent sidebar and top navigation |

## Implementation Notes

- Use CSS or design tokens to map each size family to a single source of truth.
- Keep `min-height` on tappable elements at or above 44px on touch devices.
- Let text, especially Arabic text, determine width when content is longer than the default token.
- Avoid squeezing product and artist cards below the point where imagery and price metadata lose hierarchy.
- For React components, expose size props such as `sm`, `md`, and `lg` only when they map cleanly to this spec.
- In TailwindCSS, keep utility combinations predictable by pairing a size token with a component variant token rather than ad hoc one-off values.

## Tailwind Recommendation

- Use semantic component classes such as `btn-primary`, `input-field`, `card-product`, and `sheet-bottom` in addition to utility classes.
- Map component sizes to a small token set, for example `h-11`, `h-12`, `px-4`, `px-5`, `rounded-xl`, and `rounded-2xl`.
- Prefer responsive modifiers for layout changes rather than changing the underlying component system on every breakpoint.

## React Recommendation

- Build size-aware primitives that accept a constrained `size` prop and apply the documented dimensions consistently.
- Keep visual variants separate from density variants so a component can change emphasis without changing its geometry.
- For overlays, centralize sizing behavior in the dialog, modal, drawer, and bottom sheet primitives so the same logic is reused across the product.
