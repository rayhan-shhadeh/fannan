# FANNAN Design Tokens

This document defines the canonical design tokens for FANNAN. The system is built for a premium Palestinian marketplace experience: elegant, warm, minimal, and culturally grounded. Tokens are written to support consistent implementation across CSS, TailwindCSS, React, and Flutter.

## Token Principles

- Use semantic token names for product-level decisions, not raw visual values in component code.
- Prefer a single source of truth for each scale.
- Keep the token system portable so the same meaning can be translated across platforms.
- Expose only stable primitives to application code.
- Reserve arbitrary values for rare, local exceptions.

## Naming Conventions

Use a layered naming structure:

- `fannan` as the namespace.
- A category such as `color`, `space`, `radius`, or `shadow`.
- A role or scale name such as `surface`, `text`, `brand`, `100`, or `xl`.

Recommended patterns:

- CSS variables: `--fannan-color-brand-500`
- JSON tokens: `color.brand.500`
- TypeScript constants: `COLOR.BRAND[500]`
- Tailwind theme keys: `theme.extend.colors.brand[500]`
- Flutter theme values: `Color(0xFF...)` in a semantic theme map

Rules:

- Use lowercase for token names in source files.
- Use numeric scales in ascending order.
- Use semantic aliases for frequently used UI roles.
- Do not encode component names in foundational tokens.

## Token Map

| Category | Purpose |
| --- | --- |
| Typography Tokens | Font families, sizes, weights, line heights, letter spacing |
| Color Tokens | Brand, neutral, surface, text, status, and utility colors |
| Spacing Tokens | Rhythm, layout gaps, padding, and margins |
| Radius Tokens | Corner shapes for surfaces and controls |
| Border Tokens | Width, style, and color definitions |
| Shadow Tokens | Elevation and depth layers |
| Motion Tokens | Duration and easing values |
| Animation Tokens | Reusable motion patterns |
| Z-index Tokens | Layer ordering for overlays and navigation |
| Breakpoint Tokens | Responsive screen thresholds |
| Container Tokens | Layout widths and page constraints |

## Implementation Notes

- Keep foundational tokens immutable unless a system-wide visual direction changes.
- Map semantic tokens such as `surface`, `text`, and `brand` to foundation values in a design layer.
- Use aliases for product usage, but keep the underlying scale consistent.
- In React, import tokens from a shared package rather than redefining values in each app.
- In Flutter, wrap the token values in a small utility layer so themes remain testable and portable.

## Recommended Consumption Pattern

| Layer | Example |
| --- | --- |
| Foundation | `color.brand.500`, `space.24`, `radius.lg` |
| Semantic | `surface.raised`, `text.primary`, `border.default` |
| Component | `button.primary`, `card.product`, `modal.dialog` |

The foundation layer should be stable, the semantic layer should express the product language, and the component layer should remain thin.
