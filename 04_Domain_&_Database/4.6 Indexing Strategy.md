## Indexing Philosophy

### Core Principles

1. **Not All Queries Need Indexes:** Only optimize queries that run frequently or serve user-facing features (e.g., browsing artworks, checking order status)
2. **Composite Indexes Over Multiple Single Indexes:** PostgreSQL can use multiple single indexes in a single query (multi-index scans), but composite indexes are often more efficient
3. **Partial Indexes for Filtered Data:** When most queries filter on a condition (e.g., `status = 'published'`, `deleted_at IS NULL`), partial indexes reduce index size and query cost
4. **Avoid Indexing Low-Cardinality Columns:** Indexing columns with few distinct values (e.g., a boolean) is often wasteful; sequential scan may be faster
5. **Denormalization with Caution:** Denormalized columns (e.g., `artist_id` in `order_items`) enable simpler indexes but increase storage; justified for high-frequency queries
6. **Measure Before Optimizing:** Use PostgreSQL's `EXPLAIN` and query logging to identify slow queries; don't guess

### MVP Principle

**Minimize indexes at launch.** Add indexes based on observed query patterns in production or load testing. Avoid premature optimization that:
- Bloats schema without clear performance benefit
- Slows down writes (each new index must be maintained)
- Complicates migrations and deployment

### Write vs. Read Tradeoff

Every index increases write cost:
- **INSERT:** Must update all indexes on affected tables (major pain point for wide tables)
- **UPDATE:** Must update indexes for modified columns (why denormalized columns are dangerous)
- **DELETE:** Must remove from all indexes

Principle: **Index only columns frequently queried; avoid indexing columns rarely or never queried.**

## Index Types & Techniques

### B-Tree Indexes (Default)

**Type:** `CREATE INDEX ... ON table (column)`

**Use Cases:** 
- Equality conditions: `WHERE user_id = X`
- Range conditions: `WHERE created_at > '2025-01-01'`
- Sorting: `ORDER BY created_at DESC`
- NULL checks: `WHERE deleted_at IS NULL`

**Characteristics:**
- Efficient for most queries
- Default PostgreSQL index type
- Works for single or composite columns

**Example:**
```sql
CREATE INDEX idx_orders_buyer_id ON orders (buyer_id);
-- Efficient for: WHERE buyer_id = X
```

---

### Composite Indexes (Multi-Column B-Tree)

**Type:** `CREATE INDEX ... ON table (col1, col2, col3)`

**Use Cases:**
- Multi-column WHERE clauses: `WHERE buyer_id = X AND status = Y`
- Queries filtering then sorting: `WHERE buyer_id = X ORDER BY created_at DESC`
- Covering queries (all needed columns in index)

**Column Order Matters:**
- Filter columns first (high selectivity)
- Sort columns last
- Left-to-right rule: PostgreSQL uses leftmost prefix of composite index

**Example:**
```sql
CREATE INDEX idx_orders_buyer_status_date ON orders (buyer_id, status, created_at DESC);
-- Efficient for:
--   WHERE buyer_id = X AND status = Y
--   WHERE buyer_id = X AND status = Y ORDER BY created_at DESC
--   WHERE buyer_id = X ORDER BY created_at DESC
-- NOT efficient for:
--   WHERE status = Y (doesn't use index)
--   WHERE created_at > Z (doesn't use index)
```

---

### Partial Indexes (Filtered)

**Type:** `CREATE INDEX ... ON table (column) WHERE condition`

**Use Cases:**
- Query filters heavily on one condition (e.g., published vs. draft)
- Soft-delete pattern: index only active records
- Status-specific queries

**Benefits:**
- Smaller index (fewer rows indexed)
- Faster index maintenance (fewer inserts/deletes)
- Better selectivity for WHERE clause matching the condition

**Example:**
```sql
CREATE INDEX idx_artworks_published_artist ON artworks (artist_id, published_at DESC)
WHERE status = 'published' AND deleted_at IS NULL;
-- Efficient for browsing artist's published portfolio
-- Not indexed: draft, suspended, archived, deleted artworks
```

---

### Unique Indexes (Constraint Enforcement)

**Type:** `CONSTRAINT name UNIQUE (column)` or `CREATE UNIQUE INDEX ... ON table (column)`

**Use Cases:**
- Enforce uniqueness (email, username)
- Prevent duplicates (single follow per pair, single favorite per pair)
- Fast lookups by unique column (email login)

**Example:**
```sql
CREATE UNIQUE INDEX uniq_users_email ON users (email);
-- Efficient for: WHERE email = 'user@example.com'
-- Prevents duplicate emails
```

## Performance-Critical Indexes (MVP)

These indexes are **essential for launch** because they serve user-facing features with high frequency.

### 1. User Authentication & Lookup

**Index Name:** `idx_users_email`  
**Table:** `users`  
**Columns:** `email`  
**Type:** B-Tree with partial filter  
**SQL:**
```sql
CREATE INDEX idx_users_email ON users (email) WHERE deleted_at IS NULL;
```
**Query Pattern:** User login (email-based authentication)  
**Query Example:**
```sql
SELECT id, password_hash FROM users WHERE email = 'artist@example.com' AND deleted_at IS NULL;
```
**Importance:** **CRITICAL** — Executed on every login attempt  
**Write Impact:** LOW — Email rarely updated; soft-delete doesn't retroactively index  
**Reason:** Login is high-frequency user-facing operation; partial index reduces size (excludes deleted users)

**Columns:** `buyer_id`, `created_at DESC`

**Importance:** **CRITICAL** — Customer dashboard; high-frequency

**Reason:** Every customer views their order history; DESC sort prevents reverse index scan

## Write Performance Considerations

### Impact Analysis

Every index increases **INSERT/UPDATE/DELETE** cost:

| Operation | Impact | Example |
|-----------|--------|---------|
| INSERT | Multiply writes by number of indexes | 10 indexes on artworks = 10 index writes per INSERT |
| UPDATE | Indexes on updated columns must be maintained | Changing artwork.status requires updates on idx_artworks_status |
| DELETE (soft) | Minimal (only soft-delete marker set) | `UPDATE artworks SET deleted_at = NOW()` updates 1 column + affected indexes |
| DELETE (hard) | Expensive (remove from all indexes) | Avoid for orders, reviews, audit logs (keep forever) |

### Mitigation Strategies

1. **Minimize Index Count:** Only create indexes that serve frequent queries
2. **Avoid Indexing Updated Columns:** Don't index columns that change often (e.g., `updated_at`)
3. **Denormalize Carefully:** Denormalized columns (e.g., `artist_id` in `order_items`) enable better indexes but slow writes
4. **Batch Operations:** Use `COPY` or bulk INSERT for initial data load; bypasses index maintenance
5. **Partial Indexes:** Reduce index size; fewer rows to maintain

### Expected Write Impact (MVP)

**Artworks table** (frequently published):
- 20 indexes on artworks
- Each INSERT/UPDATE scans 20 indexes
- Mitigation: Partial indexes exclude deleted/draft records; reduced write cost

**Orders table** (frequent order creation):
- 8-10 indexes on orders
- Each INSERT requires updating all indexes
- Mitigation: Composite indexes replace multiple single indexes; same effect, better selectivity

**Recommendations:**
- Monitor write latency in production
- Add indexes if read latency is unacceptable
- Remove unused indexes quarterly

## Monitoring & Maintenance

### Identifying Slow Queries

Use PostgreSQL's `pg_stat_statements` to identify slow queries:

```sql
-- Enable query statistics
CREATE EXTENSION IF NOT EXISTS pg_stat_statements;

-- Find slowest queries
SELECT query, calls, total_time, mean_time 
FROM pg_stat_statements 
ORDER BY mean_time DESC LIMIT 20;

-- Find most frequently called queries
SELECT query, calls 
FROM pg_stat_statements 
ORDER BY calls DESC LIMIT 20;
```

### Missing Index Detection

```sql
-- Find sequential scans on tables > 1GB
SELECT schemaname, tablename, seq_scan, idx_scan, n_live_tup
FROM pg_stat_user_tables
WHERE seq_scan > 100 AND idx_scan = 0
ORDER BY seq_scan DESC;
```

### Index Usage Monitoring

```sql
-- Find unused indexes (candidates for removal)
SELECT schemaname, tablename, indexname, idx_scan, idx_tup_read, idx_tup_fetch
FROM pg_stat_user_indexes
WHERE idx_scan = 0
ORDER BY pg_relation_size(indexrelid) DESC;
```

### Periodic Maintenance

**Weekly:**
- Monitor query logs for new slow queries
- Check for table bloat from deletes/updates

**Monthly:**
- `ANALYZE` — update table statistics (optimizer uses this for query planning)
- `REINDEX` — only if index bloat suspected (rare)

**Quarterly:**
- Review index usage statistics
- Remove unused indexes
- Add missing indexes based on production data
