**Based On:** 4.4 Database Schema

> **Purpose:** This document exhaustively specifies all database-level integrity constraints that enforce business invariants and prevent invalid states. It distinguishes database invariants (enforced by PostgreSQL) from application business rules (enforced by NestJS backend logic). This ensures data consistency, prevents common errors (negative prices, double-selling, duplicate entries), and clarifies implementation responsibility.

## Constraint Classification

### Database Invariants vs. Application Business Rules

This document distinguishes two categories:

#### Database Invariants
These are enforced **at the database level** by PostgreSQL:
- Primary key uniqueness
- Foreign key referential integrity
- Check constraints
- Unique constraints
- NOT NULL constraints
- Enum type enforcement

**Enforcement:** PostgreSQL rejects violating SQL statements immediately  
**Testing:** Database unit tests (verify constraints catch violations)  
**Responsibility:** Database schema and DDL

#### Application Business Rules
These are enforced **at the application level** (NestJS backend):
- State machine transitions (e.g., order status → payment_pending → paid)
- Complex multi-step workflows (negotiation rounds, offer acceptance)
- Authorization checks (user owns artwork before editing)
- Event-driven logic (triggering notifications, inventory holds)
- Calculation validation (order total = sum of items)

**Enforcement:** Backend service logic, guards, and middleware  
**Testing:** Integration tests (verify business logic enforces rules)  
**Responsibility:** NestJS services and domain models

### Critical Rule: Defense in Depth

**Never rely exclusively on frontend validation.** Frontend validation improves UX; database constraints catch malicious/buggy requests.

```
Frontend Validation (UX only)
      ↓
    API Guards (validate input shape)
      ↓
    NestJS Services (apply business logic)
      ↓
    Database Constraints (final safeguard)
```

## User & Identity Constraints

### PK_users_id

| Property | Value |
|----------|-------|
| **Type** | Primary Key |
| **Column(s)** | `id` (UUID) |
| **Enforcement** | PostgreSQL |
| **SQL** | `id UUID PRIMARY KEY DEFAULT gen_random_uuid()` |
| **Purpose** | Globally unique identifier for each user; foundation for all relationships |
| **Business Rule** | Every user has exactly one immutable ID |
| **Implication** | Cannot have duplicate user records; ID never changes post-creation |

---

### UQ_users_email

| Property | Value |
|----------|-------|
| **Type** | Unique Constraint |
| **Column(s)** | `email` |
| **Enforcement** | PostgreSQL |
| **SQL** | `email VARCHAR(254) NOT NULL UNIQUE` |
| **Purpose** | Email is login credential; must be globally unique |
| **Business Rule** | No two active users can share an email address |
| **Caveat** | Soft-deleted users (deleted_at IS NOT NULL) can have duplicate emails (allows re-registration after account deletion) |
| **Index** | `idx_users_email ON users (email) WHERE deleted_at IS NULL` (partial index for active users) |
| **Database Invariant** | PostgreSQL enforces uniqueness |
| **Application Rule** | Prevent user re-registration within 30 days of deletion (business policy) |

---

### NN_users_email, NN_users_password_hash, NN_users_display_name

| Property | Value |
|----------|-------|
| **Type** | NOT NULL Constraint |
| **Columns** | `email`, `password_hash`, `display_name` |
| **Enforcement** | PostgreSQL |
| **SQL** | `email VARCHAR(254) NOT NULL`, `password_hash VARCHAR(255) NOT NULL`, `display_name VARCHAR(255) NOT NULL` |
| **Purpose** | Essential user fields must always be present |
| **Business Rule** | User registration requires email, password, and public name |

### CHK_users_email_format

| Property | Value |
|----------|-------|
| **Type** | Check Constraint |
| **Column** | `email` |
| **Enforcement** | PostgreSQL |
| **SQL** | `CONSTRAINT chk_email_format CHECK (email ~ '^[A-Za-z0-9._%+\-]+@[A-Za-z0-9.\-]+\.[A-Z\|a-z]{2,}$')` |
| **Purpose** | Validate email format at database level (defense in depth) |
| **Business Rule** | Email must conform to standard email syntax |
| **Caveat** | This regex is basic; full RFC 5322 validation happens in application |
| **Database Invariant** | PostgreSQL rejects invalid emails on INSERT/UPDATE |
| **Application Rule** | Deeper validation (DNS check, bounce detection) handled by backend |

---

### ENUM_user_status

| Property | Value |
|----------|-------|
| **Type** | Enum Type Constraint |

| **Enforcement** | PostgreSQL |

| **Implication** | Inserting second artist profile for same user_id raises UNIQUE constraint violation |

| **Values** | 'not_applied', 'pending', 'approved', 'rejected', 'suspended' |
| **Enforcement** | PostgreSQL |
| **SQL** | `verification_status artist_verification_status_enum DEFAULT 'not_applied' NOT NULL` |
| **Purpose** | Artist verification state machine; only valid states allowed |

| **Database Invariant** | PostgreSQL rejects invalid verification_status values |
| **Application Rule** | Enforce state machine: can't transition rejected → approved (must re-apply); suspensions require admin action |
| **Critical Rule** | Artist can only publish artworks if status = 'approved' |

| Property | Value |
|----------|-------|
| **Type** | Application Business Rule (NOT database constraint) |

---

### CHK_inventory_quantities_valid

| Property | Value |
|----------|-------|
| **Type** | Check Constraint (Complex Multi-Column) |
| **Columns** | `quantity_total`, `quantity_available`, `reserved_quantity` |
| **Enforcement** | PostgreSQL |
| **SQL** | `CONSTRAINT chk_inventory_quantities_valid CHECK (quantity_total > 0 AND quantity_available >= 0 AND reserved_quantity >= 0 AND (quantity_available + reserved_quantity <= quantity_total))` |
| **Purpose** | **CRITICAL:** Prevent inventory double-selling and invalid stock states |
| **Business Rules** | 1. Total stock must be positive (at least 1 unit)<br/>2. Available must be non-negative (never negative)<br/>3. Reserved must be non-negative<br/>4. Available + Reserved ≤ Total (no overbooking) |
| **Example Violations** | ❌ quantity_total = 0 (empty inventory)<br/>❌ quantity_available = -5 (sold more than available)<br/>❌ reserved_quantity = 100 when quantity_total = 50 (overbooking)<br/>❌ quantity_available + reserved_quantity = 51 when quantity_total = 50 |
| **Invariant** | Always: `quantity_available = quantity_total - reserved_quantity` |
| **Transaction Requirement** | When order is placed, update inventory WITHIN SAME TRANSACTION as order creation to prevent race conditions |

---

### Unique Product Inventory Constraint (Application Rule)

| Property | Value |
|----------|-------|
| **Type** | Application Business Rule |
| **Rule** | If `artwork.supply_type = 'unique'`, then `inventory.quantity_total MUST = 1` |
| **Enforcement** | NestJS validation in ArtworkService and InventoryService |
| **Database Support** | Could add CHECK constraint with CASE statement, but complex; application layer is clearer |
| **Testing** | Verify: attempt to set quantity > 1 for unique artwork; expect validation error |

## Concurrency & Transaction Constraints

### Inventory Reservation Atomicity

| Property | Value |
|----------|-------|
| **Type** | Transaction Constraint (Application Rule) |
| **Rule** | Order creation + inventory deduction must be atomic (single transaction) |
| **Enforcement** | NestJS uses database transaction: BEGIN → INSERT order → INSERT order_items → UPDATE inventory → COMMIT |
| **Database Support** | PostgreSQL SERIALIZABLE isolation level for strict enforcement; READ_COMMITTED with app-level optimistic locking acceptable |
| **Purpose** | Prevent race condition: concurrent orders could both succeed even though only 1 unit available |
| **Example Race Condition** | ❌ Thread A reads inventory.quantity_available=1; Thread B reads inventory.quantity_available=1; both create orders; result: 2 orders but only 1 stock (DOUBLE-SELL)<br/>✓ Atomic transaction prevents this |
| **Testing** | Load test: concurrent order placement on unique artwork; verify only one order succeeds |

## Summary: Critical Invariants

The following are the **most critical database invariants** that prevent common errors:

### 1. Prevent Negative Prices
**Constraints:** CHK_artworks_base_price_positive, CHK_order_items_price_valid, CHK_payments_amount_positive  
**Purpose:** Negative prices indicate fraud or data corruption  
**Testing:** Attempt to insert artwork with base_price = -10; expect constraint violation

### 2. Prevent Inventory Double-Selling
**Constraint:** CHK_inventory_quantities_valid (quantity_available >= 0, reserved + available <= total)  
**Purpose:** Ensure single unique item not sold twice; prevent overselling quantity-based items  
**Testing:** Concurrent order placement on unique artwork; verify only 1 succeeds

### 3. Prevent Duplicate Favorites/Follows/Reviews
**Constraints:** UQ_favorites, UQ_follows, UQ_reviews_artist_order  
**Purpose:** User-artist relationships must be unique; duplicate entries clutter UI and double-count metrics  
**Testing:** Attempt to add same favorite twice; expect UNIQUE constraint violation

### 4. Prevent Negative Quantities
**Constraint:** CHK_order_items_quantity_positive, CHK_inventory_quantities_valid  
**Purpose:** Quantity must be ≥ 1; negative quantities are nonsensical  
**Testing:** Attempt to create order_item with quantity = 0 or -5; expect constraint violation

### 5. Enforce Artist Verification Gate
**Enum:** artist_verification_status (only 'approved' can publish)  
**Application Rule:** Cannot publish artwork unless artist.verification_status = 'approved'  
**Purpose:** Prevent unverified users from listing (marketplace quality control)  
**Testing:** Attempt to publish with unverified artist; expect 403 Forbidden

### 6. Enforce Finite Negotiations
**Constraint:** CHK_negotiations_max_rounds_positive, UQ_negotiations_buyer_product  
**Application Rule:** Only one active negotiation per (buyer, artwork); max rounds enforced  
**Purpose:** Prevent infinite negotiation loops; bound computational resources  
**Testing:** Reach max_rounds; attempt to create new offer; expect error

### 7. Prevent Shipping Address for Digital-Only Orders
**Constraint:** CHK_orders_shipping_address  
**Purpose:** Digital products don't require shipping; NULL address indicates logical consistency  
**Testing:** Attempt to create digital-only order with shipping_required=true; expect constraint violation

### 8. Enforce Order Total Reconciliation
**Application Rule:** order.total_amount = SUM(order_items prices) + shipping + tax  
**Purpose:** Prevent payment mismatches; detect unauthorized price adjustments  
**Testing:** Verify: order total calculated correctly; audit log captures changes

### 9. Prevent Self-Reviews and Self-Follows
**Constraints:** CHK_reviews_reviewer_not_artist, CHK_follows_not_self_follow  
**Purpose:** Prevent reputational gaming; maintain data sanity  
**Testing:** Attempt to review self; expect constraint violation

### 10. Enforce Immutable Audit Logs
**Application Rule:** audit_log entries never updated or deleted; only INSERT allowed  
**Purpose:** Compliance and forensics; tamper-evident trail for investigations  
**Testing:** Attempt to DELETE audit_log record; expect 403 Forbidden
