# 4.0 Domain & Database Consistency Audit

**Status:** Architecture audit  
**Scope:** Internationalization and localization impact on documents 4.1–4.8  
**Decision baseline:** FANNAN MVP supports Arabic (`ar`, RTL) and English (`en`, LTR), with future languages possible.

## 1. Executive Summary

The existing 4.1–4.8 documentation remains a valid marketplace foundation, but it is not fully complete for the new first-class internationalization requirement. The marketplace aggregates, order model, inventory model, payment model, and lifecycle concepts do not need redesign. They do need explicit localization rules at their boundaries.

The required change is a **partial update**, not regeneration:

- Treat localization as a cross-cutting platform capability, not a new marketplace bounded context.
- Add an explicit user preferred locale and request/response locale policy.
- Store locale-aware translation resources, notification/email templates, and selected multilingual catalog content in PostgreSQL.
- Keep translation keys stable and separate from user-generated content.
- Do not add `*_ar` and `*_en` columns to every table.
- Preserve the original locale and translation provenance for artist-created content.
- Make search, categories, tags, notifications, validation, caching, APIs, clients, and seed data locale-aware.

## 3. 4.1 Domain Model Impact

The domain model should be amended, not replaced.

### Required changes

1. Add a cross-cutting **Localization capability** spanning Identity, Catalog, Notifications, Search, API, and client presentation.
2. Define three separate data classes:
   - **System/UI translations:** stable keys and translated messages owned by the platform.
   - **User-generated marketplace content:** artwork titles, descriptions, biographies, collection names, and similar artist content.
   - **Domain data:** prices, statuses, quantities, IDs, timestamps, payment states, and workflow values, which remain language-neutral.
3. Define locale resolution order: explicit request locale, authenticated user preference, browser/device locale, supported default (`en`).
4. Define fallback behavior and include the resolved locale/fallback state in application/API policy.
5. Add locale-aware domain events where consumers render text, such as notification creation and template publication.

Localization is not a reason to split the MVP into a translation bounded context or microservice. Translation ownership can be a shared platform module with clear interfaces.

## 4. 4.2 Entity Definitions Impact

The existing entities remain conceptually correct. The following additions are required:

- **User:** `preferred_locale` (nullable or defaulted to `en`), validated against supported locales.
- **Locale:** a supported-locale reference/value object containing code, language direction, and formatting metadata. For MVP, `ar` and `en` may be application configuration rather than a separate table.
- **TranslationResource:** stable `translation_key`, `locale`, translated value, namespace/type, version, and publication metadata.
- **NotificationTemplate / MessageTemplate:** stable template key, channel, locale, parameter schema/version, body/title, active version, and fallback policy.
- **ContentTranslation:** reusable conceptual entity for translated user-generated fields, with owner entity, locale, translated fields, source/original locale, status, and timestamps.

Rendered notification content should be retained when needed for audit/user history, together with the locale and template version used. It must not be regenerated later from a changed translation.

## 5. 4.3 Relationship Impact

Existing User, ArtistProfile, Artwork, Category, Tag, Notification, Order, and Search relationships remain valid.

Add only these optional relationships:

- User `1 : 0..1` preferred locale (a scalar preference, not a new user aggregate).
- Artwork `1 : 0..N` artwork translations, unique per locale.
- ArtistProfile `1 : 0..N` biography/profile translations, unique per locale.
- Category and Tag `1 : 0..N` localized labels, unique per locale.
- Template key `1 : 0..N` localized template versions, unique by channel/locale/version.
- Translation resource key `1 : N` locale values, unique by key/locale/version.

Translation rows belong to their source entity and must not become independent marketplace aggregates. Deleting or anonymizing source content must apply the existing lifecycle policy to its translations.

## 6. 4.4 Database Schema Impact

### PostgreSQL should store

- User preferred locale (`ar` or `en` initially).
- Supported locale configuration if operationally managed.
- UI/system translation resources if runtime admin editing is required.
- Notification, email, and push template definitions and localized versions.
- Template/resource version and publication metadata.
- User-generated localized artwork, artist profile, collection, category, and tag content.
- Original/source locale and translation status/provenance.
- Locale used for a sent notification and immutable rendered snapshots where required.
- Search read-model language/script fields and normalized searchable text, if the search read model is persisted in PostgreSQL.

### PostgreSQL should not store

- Browser/device locale detection results as authoritative user data.
- Client-side compiled translation bundles or UI formatting caches.
- Duplicated localized copies of every domain enum, status, ID, or numeric value.
- Rendered text as the source of truth for templates.
- Secrets, provider credentials, or third-party translation-service state that is not part of FANNAN business data.

### Recommended MVP shape

Use stable, language-neutral columns for domain values and separate translation tables for variable multilingual content:

- `users.preferred_locale`
- `translation_resources(translation_key, locale, value, namespace, version, status, ...)`
- `message_templates(template_key, channel, locale, subject/title/body, version, status, ...)`
- `artwork_translations(artwork_id, locale, title, description, ...)`
- `artist_profile_translations(artist_profile_id, locale, public_bio, ...)`
- `category_translations(category_id, locale, name, description, ...)`
- `tag_translations(tag_id, locale, label, ...)`

Exact physical names should be applied in the schema update so they match existing naming conventions.

## 7. 4.5 Constraint Impact

Add the following constraints and rules:

- `preferred_locale` must be a supported BCP 47-style code; MVP permits only `ar` and `en`.
- Translation keys are non-null, stable, namespaced, and unique with locale and active version.
- One active translation per `(translation_key, locale)` and one active content translation per `(source_id, locale)`.
- A translation row cannot reference a missing or deleted source entity.
- Template parameters must be compatible with the event/message contract; missing parameters are an application error, not silent text.
- Locale fallback must never select an unsupported locale or expose an unpublished translation.
- Original/source locale must be retained for user-generated content.
- Do not enforce that every record has both Arabic and English translations; missing content is valid and follows the documented fallback policy.
- Do not translate or constrain monetary amounts, statuses, IDs, or workflow enum values as text.

Authorization for editing translations/templates remains an application/admin permission, not solely a database constraint.

## 8. 4.6 Indexing Impact

Add only indexes justified by real request patterns:

- `users(preferred_locale)` only if administrative/reporting queries need it; it is not a high-value user-facing index by itself.
- Unique indexes on `(translation_key, locale, active/version)` and template `(template_key, channel, locale, active/version)`.
- Unique indexes on `(artwork_id, locale)`, `(artist_profile_id, locale)`, `(category_id, locale)`, and `(tag_id, locale)`.
- Search/read-model indexes that include `locale` or language/script and only index published, visible content.
- Full-text/search-provider indexes for Arabic and English normalized fields separately where the provider supports language analyzers.

Do not index every translated text column with B-tree indexes. Use the existing search read model/provider for full-text, autocomplete, stemming, transliteration, and ranking.

## 9. 4.7 Data Lifecycle Impact

Add lifecycle rules for:

- Translation resource and template draft, review, publish, supersede, and rollback states.
- Cache invalidation on translation/template publication.
- Retention of the locale and template/resource version used for sent email, push, and in-app notifications.
- Cascade or soft-delete of content translations with their artwork/profile/category/tag source.
- Preservation of historical order/payment/shipping records in their language-neutral form.
- Reindexing translated content after publication, edit, unpublish, or deletion.
- Export and deletion of user-generated translations under the existing account privacy lifecycle.

Changing a translation must not rewrite historical notification snapshots, order records, invoices, or audit evidence.

## 10. 4.8 Seed Data Impact

Seed data must exercise both locales:

- Users with `ar`, `en`, and unset/preference-fallback scenarios.
- UI translation resources for all required MVP keys in both languages.
- Missing-translation fixtures to verify fallback and missing-key behavior.
- Localized notification, email, and push templates.
- Arabic and English category labels, tag labels, artwork titles/descriptions, and artist biographies.
- RTL/LTR examples, Arabic numerals/date/price display cases, pluralization cases, validation messages, and error messages.
- Stable translation keys and deterministic IDs; no hard-coded user-facing strings in application seed logic.

Seed data should remain fictional and should not be treated as production translation approval.

## 11. Recommended Localization Architecture

Use a shared localization module in the application:

1. Resolve locale at the edge using request, user preference, and browser/device hints.
2. Validate against the supported locale registry.
3. Load translation resources/templates through a repository interface.
4. Cache immutable or versioned resources by `(namespace, locale, version)`.
5. Fall back from `ar` to `en` (the MVP default) when a key is absent, and expose an observable missing-translation event/metric.
6. Keep business logic dependent on stable keys and structured parameters, never translated prose.
7. Store translated user content separately from UI resources.
8. Keep formatting locale-aware through standard server/client internationalization libraries.

No translation microservice or CMS is justified for MVP. Admin screens may manage a small translation/template catalog through the application if runtime editing is a confirmed operational need.

## 12. Translation Storage Decision

**Recommendation: PostgreSQL translation tables with versioned, seeded resources for MVP.**

This supports admin editing, auditability, fallback, transactional publication, notification templates, and future languages without adding columns to every domain table. It is simpler and more operationally controllable than a translation microservice, and safer than JSONB for uniqueness, validation, indexing, and partial updates.

Use JSONB only for truly flexible provider payloads or non-queryable metadata, not as the primary store for translations. Use separate columns only for immutable, genuinely language-independent values.

## 13. User Locale Model

Store a nullable `preferred_locale` on `users`, with `en` as the effective default when unset. Normalize accepted values to supported canonical codes (`ar`, `en`), and keep direction (`rtl`/`ltr`) and formatting rules in locale configuration rather than duplicating them on users.

The user preference overrides browser/device detection. A guest session may retain a client preference, but it is not an authoritative user record until the user saves it.

## 14. User-Generated Multilingual Content

Artwork titles, descriptions, artist biographies, collection names, and similar content are marketplace content, not UI translations.

Use separate translation tables for fields that need multilingual support. Each row has one locale and only the translated fields relevant to that entity. Keep an original/source locale and allow an artist to publish only the languages they actually provide. Missing translated content falls back to the source/or default locale with an explicit indicator where useful.

This approach is preferable to `name_ar`/`name_en` columns because it supports future languages, optional translations, uniqueness, moderation, provenance, and incremental translation without schema changes.

## 15. Search Implications

Search must support Arabic and English independently and must not assume that UI locale equals content locale. The search read model should retain locale/script and index all approved localized fields.

Arabic search requires Unicode normalization, Arabic character/diacritic handling, appropriate tokenization, and, where product-approved, transliteration/synonym behavior. English requires normal stemming/tokenization. Search filters must remain language-neutral for price, status, category identity, and availability.

Results should select the requested locale first, then source/default fallback. Publishing or removing a translation must emit the same search-index update path as other searchable content changes.

## 16. Notification Implications

Notifications should be generated from stable event/type keys and structured parameters. In-app, email, and push templates each need locale-specific versions. Resolve the recipient's locale at creation/send time, record it, and render with the selected template version.

If a locale template is missing, fall back to English and log a missing-translation metric. Push payloads should contain localized title/body; clients should not invent business wording. Historical notifications should retain their rendered snapshot or enough immutable data to display consistently.

## 17. API Implications

APIs should accept an explicit locale or standard locale header where appropriate, while enforcing the supported-locale list. Responses should return localized labels/content according to the resolved locale and may include `locale`, `fallbackLocale`, or translation-availability metadata.

Stable enum/status codes remain language-neutral; clients translate them or receive a server-localized label according to the endpoint contract. Validation and error responses should use stable error codes plus localized message keys/parameters, not only hard-coded prose.

Caching must vary by locale and translation/template version. ETags/cache keys must not allow Arabic content to be served to an English request or vice versa.

## 18. Web/Mobile Implications

The backend owns locale resolution policy, translation resources/templates requiring server consistency, fallback, notification/email wording, and localized catalog content.

Web and Flutter clients own locale selection UI, persistence of guest preference, RTL/LTR layout direction, typography/layout mirroring, and locale-aware date/number/currency rendering using server-provided currency and numeric values. Clients must not hard-code product copy and must consume stable translation keys/resources. Both clients must react to runtime locale changes and support missing-key behavior without crashing.

## 20. No-Change Decisions

- Do not split localization into a separate microservice or bounded context for MVP.
- Do not add `name_ar`, `name_en`, `description_ar`, `description_en`, or equivalent columns to every table.
- Do not redesign User, Artwork, Order, Payment, Shipment, Inventory, Offer, or Analytics aggregates.
- Do not translate IDs, status codes, internal event names, currency codes, or numeric domain values in storage.
- Do not store browser/device detection as a permanent user preference automatically.
- Do not make both Arabic and English content mandatory for every artwork or profile.
- Do not replace the existing search read-model/event approach with database full-text search solely because of i18n.
- Do not modify historical financial/order records when translations change.
- Do not introduce a CMS unless future operational volume demonstrates that the admin translation catalog is insufficient.
