# 4.2 Entity Definitions

This document defines database-relevant domain entities for FANNAN following the Product Requirements (02_PRODUCT_REQUIREMENTS). It assumes the domain model (4.1 Domain Model) is the source of truth; where 4.1 is missing or ambiguous this document records the assumption, recommended decision, and consequence.

For each entity: Entity ID, Official Name, Definition, Purpose, Aggregate, Aggregate Root, Ownership, Lifecycle, Required attributes (conceptual), Optional attributes (conceptual), Relationships, Business rules, Validation rules, Statuses, Creation conditions, Update conditions, Deletion/archive behavior, Audit requirements, Security/privacy, MVP/Future.

---

## USER
- Entity ID: user
- Official Name: User
- Definition: Person or organization with an account on FANNAN that can act as customer and/or artist.
- Purpose: Authentication, authorization, contact, and global identity across customer and artist capabilities.
- Aggregate: user aggregate
- Aggregate Root: User
- Ownership: Owned by FANNAN (primary account record)
- Lifecycle: Registered -> Email/Phone verified? -> Active -> Suspended/Disabled -> Deleted (soft or hard)
- Required attributes (conceptual): id (UUID), primary_email, password_hash, created_at (UTC), roles (set: customer, artist pending/approved), display_name
- Optional attributes: bio, profile_picture_url (S3 reference), phone, locale, metadata
- Relationships: 1-to-many ArtistProfile, 1-to-many Orders (as customer), 1-to-many Listings (as artist), Reviews given, Follows
- Business rules: Single User may hold both Customer and Artist capabilities; enabling artist capability requires ArtistVerification approval.
- Validation rules: email format, password complexity on creation, unique email constraint, UUID primary key
- Statuses: active, pending_verification, suspended, deleted
- Creation conditions: On sign-up with unique email
- Update conditions: Profile edits, role changes upon verification
- Deletion/archive: Prefer soft delete (mvp: only when business requires). If soft-delete, cascade rules must be explicit (e.g., preserve orders and audit logs)
- Audit requirements: track created_by, created_at, updated_by, updated_at. Log critical events (login, password reset, role changes)
- Security/privacy: store password as salted hash (bcrypt/argon2). PIIs protected and encrypted at rest if required. Limit exposed fields in API responses.
- MVP/Future: MVP: core fields, authentication, roles. Future: advanced identity (SSO, multi-factor)

## CUSTOMER CAPABILITY / PROFILE
- Entity ID: customer_profile
- Official Name: Customer Capability / Profile
- Definition: Projection of User capturing attributes specific to the customer role.
- Purpose: Store customer-specific preferences, address book, purchase history pointers.
- Aggregate: user aggregate (customer profile is a child)
- Aggregate Root: User
- Ownership: Owned by User
- Lifecycle: created when user uses customer features -> active -> archived/deleted
- Required attributes: id (UUID), user_id (FK), default_shipping_address_id
- Optional attributes: preferences, marketing_opt_in
- Relationships: belongs to User, has many ShippingAddress, Orders
- Business rules: no separate login; inherits user authentication
- Validation rules: FK to user exists
- Statuses: active, archived
- Creation conditions: lazily created when user first uses customer functionality
- Update conditions: user edits preferences / addresses
- Deletion/archive: follow user deletion policy; do not remove historical orders
- Audit requirements: track changes to addresses and payment preferences
- Security/privacy: protect stored addresses and payment metadata (do not store full card data)
- MVP/Future: MVP: minimal profile with addresses and opt-ins

---

## ARTIST PROFILE
- Entity ID: artist_profile
- Official Name: Artist Profile
- Definition: Projection of User with attributes required to present an artist and to manage listings.
- Purpose: Artist storefront, public bio, stats, verification status
- Aggregate: artist aggregate (root: ArtistProfile? or User as root — prefer User as root with ArtistProfile as owned child)
- Aggregate Root: User (recommended)
- Ownership: Owned by User
- Lifecycle: not_applied -> pending -> approved -> suspended -> rejected
- Required attributes: id (UUID), user_id (FK), display_name (store front), public_bio, allow_offers (boolean default false), verification_status
- Optional attributes: social_links, location, shipping_policies, payout_details_reference (external token)
- Relationships: User, Listings (Artworks/Products), Reviews (received), Analytics metrics
- Business rules: artist capability active only after verification_status == approved; allow_offers can be toggled per product or at artist level as default
- Validation rules: unique storefront name if applicable
- Statuses: not_applied, pending, approved, rejected, suspended
- Creation conditions: created when user applies for artist capability or when user toggles artist intent
- Update conditions: admin actions for verification, artist edits profile
- Deletion/archive: preserve listings and orders; mark profile suspended or removed
- Audit requirements: log verification decisions and profile changes
- Security/privacy: payout details stored as references to external vault, not raw financial data
- MVP/Future: MVP: essential public info and verification state

## ARTWORK / PRODUCT
- Entity ID: product (artwork)
- Official Name: Product (Artwork)
- Definition: An item offered for sale by an artist. Can be physical or digital; can be unique or quantity-based.
- Purpose: Represent sellable inventory and pricing for marketplace operations
- Aggregate: Product aggregate (root: Product)
- Aggregate Root: Product
- Ownership: Owned by artist (user_id) but logically belongs to marketplace for order lifecycle
- Lifecycle: draft -> published -> available -> reserved (negotiated hold) -> sold/out_of_stock -> archived
- Required attributes: id (UUID), artist_id (FK to user), title, type (physical|digital), supply_type (unique|quantity), base_price, currency, status (published/draft), created_at
- Optional attributes: description, dimensions, year, sku, metadata, private_minimum_price (for negotiation, encrypted/hidden), published_at
- Relationships: ProductMedia, Inventory (for quantity-based), Category/Tags, Offers, Orders (via OrderItem)
- Business rules: negotiated accepted price must be preserved per order; product price change must not retroactively alter existing orders/agreements
- Validation rules: if type == physical then shipping applies; if supply_type == unique then inventory quantity must be 1 and immutable
- Statuses: draft, published, available, disabled, archived
- Creation conditions: created by artist or via API
- Update conditions: artist edits; price changes create audit trail
- Deletion/archive: do not hard-delete if referenced by historical orders; archive instead
- Audit requirements: record changes to price, ownership transfers, and publication events
- Security/privacy: media stored in S3; private_minimum_price only accessible to artist/admin, not to customers
- MVP/Future: MVP: publishable products with inventory for quantity-based and unique support; future: complex variants, editions

## PRODUCT MEDIA
- Entity ID: product_media
- Official Name: Product Media
- Definition: Metadata record referencing artwork media stored in S3 (images, download files)
- Purpose: Provide references and metadata for product presentation
- Aggregate: product aggregate
- Aggregate Root: Product
- Ownership: Owned by Product (artist uploader)
- Lifecycle: uploaded -> attached -> removed
- Required attributes: id (UUID), product_id (FK), media_type (image|download|preview), s3_key/url, mime_type, width/height (if image)
- Optional attributes: alt_text, order_index
- Relationships: Product
- Business rules: do not store binary in DB; store only metadata and references
- Validation rules: validate mime-type and size at upload service
- Statuses: active, removed
- Creation conditions: upload by artist
- Update conditions: replace media or reorder
- Deletion/archive: remove metadata and delete S3 only after ensuring no historical requirement; consider retention policy
- Audit requirements: log uploads/deletes
- Security/privacy: signed URLs for private assets; access control for downloadable digital goods
- MVP/Future: MVP: images and downloadable files behind controlled access

## DIGITAL ASSET
- Entity ID: digital_asset
- Official Name: Digital Asset
- Definition: Representation for downloadable or deliverable digital products, including storage and entitlement metadata
- Purpose: Manage delivery of purchased digital goods
- Aggregate: product or license aggregate
- Aggregate Root: Product
- Ownership: Owned by Product (and by order/license after purchase)
- Lifecycle: created -> available -> assigned to order/license -> revoked
- Required attributes: id, product_id, s3_key/reference, access_policy, max_downloads, expiry
- Optional: checksum, file_size
- Relationships: Product, OrderItem, License/Entitlement
- Business rules: entitlement issuance at successful order completion; revocation policy for refunds
- Validation: ensure file exists in S3
- MVP: basic delivery metadata and secure URLs

## CATEGORY
- Entity ID: category
- Official Name: Category
- Definition: Hierarchical (optional) classification of products
- Purpose: Navigation and search filtering
- Aggregate: category catalog
- Aggregate Root: Category
- Ownership: Admin-managed
- Required: id, name, slug, parent_id (nullable)
- Optional: description, display_order
- Relationships: ProductCategory join table
- Business rules: category hierarchy depth limited
- MVP: simple category list

## TAG
- Entity ID: tag
- Official Name: Tag
- Definition: Non-hierarchical label for products
- Purpose: flexible discovery and filtering
- Required: id, name, slug
- Relationships: ProductTag join
- MVP: yes

## COLLECTION
- Entity ID: collection
- Official Name: Collection
- Definition: Curated grouping of products (created by artist or admin)
- Purpose: Present themed sets
- Required: id, owner_id, title, visibility (public/private)
- Relationships: collection_items (product_id, order_index)
- MVP: optional (future) but useful for artist pages

---

## INVENTORY
- Entity ID: inventory
- Official Name: Inventory
- Definition: Tracks stock for quantity-based products; unique products have inventory entry quantity=1
- Purpose: Prevent oversell and manage stock
- Aggregate: Product
- Required: id, product_id (FK), quantity_available, reserved_quantity
- Optional: location, restock_date
- Business rules: reservations (holds) when negotiation accepted or cart checkout in progress; release after expiration
- Validation: quantity >= 0
- MVP: required for quantity-based products; unique products simply set quantity 1 and mark sold

---

## WISHLIST / FAVORITE
- Entity ID: favorite (wishlist)
- Official Name: Favorite (or Wishlist)
- Definition: User-saved reference to product
- Purpose: user engagement and follow-up actions
- Required: id, user_id, product_id, created_at
- Relationships: User, Product
- Business rules: idempotent add operation
- MVP: favorite simple table

---

## CART and CART ITEM
- Entity ID: cart, cart_item
- Official Name: Cart, Cart Item
- Definition: Ephemeral shopping cart for a user or session; cart items reference products and snapshot prices
- Purpose: Collect items prior to order creation
- Required (cart): id, user_id (nullable for guest), created_at, updated_at
- Required (cart_item): id, cart_id, product_id, quantity, unit_price_snapshot, added_at
- Business rules: unit_price_snapshot captures price at add or at checkout decision; expiration policy for guest carts; inventory reservation is not automatic (only at checkout or explicit hold)
- MVP: simple cart with item snapshots

---

## ORDER and ORDER ITEM
- Entity ID: order, order_item
- Official Name: Order, Order Item
- Definition: Completed purchase intent processed by FANNAN; order items capture finalized prices and references
- Purpose: Primary business transaction record; source of truth for fulfillment and payments
- Required (order): id (UUID), user_id (buyer), total_amount, currency, status, created_at, payment_method (enum), shipping_address_id (nullable for digital), shipping_required (bool)
- Required (order_item): id, order_id, product_id, artist_id (seller), quantity, unit_price, total_price, product_snapshot (title, sku, media ref)
- Relationships: Payment(s), Shipment(s), OrderItem -> Product
- Business rules: order status machine (pending -> paid -> fulfilled -> completed/closed/cancelled -> refunded). For negotiated purchases, order should reference negotiated_agreement_id.
- Validation: totals reconcile with item sums and taxes/shipping
- Deletion/archive: never hard-delete; archive for data retention
- Audit: log status transitions
- MVP: support Cash-on-Delivery and later online payments

---

## PAYMENT
- Entity ID: payment
- Official Name: Payment
- Definition: Record of payment attempt/settlement associated with an order
- Purpose: Track payment lifecycle and reconcile with orders
- Required: id, order_id, amount, currency, method, status, provider_reference, created_at
- Statuses: pending, succeeded, failed, refunded
- Business rules: idempotent provider callbacks; do not store full payment credentials
- MVP: support Cash-on-Delivery as default; provider-agnostic schema

---

## SHIPPING, SHIPPING ADDRESS, SHIPMENT
- Entity ID: shipping_address, shipment
- Official Name: Shipping Address; Shipment
- Definition: Address records and shipment units representing fulfillment by shipping provider
- Purpose: Support physical product delivery
- Shipping Address: id, user_id, recipient_name, line1/line2, city, postal_code, country, phone
- Shipment: id, order_id, shipment_status, provider_id (FK to shipping_provider table), tracking_number, cost, shipped_at, delivered_at
- Business rules: multiple shipments per order allowed; shipment applies only to physical items
- MVP: basic address and shipment tracking with provider-agnostic provider reference

---

## REVIEW
- Entity ID: review
- Official Name: Artist Review
- Definition: Customer-provided feedback about an artist after eligible completed purchase
- Purpose: Reputation system for artists
- Required: id, artist_id, user_id (reviewer), order_id (nullable or required), rating (1-5), content, created_at
- Business rules: review allowed only after eligible completed purchase and within allowed window; 1 review per order per customer
- MVP: reviews for artists only

---

## FOLLOW
- Entity ID: follow
- Official Name: Follow
- Definition: User follows an artist
- Required: id, follower_user_id, artist_user_id, created_at
- Business rules: idempotent; cannot follow oneself
- MVP: simple follow table

---

## NOTIFICATION
- Entity ID: notification
- Official Name: Notification
- Definition: System notification record for user; supports delivery channels
- Purpose: track and deliver notifications (email/push/in-app)
- Required: id, user_id, type, payload (json), status (queued/sent/failed/read), created_at
- Business rules: do not store sensitive PII in payload; expire old notifications per retention
- MVP: basic notification queue and audit

---

## OFFER and NEGOTIATION
- Entity ID: offer, negotiation, offer_event
- Official Name: Offer, Negotiation, Offer Event / History
- Definition: Structured offers made by customers on a product and the lifecycle events representing negotiation rounds
- Purpose: Support negotiation flows with finite rounds
- Offer (conceptual): id, product_id, offeror_id (user), proposed_price, currency, quantity, status (pending/accepted/rejected/countered/withdrawn/expired/cancelled), created_at, expires_at
- Negotiation: grouping of offers for one negotiation session (negotiation_id) with finite rounds, participant references, current_round
- Offer Event / History: immutable event log per offer/negotiation capturing timestamps, actor, action, message, resulting_status
- Relationships: Offers -> Product, Negotiation -> Product & Artist, OfferEvent -> Offer/Negotiation
- Business rules: artist private minimum price must be stored only in encrypted or separate domain not exposed; accepted negotiation can produce a reserved Order opportunity; agreed price snapshot stored on created order; negotiation rounds limited and may expire
- Validation: ensure only allowed quantity, offeror not artist, price > 0
- MVP: basic offer/negotiation with server-side enforced rounds and event history

---

## NEGOTIATED AGREEMENT
- Entity ID: negotiated_agreement
- Official Name: Negotiated Agreement
- Definition: Persisted agreement representing accepted negotiation terms that can be converted to an order
- Required: id, negotiation_id, agreed_price, currency, agreed_quantity, expires_at, created_at
- Business rules: once converted to order, snapshot agreed_price must be copied into order_item; agreement may hold inventory reservation
- MVP: yes, to enable negotiated purchase

---

## ADMIN MODERATION ENTITIES
- Entity ID: moderation_action, moderation_queue_item
- Official Name: Moderation Action / Queue Item
- Definition: Records for content moderation decisions and pending moderation tasks
- Required: id, target_type (user/product/media), target_id, action_type, actor_admin_id, reason, status, created_at
- Business rules: moderation decisions may affect product/artist statuses and must be auditable
- MVP: minimal moderation logs and a queue table

---

## AUDIT LOG
- Entity ID: audit_log
- Official Name: Audit Log
- Definition: Immutable event log capturing important domain events and administrative actions
- Required: id, actor_id (user/admin/system), target_type, target_id, action, payload, occurred_at
- Business rules: retention and access controls; do not store sensitive raw credentials
- MVP: required for admin review and dispute resolution

---

## SHIPPING PROVIDER (REFERENCE)
- Entity ID: shipping_provider
- Official Name: Shipping Provider
- Definition: Abstraction record for an external shipping provider integration
- Required: id, name, provider_key, config_reference
- Business rules: provider-agnostic references in shipments; provider config stored in secure vault

## NOTES ON MODELING DECISIONS
1. Use UUIDs for all primary keys unless a specific reason exists.
2. Prefer normalized relational modeling: reference tables and join tables for many-to-many (ProductTag, ProductCategory, CollectionItem).
3. Avoid creating separate top-level tables for transient UI concepts (e.g., UI-only presentation state should not become DB tables).
4. Use explicit join tables: product_tags (product_id, tag_id), product_categories (product_id, category_id).
5. Inventory and product are in the same aggregate; inventory changes should be performed in transactions to preserve invariants.
6. For negotiation, separate negotiation (session) and offer (event) tables with immutable offer event history to support auditing and replay.
7. Review the 02_PRODUCT_REQUIREMENTS documents for any domain-specific fields; this document aligns with them. Any conflicts discovered should be documented and flagged for product clarification.
