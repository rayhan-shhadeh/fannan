# 5.14 Observability & Logging Architecture

## 1. Purpose

This document defines how FANNAN understands system health, behavior,
performance, and failure. Its operating loop is:

**Detect -> Diagnose -> Resolve -> Learn**

Observability must make it possible to answer what happened, when it happened,
which request or business operation was affected, whether data or money was at
risk, and what action is required without turning telemetry into a source of
data leakage.

## 2. Scope

This architecture covers the web and mobile clients, Laravel API, queue
workers, scheduled jobs, PostgreSQL, Redis, media storage and processing,
search, notifications, payment and shipping providers, infrastructure,
deployment, audit records, and operational dashboards.

It defines logs, metrics, error events, traces/correlation, health checks,
alerts, retention, troubleshooting, and MVP monitoring. It does not define
new product behavior, authorization rules, payment states, notification
channels, or data-retention periods; those remain owned by their respective
architecture and product documents.

## 3. Observability Principles

1. **Purpose-driven telemetry:** Collect telemetry to operate, secure, support,
   and improve FANNAN, not merely because it is available.
2. **Structured first:** Machine-readable events are the primary interface;
   human-readable messages are a presentation of structured fields.
3. **Correlation over guesswork:** Every request and asynchronous business
   operation has safe identifiers that connect logs, metrics, errors, and
   provider interactions.
4. **Authoritative state:** Telemetry describes authoritative API, database,
   queue, and provider outcomes. Client optimism or stale cache is never
   reported as completed business success.
5. **Minimum necessary data:** Do not log secrets, credentials, full addresses,
   private content, or raw payloads when a classification, status, hash, or
   safe reference is sufficient.
6. **Actionable alerts:** Alert only when an owner can investigate or act.
   Alerts have severity, impact, runbook, and escalation.
7. **Separate operational and audit concerns:** Debugging telemetry may expire
   sooner; durable audit evidence follows policy and [4.7 Data
   Lifecycle](4.7%20Data%20Lifecycle.md).
8. **Client parity:** Web and mobile emit equivalent operational outcomes
   without becoming authorities or exposing internal diagnostics.
9. **Failure is a state:** Pending, rejected, delayed, retried, and failed
   outcomes remain visible and distinguishable.
10. **MVP simplicity:** Start with a small, reliable set of logs, metrics,
    dashboards, and alerts that can evolve without premature enterprise cost.

## 4. Observability Model

FANNAN uses four complementary signal types:

- **Logs:** Discrete events with context, useful for exact diagnosis and audit.
- **Metrics:** Aggregated numeric measurements for health, trends, capacity,
  and alert thresholds.
- **Errors:** Exception and failure records with stack/context grouping,
  release/environment information, and safe request correlation.
- **Traces/correlation:** Relationships between a client request, API work,
  database calls, queue jobs, provider calls, and resulting business events.

The minimum diagnostic path is:

1. A client or provider interaction receives a request/correlation identifier.
2. The API records outcome, latency, status, and safe actor/resource context.
3. Domain transitions emit metrics and business events.
4. Queued work preserves the correlation context and records retries/final
   outcomes.
5. Dashboards link the metric to representative logs and errors.
6. Operators use the relevant runbook and record resolution and follow-up.

Telemetry systems are not a replacement for PostgreSQL, the API authorization
authority, payment reconciliation, or an audit ledger.

## 5. Structured Logging

All backend, worker, scheduler, provider-adapter, and infrastructure logs use
structured JSON or an equivalent schema. A normal event contains:

| Field | Meaning |
| --- | --- |
| `timestamp` | UTC event time from a synchronized service clock. |
| `level` | `debug`, `info`, `notice`, `warn`, `error`, or `critical`. |
| `service` | API, worker, scheduler, media, notification, or provider adapter. |
| `environment` | Development, test, staging, or production. |
| `release` | Deploy or application version safe identifier. |
| `event` | Stable event name, such as `checkout.completed` or `media.rejected`. |
| `request_id` | Identifier for one inbound request, when applicable. |
| `correlation_id` | Identifier for a distributed or business operation. |
| `actor_type` | Guest, customer, artist, staff, service, or provider, when safe. |
| `resource_type` | Safe domain type, such as order, artwork, or shipment. |
| `resource_ref` | Non-sensitive internal reference or redacted identifier. |
| `outcome` | Success, rejected, pending, retry, timeout, or failure. |
| `duration_ms` | Measured operation duration, where applicable. |
| `error_code` | Stable safe error classification, not a stack or secret. |
| `provider` | Approved provider name, never its credential. |

Events use stable names and bounded values so dashboards and alerts do not
depend on parsing prose. High-cardinality values, request bodies, response
bodies, headers, SQL, stack traces, and user-authored text are excluded from
normal logs or redacted before collection.

Logs are emitted at the event boundary that knows the outcome. A controller
must not log a successful request before the domain operation or transaction
has succeeded.

## 6. Log Levels

| Level | Use | Production guidance |
| --- | --- | --- |
| `debug` | Detailed diagnostic context for local or temporary investigations. | Disabled or tightly sampled by default; never a place for secrets. |
| `info` | Normal lifecycle events and meaningful successful operations. | Enabled for key request, job, provider, and business transitions. |
| `notice` | Expected but operationally important conditions, such as degraded provider mode or a policy decision. | Retained and dashboarded where it indicates a trend. |
| `warn` | Recoverable anomaly, retry, rejected input, approaching limit, or degraded dependency. | Must be actionable or trendable; avoid alert fatigue. |
| `error` | Operation failed and requires investigation or recovery, but service continues. | Includes safe error classification and correlation. |
| `critical` | Service-wide, security-critical, data-integrity, or payment-impacting failure requiring immediate response. | Pages the responsible owner according to the alert policy. |

Expected user validation failures are normally metrics or `info`/`notice`
events, not errors. Repeated validation abuse may additionally produce a
security event.

## 7. Request & Correlation IDs

- Every inbound API request receives a server-generated `request_id`, unless
  a validated, bounded incoming identifier is accepted for cross-system
  troubleshooting. The server remains responsible for format and uniqueness.
- A `correlation_id` connects one business operation across synchronous calls,
  queue jobs, retries, provider calls, notifications, and reconciliation.
- Request and correlation IDs are opaque, non-secret, non-user-controlled
  identifiers. They must not encode email, phone, address, token, or payment
  information.
- IDs are returned to clients only when useful for support and are safe to
  expose. They are not authorization credentials.
- Queue payloads preserve correlation context but exclude authentication
  headers, bearer tokens, raw provider bodies, and unnecessary personal data.
- Provider request IDs and webhook event IDs are stored as safe references
  where needed for reconciliation.
- Client retries may use an idempotency key for eligible operations; it is
  distinct from a request ID and must be redacted from public diagnostics if it
  could authorize replay.
- Logs from API, workers, database instrumentation, cache, media, and
  providers use the same correlation fields where technically possible.

## 8. Error Tracking

Error tracking groups failures by stable type, location, release, environment,
service, and sanitized operation context.

- Capture unhandled exceptions, failed jobs, provider timeouts, callback
  verification failures, database errors, media-processing failures, and
  client crashes that affect supported flows.
- Record safe stack/context, release, deployment, route or job name, request
  and correlation IDs, and user-impact classification.
- Do not attach request bodies, authorization headers, cookies, passwords,
  tokens, payment data, full addresses, private media links, or raw provider
  payloads.
- Group duplicates so one outage produces one actionable issue rather than
  thousands of alerts.
- Mark expected validation, authorization denial, user cancellation, and
  provider-declared business rejection separately from defects.
- Link errors to the relevant log search, metric, runbook, and deployment.
- Client error reporting is opt-in to approved fields and must honor consent,
  privacy, and the web/mobile redaction policy.
- Error tracking must support release health and regression comparison without
  becoming a shadow analytics or user-profile system.

## 9. Metrics

Metrics use stable names, units, labels, and aggregation windows. Labels are
bounded; do not use user IDs, email addresses, full resource IDs, search text,
addresses, or arbitrary exception messages as metric labels.

The baseline metric families are:

- **Availability:** successful, failed, and unavailable operations.
- **Latency:** request, job, dependency, database, cache, and provider
  duration, including p50, p95, and p99 where volume supports it.
- **Traffic:** requests, jobs, uploads, searches, notifications, and payment
  attempts.
- **Errors:** classified failures, timeouts, retries, rejected input, and
  authorization denials.
- **Saturation:** CPU, memory, storage, connections, queue depth, worker
  capacity, Redis memory, and provider quotas.
- **Business state:** orders, payments, shipments, publishing, onboarding,
  and notifications by safe state.

Metrics are aggregated before export where possible and are not a mechanism to
store event-level personal data.

## 10. Application Metrics

The Laravel API and workers expose:

- Request count, outcome, latency, uncaught exception count, validation
  failures, authorization denials, throttles, and queue dispatch failures.
- Queue depth, age of oldest job, processing duration, retry count, dead-letter
  count, scheduler lateness, and worker utilization.
- Domain transition counts and failures for registration, artist approval,
  product publication, checkout, order creation, payment, shipping,
  notifications, search, and media.
- Cache hit/miss, stale/revalidation, invalidation, and isolation-failure
  counters.
- Configuration, release, migration, and feature-flag changes as audit events.

Application metrics distinguish public reads, authenticated reads, mutations,
staff actions, and provider time from FANNAN processing time. This prevents a
slow external provider from being mistaken for slow application code.

## 11. API Metrics

For each documented route or safe route group, measure:

- Request rate by method and route template, not raw URL.
- Status-class distribution and stable error codes.
- p50/p95/p99 latency and timeout count.
- Payload size, pagination usage, rate-limit responses, and authentication/
  authorization outcomes.
- Dependency duration and result for database, cache, queue, search, media,
  payment, shipping, and notification calls.

Security-sensitive endpoints such as login, recovery, upload, checkout,
payment, export, and admin bulk actions have separate dashboards and tighter
thresholds. API metrics must not reveal whether a particular private account
exists.

## 12. Database Metrics

PostgreSQL monitoring includes:

- Connection usage, saturation, failed connections, transaction rate, commit
  and rollback counts, lock waits, deadlocks, and long-running transactions.
- Query latency and error rate by safe query or operation group, not raw
  sensitive SQL or values.
- Replication/backup status where applicable, storage growth, table/index
  health, vacuum/analyze health, and migration duration.
- Constraint violations, serialization/deadlock retries, and transaction
  failures for checkout, payment, order, shipping, and ownership operations.
- Privilege, schema, migration, export, and unusual access events through the
  audit/security channel.

Database logs are redacted and access-controlled. Slow-query diagnostics use
parameterized or normalized statements and never expose bound personal data.

## 13. Redis Metrics

Monitor:

- Availability, connection count, command latency, memory usage, eviction,
  expiration, persistence/replication status, and blocked clients.
- Cache hit/miss and stale rates by safe cache class.
- Rate-limit counter growth, queue depth, consumer lag, retry/dead-letter
  behavior, and serialization/deserialization failures.
- Lock contention, lock expiry, duplicate-work prevention, and invalidation
  failures for critical operations.

Redis telemetry must not include raw values, session tokens, private payloads,
or key names containing personal data. A cache isolation failure is a
security event and a critical operational signal.

## 14. Infrastructure Metrics

At MVP, monitor the deployed hosts, containers, or managed services for:

- CPU, memory, disk, network, file descriptors, process restarts, and
  container/service availability.
- TLS certificate expiry, DNS/edge availability, load balancer health, and
  deployment/rollback state.
- PostgreSQL, Redis, object storage, queue, and provider connectivity.
- Backup completion, backup age, restore-test result, and storage capacity.
- Worker and scheduler liveness, time synchronization, and log pipeline
  delivery health.

Infrastructure identifiers are environment and service scoped. Monitoring
credentials are separate from application credentials and have read-only
access where possible.

## 15. Business Metrics

Business metrics measure whether FANNAN works for its users, not just whether
servers respond:

- Registration, verification, artist onboarding and approval funnel.
- Artwork upload, moderation, publication, suspension, and removal funnel.
- Search requests, result quality signals, zero-result rate, and indexing lag.
- Cart, checkout, order creation, cancellation, return, and recovery states.
- Payment authorization/capture/failure/refund/settlement and reconciliation.
- COD order creation, confirmation, fulfillment, delivery, refusal, and
  reconciliation states where COD is enabled.
- Shipment creation, label/rate failures, tracking freshness, delivery
  exceptions, returns, and provider mismatch.
- Notification queued, sent, delivered, failed, suppressed, retried, and
  preference-blocked outcomes by channel.
- Media upload, quarantine, processing, rejection, derivative delivery, and
  access failures.

Business dashboards use aggregation and role-appropriate access. They do not
expose customer-level histories or private content to unauthorized viewers.

## 16. Domain-Specific Observability

### Authentication and authorization

Track sign-in/recovery/verification outcomes, session failures, suspicious
velocity, authorization denials, role changes, and session revocation. Do not
log credentials or token material. Refer to 5.5 for behavior and to 5.13 for
security-event handling.

### Artist approval and product publication

Track applications, review queue age, approval/rejection/suspension counts,
moderation failures, publication latency, visibility transitions, and cache
invalidation. Correlate the artist, artwork, reviewer role, and decision using
safe references, not private evidence or original files.

### Checkout and order creation

Track cart validation failures, stale availability/price conflicts, address
and shipping validation, idempotency conflicts, order transaction duration,
duplicate prevention, and pending/recovery states. A successful checkout
metric requires authoritative order state, not a client click.

### Payment and COD

Track provider initiation, authorization/capture, failure, timeout, callback,
refund, payout, reconciliation, and dispute states. For COD, separately track
order confirmation, dispatch, delivery/refusal, collection or settlement
confirmation, and exceptions. Never log card data, credentials, signatures,
full provider payloads, or unnecessary cash/customer details.

### Shipping and shipment tracking

Track rate requests, label creation, shipment creation, provider callbacks,
tracking freshness, state transitions, delivery exceptions, returns, and
reconciliation. Use shipment/order references, provider event IDs, and
country/region aggregates where useful, not full addresses.

### Notifications

Track event eligibility, preference decision, queue age, provider acceptance,
delivery/failure, retry, suppression, and final disposition per channel.
Security-sensitive notifications have separate reliability indicators.
Telemetry records template/version and safe category, never message bodies,
tokens, or sensitive content.

### Search

Track request volume, latency, zero-result rate, indexing lag, stale-index
events, parser failures, filter errors, and cache behavior. Search text is
potentially personal or sensitive: do not log raw queries by default. If
approved for quality analysis, use redaction, aggregation, sampling, and the
retention policy.

### Media

Track upload acceptance/rejection, quarantine age, scan/transformation
failures, derivative generation, storage errors, authorization failures,
download/preview latency, and cache/CDN errors. Do not log private signed URLs,
raw files, EXIF data, or artwork content.

## 17. Health Checks

Health checks are explicit and minimal:

- **Liveness:** The process is running and able to serve its basic runtime
  loop. It must not depend on every external provider or deep database query.
- **Readiness:** The instance can safely receive the traffic assigned to it,
  including required configuration and essential dependencies.
- **Dependency health:** Separate checks measure PostgreSQL, Redis, queue,
  object storage, search, and provider reachability with timeouts.
- **Business health:** Separate synthetic or scheduled checks validate critical
  workflows such as authentication, checkout/order creation in a safe test
  path, payment callback processing, and notification dispatch.

Health endpoints expose only status, safe component names, version, and
correlation information. They do not expose credentials, connection strings,
stack traces, customer data, or detailed provider responses. Readiness may
remove an instance from service; liveness must not cause restart loops merely
because an external provider is temporarily unavailable.

## 18. Alerting

Alerts are based on user impact, error budget, security significance, and
trend, not on every log line.

| Severity | Meaning | Example |
| --- | --- | --- |
| Critical | Immediate risk to availability, money, privacy, or integrity. | Payment callback outage, cross-user cache exposure, database loss, secret compromise. |
| High | Major degradation or rapidly growing failure requiring prompt action. | Checkout errors above threshold, queue backlog threatening order/notification SLAs. |
| Medium | Material issue with workaround or limited scope. | Search indexing lag, elevated media rejection, repeated provider retries. |
| Low | Informational trend or maintenance need. | Capacity growth, certificate nearing renewal, isolated non-critical job failure. |

Each alert includes service, environment, symptom, first observed time,
current impact, request/correlation examples, safe dashboard links, owner,
runbook, and escalation. Alerts are deduplicated, rate-limited, and tested.
Pager or equivalent notification is reserved for critical/high signals.

## 19. Audit Logging

Audit logging records durable, reviewable actions that affect access, users,
content, commerce, money, privacy, or operational governance:

- Role/capability changes, account state, authentication administration, and
  staff access.
- Artist approval, moderation, publication, suspension, and media visibility.
- Orders, payment/refund/payout decisions, shipping changes, and manual
  adjustments.
- Exports, privacy requests, deletion/retention exceptions, configuration,
  provider, secret, deployment, and backup actions.

Audit events contain timestamp, actor/service, action, target type and safe
reference, outcome, reason, correlation ID, and before/after state summary
where permitted. They do not contain secrets, credentials, raw payloads,
full addresses, payment data, or unnecessary private content.

Audit records are append-oriented, access-controlled, tamper-evident where
available, and retained under 4.7. Reading audit logs is itself restricted
and observable.

## 20. Security Event Logging

Security events are a distinct, queryable class for:

- Authentication failures, recovery anomalies, token/session revocation, and
  suspicious account activity.
- Authorization denials, IDOR patterns, privilege changes, staff-scope
  violations, enumeration, scraping, and rate-limit abuse.
- Invalid webhook signatures, replay attempts, malicious file detections,
  cache isolation failures, secret exposure, and unexpected exports.
- Database privilege changes, dependency/deployment anomalies, and provider
  credential failures.

Security events include safe classification, severity, actor/service context,
request/correlation ID, target category, outcome, and response action. They
are routed to security monitoring with stricter access than ordinary
application logs. The event itself must not reveal the protected secret or
private data that triggered it.

## 21. Sensitive Data Protection

The following must **never** be logged, emitted as metric labels, attached to
error reports, placed in traces, or included in ordinary alerts:

- Passwords, password hashes, reset values, access tokens, refresh tokens,
  session cookies, API keys, signing secrets, encryption keys, and credentials.
- Payment credentials, card numbers, security codes, bank credentials,
  provider authentication material, or raw signed webhook content.
- Full shipping addresses, private phone/email values, identity documents,
  private support/commission messages, and unnecessary personal data.
- Private or expiring media URLs, signed storage URLs, original private files,
  EXIF/location metadata, and raw artwork content.
- Raw request/response bodies, authorization headers, cookies, query strings
  containing secrets, SQL with bound values, and arbitrary user text.

Use redaction at the producer and collector boundary, allowlisted fields,
masked references, bounded enums, one-way fingerprints only where justified,
and access controls. Redaction failures are security events. Developers must
not enable verbose logging in production as a first response to an incident
without a reviewed, time-bounded, redacted configuration.

## 22. Log Retention

Retention follows [4.7 Data Lifecycle](4.7%20Data%20Lifecycle.md), legal
requirements, contractual provider obligations, and the purpose of each
signal:

- Short-lived debug and request detail is retained only as long as needed for
  active diagnosis.
- Application and dependency logs are retained for operational trend and
  incident investigation within the approved MVP period.
- Security and audit events use a longer, policy-defined retention period.
- Metrics are downsampled or aggregated for historical capacity and business
  trends.
- Error groups and release records are retained for regression analysis while
  their attached context remains minimized.
- Backups and exported observability data are encrypted, access-controlled,
  expiry-managed, and included in deletion/retention reviews.

Retention must be documented per signal and environment. Deletion is itself
auditable. A legal hold or active incident may pause normal deletion with an
explicit owner and expiry/review date.

## 23. Troubleshooting & Diagnostics

The standard diagnostic workflow is:

1. Confirm the affected environment, user-facing symptom, start time, scope,
   and whether money, privacy, access, or data integrity is involved.
2. Start with availability, error rate, latency, queue age, provider, and
   deployment dashboards.
3. Use request and correlation IDs to follow one safe operation through API,
   database/cache, worker, provider, notification, and audit events.
4. Compare affected release, route, dependency, role, locale, device, and
   region aggregates without exposing user data.
5. Determine whether the issue is code, configuration, capacity, dependency,
   data, authorization, abuse, or provider behavior.
6. Apply the smallest safe mitigation: rollback, throttle, disable an
   integration, pause a queue, invalidate a cache, or move the workflow to
   pending/reconciliation.
7. Verify recovery through health, metrics, synthetic flow, and authoritative
   business state, not only a green process check.
8. Record the incident timeline, root cause, impact, corrective action, and
   follow-up test or architecture change.

Runbooks cover authentication, artist approval, publication, checkout/order
creation, payment/COD, shipping/tracking, notifications, search, media,
database, Redis, and provider outage scenarios.

## 24. MVP Scope

MVP observability includes:

- Structured redacted application, worker, scheduler, provider, security, and
  audit logs.
- Request and correlation IDs across synchronous and asynchronous work.
- Central log search, error grouping, basic dashboards, and safe release
  correlation.
- Application/API, PostgreSQL, Redis, infrastructure, queue, backup, and
  provider health metrics.
- Business-critical metrics for authentication, artist approval, publication,
  checkout/order creation, payment/COD, shipping/tracking, notifications,
  search, and media.
- Liveness/readiness/dependency checks, critical synthetic checks, and
  actionable alerts with owners and runbooks.
- Explicit redaction, retention, access control, and incident procedures.

MVP does not require a costly full distributed-tracing platform, a data lake,
real-time user-level behavioral profiling, universal client telemetry, or
custom machine-learning anomaly detection. Sampling and bounded correlation
are sufficient until traffic and operational evidence justify expansion.

## 25. Future Extensions

Future scale may add:

- OpenTelemetry-compatible traces across API, queues, database, cache, media,
  and providers with privacy-safe sampling.
- Service-level objectives, error budgets, automated burn-rate alerting, and
  dependency-aware topology views.
- Long-term metric storage, capacity forecasting, anomaly detection, and
  business data quality monitoring.
- Privacy-preserving session replay or client performance monitoring after
  consent and redaction review.
- Synthetic multi-region journeys, disaster-recovery observability, and
  provider failover dashboards.
- Tamper-evident centralized audit storage, security information/event
  integration, and automated evidence collection.
- Dedicated payment, fraud, fulfillment, and marketplace integrity analytics.

## 26. Alternatives Considered

| Alternative | Decision |
| --- | --- |
| Plain text application logs | Rejected. They are difficult to query consistently and encourage unsafe payload logging. |
| Logging every request and response body | Rejected. It creates unnecessary privacy, credential, and payment exposure. |
| Client-side telemetry as the authority | Rejected. Client signals are supplementary; server and provider outcomes are authoritative. |
| Redis or cache as the observability source of truth | Rejected. Redis is monitored, but durable business and audit state remains elsewhere. |
| Enterprise tracing and data lake at MVP | Deferred. Start with logs, metrics, errors, correlation, and targeted checks. |
| One threshold for every endpoint | Rejected. Authentication, checkout, payment, provider, and public reads have different impact and baselines. |
| Alert on every error log | Rejected. Classification, aggregation, severity, and user impact prevent alert fatigue. |

## 27. Tradeoffs

- **Detail versus privacy:** Correlation and safe references provide diagnosis
  without collecting raw payloads or private content.
- **Coverage versus cost:** MVP monitoring focuses on critical paths and
  dependencies; future scale can add high-volume traces and retention.
- **Freshness versus overhead:** Metrics and sampled traces are cheaper than
  recording every event synchronously. Critical audit events prioritize
  durability.
- **Alert sensitivity versus fatigue:** Thresholds and burn-rate signals need
  tuning as real traffic establishes baselines.
- **Business visibility versus profiling risk:** Aggregated funnel metrics
  support operations without creating unauthorized user profiles.
- **Health accuracy versus availability:** Readiness and business checks are
  separated from liveness so dependency failures do not create restart loops.

## 29. Consistency & Open Issues

- Request, correlation, idempotency, provider event, and audit identifiers
  must remain distinct and consistently named across API and workers.
- 5.5, 5.13, and this document must agree on security-event access,
  redaction, session/role-change visibility, and audit ownership.
- 5.9, 5.10, and 5.11 must expose enough safe state transitions to diagnose
  delivery, payment, COD, shipping, and reconciliation failures.
- 5.12 must define cache metrics and invalidation signals without allowing
  private data to enter shared telemetry.
- 4.7 must finalize retention periods and deletion behavior for logs, metrics,
  traces, audit events, security events, backups, and provider evidence.
- Operations must approve the MVP telemetry destination, on-call ownership,
  alert thresholds, runbooks, escalation paths, synthetic test accounts,
  provider dashboards, and restoration evidence before production.
- Launch-specific privacy, consent, data-residency, and legal requirements
  may change which client analytics or search data can be collected.
- Any new endpoint, provider, role, cache class, business-critical flow, or
  sensitive field requires an observability and redaction review.
