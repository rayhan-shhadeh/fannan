# 5.13 Security Architecture

## 1. Purpose

This document defines how security is applied across FANNAN as a system. It
protects people, artwork, marketplace state, payment and shipping workflows,
and the platform's operational controls across web, mobile, backend services,
databases, cache, media storage, external providers, and infrastructure.

This document complements, and does not replace, [5.5 Authentication &
Authorization](5.5%20Authentication%20%26%20Authorization.md). Document 5.5 is
the source of truth for authentication and authorization behavior. This
document defines the security controls that consume those decisions and apply
them consistently to every platform surface.

## 2. Scope

The scope includes:

- Responsive web, Flutter mobile, artist and customer dashboards, and admin
  operations.
- The Laravel REST API, queue workers, scheduled jobs, search and notification
  processing.
- PostgreSQL, Redis, S3-compatible media storage, backups, and delivery
  services.
- Payment, shipping, email, push, and other approved external providers.
- Security logging, monitoring, incident response, environment separation, and
  release controls.

The scope excludes defining new roles, permissions, login flows, token formats,
or provider contracts. Those remain governed by the relevant architecture and
product documents.

## 3. Security Principles

1. **Server authority:** The API independently authenticates, authorizes,
   validates, and transitions state. A screen, route, hidden field, cached
   flag, or client claim is never an authority.
2. **Deny by default:** Unknown users, roles, permissions, resource
   relationships, states, and provider messages are rejected safely.
3. **Least privilege:** Each user, service, worker, database credential, and
   provider integration receives only the access required for its task.
4. **Explicit ownership:** Access is checked against the authenticated
   principal, role scope, and target resource ownership or relationship.
5. **Public by eligibility, private by default:** Only approved, eligible
   public content is exposed publicly. Drafts, internal notes, private
   requests, addresses, and operational data remain protected.
6. **Minimize data:** Collect, return, log, cache, and retain only what is
   necessary for the documented purpose.
7. **Defense in depth:** Controls are layered across clients, API, domain
   services, persistence, infrastructure, providers, and operations.
8. **Fail closed:** Ambiguous authorization, invalid signatures, stale
   versions, provider errors, and incomplete confirmation produce a safe
   pending or error state rather than an implied success.
9. **Safe observability:** Security events are auditable without recording
   passwords, tokens, secrets, payment credentials, or unnecessary personal
   data.
10. **Recoverability:** Security controls preserve idempotency, backups,
    reconciliation, and evidence needed to recover from mistakes or attacks.
11. **Consistent clients:** Web and mobile may differ in presentation, but not
    in server-enforced security outcomes.
12. **Privacy-aware localization:** Arabic and English messages must not reveal
    more information merely because a different locale or channel is used.

## 4. Threat Model

FANNAN is an MVP marketplace with public discovery, private accounts, artist
catalogues, checkout, payments, shipping, notifications, and staff
operations. The principal actors are:

- An unauthenticated internet user browsing public content.
- A legitimate customer, artist, moderator, support agent, or administrator.
- A compromised account or device.
- An attacker manipulating requests, files, links, clients, or provider
  callbacks.
- A compromised dependency, provider credential, worker, or infrastructure
  component.
- An accidental or malicious insider with excessive staff access.

Realistic threats and primary controls are:

| Threat                                                   | Primary controls                                                                                                                                                                                |
| -------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Account takeover and credential stuffing                 | The authentication controls in 5.5, password hashing, login and recovery throttles, secure sessions, security notifications, and anomaly monitoring.                                            |
| IDOR and unauthorized resource access                    | Server-side ownership and policy checks on every protected read and mutation; opaque identifiers do not replace authorization.                                                                  |
| Privilege escalation or admin abuse                      | Explicit role scope, deny-by-default policies, separation of staff duties, re-authentication where required, audit records, and reviewable high-impact actions.                                 |
| Token, reset-link, or credential leakage                 | TLS, short-lived or revocable credentials as defined by 5.5, redaction, secure client storage, no secrets in URLs or logs, and restrictive notification content.                                |
| Malicious or deceptive file upload                       | Allowlisted types, size and dimension limits, content inspection, safe transformation, quarantine, non-executable storage, and moderation.                                                      |
| API scraping, brute force, and denial of service         | Per-principal and per-network rate limits, pagination caps, quotas, provider edge controls, and monitoring.                                                                                     |
| Payment manipulation or duplicate capture                | Server-calculated totals, provider-hosted/tokenized payment data, signed callbacks, idempotency, state validation, and reconciliation.                                                          |
| Shipping-address exposure                                | Field-level minimization, ownership checks, encrypted transport and storage controls, restricted staff access, and limited notification content.                                                |
| Webhook spoofing or replay                               | Provider signature verification, timestamp/replay controls, endpoint isolation, idempotent processing, and audit events.                                                                        |
| Cache authorization bypass                               | No shared caching of private responses, user-scoped keys where private caching is necessary, authoritative revalidation before sensitive actions, and cache invalidation on visibility changes. |
| Data leakage through search, analytics, or notifications | Public eligibility filtering, query and event minimization, role-scoped reporting, redaction, and consent/preferences.                                                                          |
| Dependency or provider compromise                        | Dependency review and updates, lockfiles, secret rotation, restricted egress, provider scopes, and incident disablement paths.                                                                  |

This is an MVP-focused threat model; it does not claim to address every
enterprise, nation-state, or future auction/NFT threat.

## 5. Trust Boundaries

The following boundaries require explicit validation and authorization:

1. **User device to public web/mobile client:** The device and client are
   untrusted. Client validation improves usability only.
2. **Client to Laravel API:** TLS protects transport; the API authenticates
   according to 5.5 and re-checks every request.
3. **API to domain and persistence layers:** Domain services enforce state,
   ownership, and business invariants before PostgreSQL writes or queue
   dispatch.
4. **API/worker to PostgreSQL:** Private network access, credential separation,
   parameterized queries, and database-level constraints protect durable data.
5. **API/worker to Redis:** Redis is a private support service, not an
   authorization authority. Values are treated as untrusted and scoped.
6. **API/worker to S3/media delivery:** Uploads and reads cross a storage
   boundary and require object-level policy, safe keys, and controlled URLs.
7. **FANNAN to external providers:** Payment, shipping, notification, and
   analytics providers receive only the minimum approved data and are never
   allowed to set internal state without validation.
8. **Staff to admin operations:** Staff access is a privileged boundary with
   role scope, audit, and separation of duties.
9. **Production to development/test:** Environments are isolated; production
   data and secrets are not copied into lower environments without an approved
   redaction process.

## 6. Attack Surface

The attack surface includes public pages, registration and recovery, login,
search, product and artist identifiers, checkout and order endpoints, payment
callbacks, shipping tracking, notification preferences, admin actions,
analytics ingestion, file uploads/downloads, media transformation, cache
keys, queue payloads, exports, health endpoints, database administration,
deployment pipelines, and provider credentials.

Every new endpoint or integration must document its actor, data classification,
authorization rule, validation, rate limit, audit requirement, failure state,
and owner before release.

## 7. Authentication Integration

- Authentication behavior, supported factors, session lifecycle, recovery,
  verification, and role assignment follow 5.5 exactly.
- Every protected request resolves one authenticated principal through the
  approved authentication mechanism. The API does not trust user IDs,
  role names, or capability claims supplied as ordinary request data.
- Guest access is limited to explicitly public operations. A guest must not
  infer private existence from response differences, identifiers, or errors.
- Authentication state changes, recovery, verification, device/session
  changes, and suspicious failures emit security events and use the approved
  notification policy from 5.9.
- A role change, suspension, account deletion, or credential compromise must
  invalidate or restrict affected sessions and cached capabilities according
  to 5.5.
- Web and mobile use the approved client integration and must not invent
  separate authentication stores or bypass API checks.

## 8. Authorization & Resource Ownership

5.5 remains the single authorization source of truth. System-wide integration
rules are:

- The API evaluates principal, role, capability, resource, relationship,
  current state, and requested action together.
- Resource ownership is explicit: customers own their account settings,
  addresses, wishlists, follows, saved searches, notifications, commissions,
  and orders as defined by product policy; artists own their approved
  profiles, drafts, catalogue workflows, and media within their scope.
- Ownership is not transferred by accepting an ID, guessing a URL, or copying a
  client-side object.
- Shared access, such as an artist's order context or staff support case, is
  granted only by an explicit documented relationship and minimum field set.
- Moderators and support agents cannot use operational access to obtain
  unrelated private, payment, or administrative data.
- Admin actions remain policy-bound and auditable; an Admin role is not a
  reason to bypass validation, state rules, or privacy minimization.
- Unknown roles, inactive roles, missing relationships, deleted resources, and
  stale permissions are denied without revealing protected details.
- Authorization-negative tests must cover cross-user, cross-artist, staff
  scope, role-change, deleted-resource, and direct-object-reference cases.

## 9. API Security

- All non-public API traffic uses HTTPS and the approved authentication
  integration.
- Routes are explicit and documented; undocumented methods, fields, state
  transitions, and privilege paths are not accepted.
- The API uses bounded pagination, filtering, sorting, body size, and query
  complexity. Bulk and long-running actions are asynchronous and quota-bound.
- Mutating commerce, payment, upload, role, moderation, and notification
  operations validate an idempotency key or equivalent replay control where
  required by their domain.
- The server recalculates prices, eligibility, permissions, shipping choices,
  and totals from authoritative state.
- Error responses are stable and actionable without disclosing stack traces,
  SQL, provider payloads, account existence, internal identifiers, or secrets.
- CORS, CSRF protections where browser credentials are used, allowed methods,
  content types, security headers, and origin policy are explicit per client.
- Administrative, export, search, upload, and authentication endpoints have
  tighter quotas than ordinary public reads.
- API versioning and deprecation must not silently weaken an existing control.

## 10. Input & Output Security

### Input

- Validate type, length, encoding, range, format, enum, relationship, current
  state, and authorization at the API boundary and again in the domain where
  state can change.
- Normalize Unicode and locale-sensitive values deliberately; preserve
  meaningful artwork text while rejecting control characters and unsafe
  encodings.
- Reject unexpected fields rather than silently persisting them.
- Validate redirect targets, URLs, sort/filter fields, pagination cursors,
  provider identifiers, and webhook timestamps against allowlists.
- Treat imported provider data, queue payloads, search results, and cached
  values as untrusted input.

### Output

- Serialize allowlisted response fields, not entire models.
- Apply field-level visibility for public, customer, artist, staff, and admin
  contexts.
- Never return passwords, password hashes, reset values, access/refresh
  tokens, API keys, provider secrets, payment credentials, private storage
  credentials, internal notes, or security answers.
- Escape or safely render user-authored text in HTML, email, notification,
  search, and admin contexts. User content is data, not markup or a template.
- Avoid exposing whether a private resource exists when the caller is not
  authorized to know.
- Do not put sensitive values in URLs, browser history, referrer headers,
  analytics events, push payloads, or translated strings.

## 11. Rate Limiting & Abuse Prevention

Rate limits are enforced server-side and applied by operation cost, principal,
account, IP/network, device/session signals where appropriate, and provider
quotas. Limits must not rely on a single spoofable header.

- Tight controls apply to login, registration, recovery, verification,
  password changes, token issuance, search suggestions, reports, exports,
  uploads, checkout, payment attempts, webhooks, and admin bulk actions.
- Public catalogue and search reads are bounded by pagination and response
  size and may use edge protection.
- Repeated failures, suspicious velocity, enumeration patterns, upload abuse,
  coupon abuse, fake orders, and notification abuse produce throttling,
  challenge, review, or temporary suspension according to policy.
- Rate-limit responses do not disclose account existence or internal thresholds
  unnecessarily and include a safe retry indication where appropriate.
- Provider quotas and queue backpressure are monitored separately so an abuse
  spike cannot exhaust email, push, payment, shipping, or worker capacity.
- Abuse controls preserve legitimate accessibility, bilingual use, retry,
  payment recovery, and support workflows.

## 12. Secrets Management

- Secrets are generated, stored, injected, rotated, and revoked through the
  approved environment secret mechanism; they are not committed to source,
  documentation, client bundles, images, or database seed data.
- Separate credentials exist for development, test, staging, and production.
  Services use distinct credentials and scopes rather than a shared master
  secret.
- Secrets are never logged, returned in errors, sent to clients, included in
  URLs, or placed in analytics and notification payloads.
- Provider keys, signing secrets, database credentials, encryption keys, and
  deployment credentials have an owner, rotation procedure, expiry/revocation
  path, and access audit.
- Rotation supports overlap where a provider requires it, but old values are
  removed promptly and tested without exposing them.
- A suspected secret leak triggers containment, revocation, replacement,
  affected-provider review, and evidence preservation.

## 13. Encryption & Data Protection

### Encryption in transit

- Public and internal service traffic uses TLS with certificate validation.
- Production databases, Redis, object storage, queues, provider calls, admin
  access, and observability transport use encrypted connections where
  supported by the service.
- Plain HTTP is redirected or disabled except for narrowly controlled
  bootstrap/health behavior that carries no sensitive data.
- Mobile and web clients must validate the platform's secure transport and
  must not disable certificate or hostname validation.

### Encryption at rest

- PostgreSQL volumes, Redis persistence where enabled, object storage,
  backups, logs, and exported data use provider/platform encryption at rest.
- Highly sensitive fields may require application-level encryption or
  tokenization after data classification and key-management approval.
- Encryption keys are separate from encrypted data and access is least
  privileged. Loss of a key must not be treated as a reason to retain
  unnecessary plaintext copies.
- Encryption does not replace authorization, deletion, retention, or audit
  controls.

## 14. Personal Data Protection

Personal data includes account details, contact information, addresses,
order history, support content, device data, notification preferences,
analytics identifiers, and any artist verification information.

- Classify fields by sensitivity and define purpose, access scope, retention,
  deletion, export, and lawful/consent basis for launch markets.
- Return only fields needed for the current screen or operational task.
- Separate public artist biography and approved portfolio data from private
  identity, payout, support, and verification data.
- Search, analytics, logs, notifications, and backups receive minimized or
  pseudonymized data where possible.
- Account deletion and data lifecycle rules follow [4.7 Data
  Lifecycle](4.7%20Data%20Lifecycle.md), including dependent media, sessions,
  notifications, search history, analytics, audit evidence, and backups.
- Legal holds, financial records, fraud evidence, and audit records may have
  controlled retention exceptions; exceptions are documented and access
  restricted.
- Privacy requests are authenticated, authorized, rate-limited, auditable, and
  protected from account-enumeration abuse.

## 15. Media & File Security

Media security follows [5.6 Media & Storage Architecture](5.6%20Media%20%26%20Storage%20Architecture.md)
and applies to artwork, avatars, documents, and generated derivatives.

- Uploads are accepted only through an authorized workflow with ownership and
  state checks.
- Enforce documented maximum size, dimensions, count, format, and processing
  limits before expensive work.
- Validate actual file content and signatures, not only filename or MIME
  headers. Reject archives, polyglots, executable content, malformed files,
  and unsafe metadata as policy requires.
- Quarantine new files until scanning, transformation, and moderation
  requirements complete. Workers process files in isolated, non-executable
  locations.
- Generate safe derivative names and storage keys; never use user input as a
  path or executable filename. Prevent path traversal and object overwrite.
- Strip unnecessary metadata, including location or device metadata, before
  public delivery where policy requires.
- Public derivatives are delivered through controlled, read-only paths.
  Originals, drafts, rejected assets, and private media are not public.
- Download and preview authorization is checked at request time. A signed
  URL, if used by 5.6, is short-lived, scoped to one object/action, and never
  logged.
- Media deletion, replacement, visibility changes, and failed processing
  invalidate dependent caches and preserve only the lifecycle evidence
  required by policy.
- Digital artwork protection is treated as risk reduction, not absolute
  prevention: use suitable resolution, derivatives, watermarking or previews
  where approved, disable unauthorized original downloads, and preserve artist
  ownership metadata. Do not promise that public images cannot be copied.

## 16. Payment Security

Payment behavior follows [5.10 Payment](5.10%20Payment.md) and the product
payments and checkout requirements.

- FANNAN does not expose or store raw card credentials unless a separately
  approved compliant architecture requires it. Prefer provider-hosted fields,
  tokenization, or redirects.
- Clients cannot set final amounts, currency, fees, commission, seller,
  discount, authorization status, refund status, or settlement outcome.
- The server validates cart, inventory/availability, shipping, address
  eligibility, pricing, and order state before initiating payment.
- Provider references are stored as minimally as possible and are treated as
  opaque identifiers, not authorization proof.
- Payment callbacks are signature-verified, replay-protected, idempotent, and
  reconciled against the expected order, amount, currency, and provider
  account before state changes.
- Payment states distinguish initiated, pending, authorized, captured,
  failed, refunded, partially refunded, disputed, and reconciled outcomes
  according to 5.10. The UI never claims success before authoritative
  confirmation.
- Refunds, payouts, settlement changes, and manual adjustments require scoped
  permission, reason, audit, and reconciliation.
- Logs and support screens show masked references and statuses only; never card
  numbers, security codes, provider secrets, or payment tokens.

## 17. Shipping Security

Shipping behavior follows [5.11 Shipping](5.11%20Shipping.md).

- A shipping address is private personal data. It is visible only to the
  owning customer and authorized fulfillment/support/admin contexts for the
  relevant order.
- Address selection, editing, and association with an order are server-side
  ownership and state-checked. Clients cannot attach another user's address
  or rewrite a confirmed order without an approved transition.
- Provider requests contain only the fields required for rate, label,
  fulfillment, or tracking. Provider responses are validated and minimized
  before persistence or display.
- Tracking pages and notifications use the minimum information needed and do
  not expose full addresses or private contact data.
- Shipping callbacks and tracking updates are authenticated where the provider
  supports signatures, correlated to the expected shipment, and idempotent.
- Labels, customs data, returns, and international shipping remain policy-
  and market-gated; future expansion does not silently widen MVP access.

## 18. Database Security

PostgreSQL is the durable source for authoritative account, catalogue,
commerce, and audit state.

- Use separate database roles for application reads/writes, migrations,
  workers, reporting, and administration. No application role is a superuser.
- Keep PostgreSQL on private network paths; restrict administration to
  controlled operator access and audited channels.
- Use parameterized queries and ORM/query-builder bindings. Never concatenate
  user input into SQL, identifiers, or migrations.
- Enforce the constraints and ownership relationships in [4.5 Database
  Constraints](4.5%20Database%20Constraints.md) and repeat security-critical
  checks in domain policies.
- Protect sensitive columns through access scope, encryption/tokenization where
  approved, and field minimization in queries and serializers.
- Migration and seed processes cannot contain production secrets or real
  personal/payment data.
- Backups are encrypted, access-controlled, tested for restoration, retained
  according to [4.7 Data Lifecycle](4.7%20Data%20Lifecycle.md), and excluded
  from ordinary application credentials.
- Database audit and query monitoring identify unusual reads, writes,
  privilege changes, exports, and failed access without logging sensitive
  values.

## 19. Redis Security

- Redis is private infrastructure with authentication, encrypted transport
  where supported, network restrictions, and no direct client access.
- Redis values are treated as cache/session/queue support data, not as the
  source of truth for authorization, payment, ownership, or order state.
- Keys include an explicit namespace and security scope. User- or role-
  specific data never uses a shared public key.
- Private cache entries are never served to a different principal. A cache
  miss or uncertainty is safer than a cross-user hit.
- Cache data is bounded, expires according to classification, and is
  invalidated on logout/session revocation, role changes, visibility changes,
  account deletion, and sensitive state transitions.
- Do not place passwords, raw tokens, provider secrets, payment credentials,
  or unencrypted high-sensitivity data in Redis.
- Rate-limit counters and queues are protected from unbounded key creation,
  spoofed identity dimensions, replay, and worker poisoning.
- Redis compromise is handled as credential and data exposure: revoke affected
  credentials, invalidate dependent sessions/caches, inspect queues, and
  restore authoritative state from PostgreSQL.

## 20. External Provider Security

Approved payment, shipping, email, push, storage, search, and analytics
providers are separate trust domains.

- Maintain an inventory of providers, purpose, data fields, region, contract,
  credentials, webhook endpoints, retention, and failure behavior.
- Send the minimum data needed for the operation. Do not send passwords,
  tokens, internal notes, full payment credentials, or unrelated profile data.
- Use separate provider projects/accounts/keys per environment and per
  capability where supported.
- Authenticate provider calls, validate TLS/certificates, apply timeouts,
  bounded retries and circuit breakers, and make side effects idempotent.
- Validate all provider responses and status transitions against internal
  records; provider data cannot grant a role or bypass ownership.
- Restrict provider egress and callback ingress to the documented endpoint and
  verification mechanism.
- Provider outage or compromise must degrade to a clear pending/error state,
  not fabricate success or expose raw provider diagnostics.
- Contracts and data-processing requirements are reviewed before production
  enablement and whenever fields or regions change.

## 21. Webhook Security

Each webhook endpoint is isolated by provider and purpose.

- Verify the provider signature over the exact raw request body using the
  secret managed for that provider/environment.
- Enforce timestamp tolerance, event-ID deduplication, replay protection,
  expected content type, body-size limits, and provider-specific event schema.
- Correlate the event to an existing internal object, expected provider
  account, amount/currency or shipment, and valid state transition.
- Acknowledge only after safely recording/queuing a validated event. Processing
  is idempotent and retry-safe.
- Never accept a client-originated request as a provider webhook.
- Do not include raw webhook bodies or signatures in ordinary logs; retain
  redacted evidence and event identifiers sufficient for investigation.
- Invalid, duplicate, late, and out-of-order events are observable and do not
  move state backward without an approved reconciliation path.

## 22. Dependency & Supply-Chain Security

- Pin and review direct and transitive dependencies through committed lockfiles.
- Use trusted registries, verify package integrity, and restrict install
  scripts and build-time network access where practical.
- Review security advisories and license changes before release; prioritize
  internet-facing, authentication, file-processing, cryptography, and payment
  dependencies.
- Keep Laravel, Next.js, Flutter, PHP, Node, mobile SDKs, image libraries,
  database clients, and infrastructure images within supported security
  versions.
- Protect CI/CD credentials and require review for workflow, dependency,
  migration, permission, and deployment changes.
- Scan built artifacts and containers where the environment supports it.
- A vulnerable dependency has an owner, severity decision, mitigation,
  upgrade/replacement plan, and documented exception if not immediately fixed.

## 23. Security Logging & Auditing

Security logs are operational evidence, not a copy of application data.

Record, as appropriate:

- Authentication success/failure, recovery, verification, session/device
  changes, lockouts, and suspicious activity.
- Authorization denials, ownership failures, privilege changes, staff scope
  changes, and access to sensitive operations.
- Upload quarantine/rejection, media visibility/deletion, moderation, export,
  privacy requests, and account lifecycle events.
- Payment, refund, payout, shipping, webhook, provider, and reconciliation
  outcomes with safe references and state transitions.
- Rate-limit, abuse, secret-rotation, configuration, deployment, backup, and
  incident events.

Each auditable event includes timestamp, actor/principal or service,
action, target type and safe identifier, result, reason/context, and
correlation ID. Logs exclude passwords, tokens, API keys, provider secrets,
payment credentials, full addresses, raw files, and unnecessary message
content. Access to logs is role-scoped, encrypted, retained and deleted
according to policy, and itself audited. Audit records are append-oriented;
corrections preserve history rather than erasing evidence.

## 24. Security Monitoring

Monitor availability and security signals together:

- Authentication failures, recovery spikes, token/session anomalies, and
  unusual role or permission changes.
- IDOR/authorization denial rates, enumeration, scraping, rate-limit hits,
  upload rejection, malware detections, and abusive reports.
- Payment mismatches, duplicate callbacks, refund anomalies, shipping
  callback failures, notification provider abuse, and reconciliation gaps.
- Cache isolation errors, Redis saturation, database privilege changes,
  unexpected exports, backup failures, and secret use from new locations.
- Dependency advisories, deployment changes, TLS/certificate expiry, and
  provider outage or contract failures.

Alerts are severity-ranked, actionable, deduplicated, assigned to an owner,
and tested. Monitoring must not become a second source of sensitive data or
expose secrets in dashboards and alert messages.

## 25. Incident Response

FANNAN incident response follows these principles:

1. **Prepare:** Maintain contacts, ownership, provider escalation paths,
   runbooks, asset inventory, backup evidence, and access to safe logs.
2. **Detect and classify:** Confirm scope and severity while preserving
   evidence. Treat account, payment, personal-data, media, and privilege
   incidents as distinct impacts where appropriate.
3. **Contain:** Revoke sessions or secrets, disable an endpoint/integration,
   quarantine media, restrict access, throttle abuse, or place a workflow in
   pending state without destroying evidence.
4. **Eradicate and recover:** Patch or rotate, remove malicious artifacts,
   reconcile PostgreSQL with providers, restore from verified backups when
   necessary, and re-enable capabilities gradually.
5. **Communicate:** Notify internal owners, affected users, providers, and
   authorities according to legal and contractual requirements. Notifications
   contain only approved information.
6. **Learn:** Record timeline, root cause, affected data, decisions,
   corrective actions, tests, and owners. Update architecture and controls.

No incident response action should conceal failure by rewriting audit history,
silently deleting evidence, or claiming payment/order success prematurely.

## 26. Environment Security

- Development, test, staging, and production have separate accounts,
  databases, buckets, Redis instances, provider projects, keys, domains, and
  notification destinations.
- Production access is individually assigned, time-bounded where practical,
  audited, and protected with the authentication controls in 5.5.
- Lower environments use synthetic or irreversibly redacted data. Production
  exports require approval, minimization, encryption, expiry, and audit.
- Production deployments require reviewed changes, migration safety,
  rollback/recovery evidence, dependency status, and security/privacy checks.
- Network paths, firewall rules, service identities, administrative access,
  secrets, and observability destinations are explicit per environment.
- Debug mode, verbose errors, test credentials, permissive CORS, public
  buckets, and development webhooks are prohibited in production.
- Health checks expose only non-sensitive liveness/readiness information.

## 27. MVP Security Scope

MVP security includes:

- Server-enforced authentication and the exact role/capability model in 5.5.
- Ownership and authorization checks on every protected resource and action.
- HTTPS, secure secret handling, password protection, session/token controls
  defined by 5.5, and security notifications.
- Input/output validation, injection protection, bounded pagination, rate
  limits, abuse controls, and safe errors.
- Private PostgreSQL, Redis, object storage, encrypted backups, and isolated
  environments.
- Quarantined and validated artwork uploads with controlled public derivatives.
- Provider-minimized payment and shipping flows with signed, idempotent
  callbacks and no raw payment credentials.
- Privacy-safe notifications, search, analytics, logs, cache behavior, and
  deletion/retention integration.
- Audited staff actions, monitoring for critical security events, incident
  runbooks, dependency review, and release blocking for critical unresolved
  security or privacy defects.

MVP does not claim to provide DRM, perfect screenshot/download prevention,
fully automated fraud detection, unrestricted international shipping, SMS
security flows, auctions, NFTs, or broad future staff roles.

## 28. Future Extensions

Future security work may include:

- Stronger administrator assurance, step-up authentication, hardware-backed
  credentials, and privileged-access management.
- Formal privacy consent/rights automation and regional data residency.
- Dedicated fraud/risk scoring, anomaly detection, and payment dispute
  controls after approved policy and data governance.
- Malware scanning and media provenance improvements at larger scale.
- Fine-grained data-loss prevention, customer-managed privacy controls, and
  verifiable artist ownership/provenance.
- Security tests in the full mobile release pipeline, penetration testing,
  red-team exercises, and formal threat-model reviews.
- Provider failover, multi-region recovery, key-management service
  integration, and stronger disaster-recovery objectives.
- Security architecture for auctions, public social content, direct
  messaging, international shipping, courses, and any NFT-related feature
  only when those features are approved.

## 29. Alternatives Considered

| Alternative                                               | Decision                                                                                            |
| --------------------------------------------------------- | --------------------------------------------------------------------------------------------------- |
| Client-side authorization                                 | Rejected. Clients are untrusted and cannot enforce resource ownership or role boundaries.           |
| A second security-specific role/permission model          | Rejected. 5.5 is the authorization source of truth; this document integrates with it.               |
| Store raw card data in FANNAN                             | Rejected for MVP. Use approved provider-hosted or tokenized payment handling.                       |
| Public S3 bucket for simple media delivery                | Rejected for originals/private media. Use controlled public derivatives and authorized access.      |
| Redis as the authority for permissions or orders          | Rejected. PostgreSQL/domain state remains authoritative.                                            |
| Log complete requests for easier debugging                | Rejected. Logs are minimized and redacted to avoid credential and personal-data leakage.            |
| Trust provider webhooks because they originate externally | Rejected. Signatures, replay controls, correlation, state validation, and idempotency are required. |
| Use one credential across services and environments       | Rejected. Isolation limits blast radius and supports rotation.                                      |

## 30. Tradeoffs

- **Security versus friction:** Throttles, verification, and re-authentication
  can add friction, but are limited to risky or high-impact actions and must
  preserve accessible recovery.
- **Privacy versus supportability:** Staff see less raw data, requiring
  masked identifiers and controlled escalation rather than unrestricted
  browsing.
- **Artwork protection versus discovery:** Public derivatives improve
  discovery but cannot prevent all copying; stronger controls may reduce
  conversion and accessibility.
- **Fresh authorization versus performance:** Private and high-impact actions
  favor authoritative checks over aggressive caching. Public content may use
  cache with safe eligibility and invalidation.
- **Provider resilience versus complexity:** Timeouts, retries, reconciliation,
  and pending states prevent false success but require operational tooling.
- **Auditability versus data minimization:** Events retain safe evidence and
  state transitions, not complete sensitive payloads.
- **MVP scope versus assurance:** The controls here address credible launch
  threats while deferring costly enterprise controls until scale and policy
  justify them.

## 32. Consistency & Open Issues

The following consistency rules are release gates:

- 5.5 must remain the only authentication and authorization behavior source;
  all endpoint policies must map to it.
- 5.6, 5.9, 5.10, 5.11, and 5.12 must define the concrete provider,
  storage, notification, payment, shipping, and cache contracts without
  weakening the controls in this document.
- 4.5 must enforce the ownership and integrity assumptions used by policies.
- 4.7 must specify legal retention and deletion periods for accounts,
  addresses, payment records, notifications, analytics, media, logs, and
  backups.
- Launch markets, currencies, payment providers, shipping providers,
  retention/legal basis, upload limits, staff access approval, and incident
  contacts remain explicit product/operational decisions before production.
- Exact rate-limit quotas, severity thresholds, encryption key service,
  backup recovery objectives, provider regions, and vulnerability response
  targets require environment and operations approval.
- Any later change to a role, resource, cache class, provider payload,
  notification channel, or data lifecycle requires a security review.
